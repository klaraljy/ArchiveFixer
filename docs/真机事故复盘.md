## 3. 分卷名后面粘着垃圾（2026-09-28 真机事故）

- **分卷名后面粘着垃圾（2026-09-28 真机事故，用户当场报）**：百度网盘给每个分卷名缀「删除」
  （`giu910.7z.001删除` / `.002删除` / `.003删除`）。老判据要求"卷标记必须是最后一段" → 三卷散成三个任务，
  而且「修正后缀」把它们改成 `amb909.7z` / `amb909(1).7z` —— **卷号被吃掉、分卷链断掉**（内容没坏，名字对不上）。
  修法：`ExtensionHelper.TrySplitVolumeSegment`（**判据只此一处**）把段拆成「分卷标记 + 粘着的垃圾」，
  `FileNameHelper.IsVolumePartFileName` / `StripVolumeMarkers` 与 `VolumeGroupDetector` 全转调它，
  垃圾记进 `VolumeNameInfo.Tail`（缺卷提示才会带同样的尾巴）；`RenameService` 那道"分卷不许改名"的闸门因此自动生效。
  - ⛔ 老口径**不许回退**：另起一段的后缀（`x.7z.001.txt` / `x.001.bak`）照旧**不算**分卷；纯数字尾巴（`0012`）不猜。
  - ⚠ **遗留**：程序只做到"认得出 + 不改坏"；带垃圾尾巴的组交给 7-Zip 仍会报缺卷（7z 只认 `<基名>.001` 这套名）。
    下一步要做的是**显式**的「把整组名字改回标准名」（沿用 `VolumeNameRepair` 的口径：用户点了才改、只改名字、绝不覆盖）。
  - 用真实数字钉住：`giu910` 三卷 7,516,192,768 ×2 + 3,975,934,338；`amb909` 现场 = 第一卷 2,147,483,648（带 `37 7A BC AF 27 1C`）
    + 第二卷 1,890,791,346。用例 `VolumeJunkTailTests`（**31 条** / 10 个方法），红检时把修复 stash 掉会红 8 条。
  - ⚠ **判据不许"一见 zip 成员就让位"**（2026-09-29 复核逮到的真缺陷）：名字路（`VolumeNameRepair.PlanJunkTailGroup`）
    原来看"手上这一片内容是跨盘 zip 成员"就把整组让给内容级那条路。可 **7-Zip 自己造的 `-tzip -v` 分卷 zip**
    第 1 片也是"PK 开头、结尾没标记的成员"，而它的**末片 EOCD 写的是盘号 0**（不是 PKZIP 那套跨盘 EOCD）→
    内容级拼不出组 → 名字路又让了位 → **两边都不动**：`enc.zip.001删除` 一个名字都没改，
    7-Zip 打不开（实测 `7z l` 报 ERRORS、`Type = zip`），任务还把它报成「密码错误」。
    现在让位条件是"**目录里真有一片自述带盘号的跨盘 zip 末片**"（`HasSpannedZipTailInDirectory`，判据仍只问
    `VolumeNumberFromContent`）；真 PKZIP 那套（`.z01`/`.zip`）照旧走内容级。用例 `EncryptedVolumePipelineTests`（2 条）。

## 4. 安装包（NSIS .exe，2026-09-27 追加 → 09-28 验收）

- **安装包（用户 2026-09-27 追加："我是要 .exe 安装文件的"）**：`installer\ArchiveFixer.nsi`（NSIS 3.10，
  `D:\Codex Tools\NSIS\nsis-3.10\makensis.exe`）+ `scripts\installer.ps1`（默认拿 `dist\ArchiveFixer-<版本>-独立`
  当内容）→ `dist\ArchiveFixer-0.1.0-setup.exe`（**47.82 MB**，164.57 MB 内容压到 29.1%，编译约 110 秒）。
  - 装法：**每用户、`RequestExecutionLevel user`（不弹 UAC）**，默认 `%LOCALAPPDATA%\ArchiveFixer`（安装页可改）；
    ⛔ 绝不能默认 `C:\Program Files\`（程序要往自己目录的 `data\` 写日志 / 设置 / 密码列表，那儿没写权限）。
  - 卸载**默认保留 `data\`**（交互式会问一次；`/S` 静默卸载一律保留）。⛔ 不许改成"卸载就清空"。
  - ⚠ `.nsi` **必须 UTF-8 带 BOM**（否则 makensis 直接报 `Bad text encoding`）；
    ⚠ **注释行末尾不要留反斜杠**（NSIS 当续行符，会把下一行命令吞掉 —— 实测 FindFirst 那一行被吞过）；
    ⚠ 命令行开关的判据只读 `${GetOptions}` **返回值**，别靠 `IfErrors`（实测搞反过 → 静默装也建快捷方式）；
    ⚠ 卸载删桌面 `.lnk` 前必须看安装时写的 `DesktopShortcut` 标记，否则会删掉**用户自己的**快捷方式（实测踩到，
      用户桌面那个 `E:\ArchiveFixer\` 的快捷方式被删过一次，已重建）。
  - **验收（2026-09-28 凌晨，静默模式走完两条路）**：`/S /D=<临时目录>` 装出 **478 个文件 / 164.73 MB**，
    `ArchiveFixer.exe` / `ArchiveFixer.dll` / `tools\7zip\7z.exe` 与发布目录**逐字节相同**（SHA256 比对）；
    静默装**不建**快捷方式、不写标记；`/S /SHORTCUTS=1` 会建桌面 + 开始菜单并写标记（卸载时按标记删干净）；
    两轮卸载后程序文件 / `tools` / `docs` / 本地化目录全清、注册表两条键全清、**`data\keepme.txt` 都保住了**、
    用户桌面快捷方式（`E:\ArchiveFixer\ArchiveFixer.exe`）**毫发无损**；装出来后跑过一次，程序正常起窗口、
    自己建出 `data\appsettings.json` + `password-list.dat` + 日志。
  - 本地另存一份：`E:\ArchiveFixer-0.1.0-setup.exe`（用户："这个本地也要留一份就放在独立版旁边"）；
    Release 上的资源名 `ArchiveFixer-0.1.0-setup.exe`（label `ArchiveFixer-0.1.0-安装包.exe`）。

## 14. 源包不许算两遍（2026-09-29 真机事故）

- ⛔ **源包不许算两遍（2026-09-29 真机事故，用户当场报"普通人随便都能解压"）**：
  判据是 `TaskSpaceEstimate.FreeSpaceDemandBytes`（**唯一出口**）= `ContentBytes + ProcessArtifactBytes`
  = "这次要从**可用空间**里新写多少"，`ScheduledExtractionItem.RequiredBytes` 与
  `ExtractionCoordinator.ReconcileReservation`（解压前预检那道门，`:8814/8824`）都只读它；
  `PeakBytes`（源包 + 过程物 + 内容物）**降级成描述**，⛔ 绝不许再拿它去比可用空间。
  - 真机现场：三卷 7,516,192,768 ×2 + 3,975,934,338 = **19,008,319,874 B（17.70 GiB）**，
    目标盘 H: 可用 **35,916,664,832 B（33.45 GiB）**。老口径算 `17.70 + 17.70 = 35.41 GiB > 32.95 GiB`（可用 − 512 MiB）
    → 判"整盘都放不下"（差 2.46 GiB），**日志里连一次引擎调用都没有**（被空间门拒了）；
    正确算式 `内容物 + 过程物 = 17.70 GiB ≤ 32.95 GiB` → **放行（余 15.25 GiB）**。
  - **为什么错**：可用空间**本来就不含**盘上现有的东西（含源包）——源包搬进同盘 `其余物` 也不产生新字节；
    盘上塞得下的恒等式是"本次新写 ≤ 可用 − 余量"。同一件事在 `Security/ResourceBudget.CheckFreeSpace`
    里一直是对的（比的是纯内容物），错的是任务级那道门。
  - **「空间不足」模式不需要另立判据**：源包在两种档下都不进需求（它已经在盘上）；那个模式的差别只体现在
    "跑完把源包收回来、下一个包更宽"（`RunScheduledTaskAsync` 每个任务收尾都真实重探可用空间）。
  - 用例 `SpaceDemandAccountingTests`（5 条：真机那一单 → 放行 / 可用 8 GiB → **必须拒绝并报差多少** /
    内容物真超可用 → 照旧拒绝 / 模式同一口径且"净占用小≠放行" / **真样本只读**：环境变量
    `ARCHIVEFIXER_REAL_SPACE_CASE_DIR` 指向真机那一组，用产品代码在真文件 + 真可用空间上算一遍，
    不在就跳过并说明）。红检：把 `FreeSpaceDemandBytes` 改回 `PeakBytes` → **8 条红**。
  - ⚠ **两处"差多少"的分母本来就不同**（`SpaceGate` 按可用空间、`ExtractionScheduler` 排计划按可用 − 余量），
    本次没动；要改先想清楚"余量算不算差额"。

## 31. 已修：RAR 卷内容加密，识别阶段读不出"加密"（2026-09-30）

- **用户原话**（2026-09-29 那一轮之后追加的整改要求）："那你就去读啊，这不是必要的程序吗" —— 批准了
  「自己解析 RAR 加密标志」这个方案（⛔ 不额外调引擎、⛔ 不引依赖）。
- **现场（第 30 节那份实测）**：三套真包里 `222` 的跨盘 zip 第一片 `IsEncrypted=True`，
  而 `111` / `333-Rar4` 两套 RAR4 卷 `IsEncrypted=False` —— 内容确实加密（`7z l -slt` 每个 mp4 `Encrypted = +`）。
  后果：①「本批有 N 个包没有可用密码」（`FindTasksWithoutUsablePassword` 只看 `IsEncrypted`）对 RAR **漏报**；
  ②一键档"要不要提醒你去确认框填密码"跟着漏。
- **根因**：识别阶段只读开头几个字节看魔数（`ArchiveDetectService.DetectByHeader`），
  RAR 的**块结构一个都不解析** —— 而"加没加密"这件事恰恰写在块的 flags 里。
- **修法**：新增 `Detection/RarEncryptionReader`（**只读头、不调引擎**，单文件读入量硬上限 **64 KiB**，
  数据区一律 seek 跳过），判据**只此一处出口**，接线在 `ArchiveDetectService.ApplyRarEncryptionVerdict`
  （识别与"尾部内嵌 RAR"两条路共用它，取回缓存后再叠这一层）。判据与出处：
  · **RAR5**（官方格式说明 `https://www.rarlab.com/technote.htm`）：签名后第一个头是**类型 4**（Archive encryption
    header，原文"This header is present only in archives with encrypted headers"）= **头也加密**（`-hp`）；
    文件/服务头（类型 2/3）**扩展区**里出现记录类型 **0x01**（File encryption，原文"This record is present if
    file data is encrypted"）= **只有数据加密**（`-p`）。
    ⚠ 主归档头（类型 1）的 `ArchiveFlags` 里 **0x0004 是 Solid（固实归档），不是"有密码"** ——
    任务书里那句按记忆写的"0x0004 = 有密码"**与官方说明不符**，按官方说明实现（拿 Solid 当密码会把一大批
    普通固实包误报成加密）。
  · **RAR 1.5–4.x**（WinRAR 里叫 RAR4，签名 `52 61 72 21 1A 07 00`）：主头（type `0x73`）的
    `MHD_PASSWORD = 0x0080` 置位 = **该头之后的块全是密文**（`-hp`）；文件/服务头（type `0x74` / `0x7A`）的
    `LHD_PASSWORD = 0x0004` 置位 = **该条目数据加密**（`-p`，文件名照样看得见）。常量取自 unrar 的移植版
    junrar `BaseBlock`（RAR5 官方说明本身就写着"更细的数据结构请用 UnRAR 源码"），并用本机 WinRAR 的
    `Rar.exe` 现造的真样本**逐字节核过**：`-ma4 -p…` 主头 flags `0x0000` + 第一个文件头 `0x0024`；
    `-ma4 -hp…` 主头 flags `0x0080` 且其后全是密文；`-ma5 -hp…` 签名后第一个头类型 = `4`。
  · 读不出来（截断 / 布局不符 / 头 CRC 对不上）一律返回 **"不知道"**，⛔ 绝不猜（宁可漏报不误报）；
    多卷只看**第 1 卷**（主头与第一个文件头都在它里面），⛔ 绝不去遍历 `VolumePaths` 要求"每卷都报加密"
    （那会把"续卷读不出来"当成"没加密"，整组当场判否）。
- **用例**：`RarEncryptionReaderTests` **13 条**（RAR4/RAR5 × `-p`/`-hp` 四种 + 两个不加密对照组 +
  多卷只看第 1 卷 + 识别阶段四种都认出来/对照组不误报 + 截断/坏头/非 RAR/文件不存在 → 不知道 +
  头 CRC 坏掉 → 连"没加密"都改口成"不知道" + 读入量 ≤ 64 KiB + 不知道与没加密结论分得开）。
  样本现场造、⛔ 不入库、密码用占位符 `<sample-password>`。
- **红检**：① 把接线那行 `ApplyRarEncryptionVerdict` 摘掉 → **2 条红**（识别阶段那两条）；
  ② 把 `RarEncryptionReader.Read` 改成恒返回 Unknown → **11 条红**（13 条里只剩两条"断言返回不知道"的照绿）。
  恢复（`--no-incremental` 重编）后 13 条全绿。
- **顺带修的**：RAR4 的签名是 **7 字节**（RAR5 是 8 字节），一开始按 8 字节读会把主头的第一个字节
  （HEAD_CRC 低字节）吃掉 → 块头 CRC 对不上 → RAR4 三条全红、RAR5 三条全绿。现在按各自长度读
  （RAR5 那第 8 个字节必须 `0x00`，读掉它头链才对齐）。
- ⚠ **遗留（如实记）**：`-p` 这一档的"每个文件头都带 LHD_PASSWORD"在**多条目**包里只辨认到**第一个**就返回
  （结论一样，不影响判定），但"某一条目加密、另一条目不加密"这种混合包只会报"有加密" —— 判据本来就是
  "这一包要不要密码"，够用。

## 33. 已修：ZIP 与 7z 的加密标志，识别阶段读不出来（用户 2026-09-30）

> 与 §31（RAR 那一版）**完全对称**：只读头/尾、不调任何引擎、不引依赖、读不出来一律"不知道"（⛔ 绝不猜、绝不误报）。
> 本节的字节表都是 2026-09-30 用内置 `src\ArchiveFixer\tools\7zip\7z.exe` 现造样本、逐字节核过的。

### 33.1 现象

- **ZIP（真缺陷，有实测样本）**：`7z a -tzip -p<pw> dirfirst.zip sub` 造出来的包里，
  第一个本地头是**目录条目** `sub/`、flags = `0x0000`，第二个条目 `sub/inner.txt` 才是加密的
  （中央目录两条记录 flags = `0x0000 0x0001`）。旧实现判成"**没加密**" ⇒ 漏报。
  混合包同理：`mixed.zip` 的中央目录 flags = `0x0001 0x0000 0x0001`。
- **7z（整档漏报）**：识别阶段过去只看开头 6 个魔数字节，7z 的加密信号写在 **coder 链**里，
  6 个字节里根本看不见。`-mhe` 那一档最狠：`7z l -slt` 对这个包**一条都不列**（连文件名都看不见，
  更没有 `Encrypted` 行）—— 也就是说**程序现在完全不知道它加密**，而它恰恰是最需要密码的那一档。
- **多卷 7z**：7z 分卷是**原样切**的，元数据在**最后一卷**，"只看第 1 卷"永远读不出加密。

### 33.2 判据现场（逐字节量到的）

**7z 起始头 32 字节** = 签名(6) + 版本(2) + StartHeaderCRC(4) + `NextHeaderOffset`(LE64，相对偏移 32) 8 +
`NextHeaderSize`(LE64) 8 + NextHeaderCRC(4)。

| 样本 | NextHeaderSize | next header 头几个字节 | 结论 |
|---|---|---|---|
| `plain.7z`（单文件，无密码） | 90 | `01 04 06 00 01 09 c4 13 00 00 07 0b 01 00 01 21 21 01 0c …`（`01` = kHeader） | 明文头、无 AES ⇒ **不加密** |
| `datapw.7z`（`-p`，单文件） | 122 | `01 04 06 … 07 0b 01 00 02 24 06 f1 07 01 12 53 …` | 明文头里有 `06 f1 07 01` = AES-256 ⇒ **数据加密** |
| `mhe.7z`（`-p -mhe=on`） | 49 | `17 06 c4 20 00 01 09 80 80 00 07 0b 01 00 01 24 06 f1 07 01 12 53 …` | `17` = kEncodedHeader + AES ⇒ **头加密** |
| `many-plain.7z`（80 文件，无密码） | 35 | `17 06 80 83 01 09 83 32 00 07 0b 01 00 01 23 03 01 01 05 5d …` | `17` + `03 01 01`(LZMA) 无 AES ⇒ **读不出来** |
| `many-p.7z`（80 文件 + `-p`） | 35 | `17 06 80 90 01 09 83 50 00 07 0b 01 00 01 23 03 01 01 05 5d …` | **只有 LZMA、看不见 AES —— 但数据确实加密** ⇒ **必须"不知道"** |
| `many-mhe.7z`（80 文件 + `-mhe`） | 63 | `17 06 80 90 01 09 83 50 00 07 0b 01 00 02 24 06 f1 07 01 12 53 …` | `17` + AES ⇒ **头加密** |

- 四个单文件样本都满足 `32 + NextHeaderOffset + NextHeaderSize == 文件长度` —— 这条自洽式就是**布局闸门**。
- **`many-p.7z` 那一档是本次最关键的发现**：引擎侧 `7z t -pWrongPassword` 报
  `ERROR: Data Error in encrypted file. Wrong password?`（正确密码 → `Everything is Ok`），
  而它的编码头与**不加密**的 `many-plain.7z` 在这 64 KiB 里**逐字节同构**（都只有 LZMA）
  ⇒ 头被压缩时文件数据的 coder 链要**解压之后**才看得见，这一档**只能说"不知道"**，
  ⛔ 说"没加密"就是误报、说"加密"就是猜。

**多卷 7z**（`-v100k`，真样本实测）：`vol-p.7z` 三卷共 300,186 B，`NextHeaderOffset = 300032`、`NextHeaderSize = 122`
⇒ `32 + 300032 + 122 = 300186` = **三卷长度之和**。第 1 卷只有 102,400 B ⇒ 单看它必然越界（如实"不知道"）。
`vol-mhe.7z` 同形（`17` + AES）。

**ZIP**：EOCD `PK\x05\x06` 在文件尾（22 字节 + 注释长度）—— 条目总数 +10(LE16)、中央目录**大小** +12(LE32)、
**偏移** +16(LE32)，偏移都相对 zip 起点；中央目录记录 `PK\x01\x02` 的 flags 在记录内 **+8**（LE16，bit0 = 加密）；
本地头 `PK\x03\x04` 的 flags 在 **+6**；ZIP64 走 EOCD 前 20 字节的 `PK\x06\x07` 定位器 → `PK\x06\x06` 记录
（中央目录大小 +40、偏移 +48，均 LE64）。

- **跨盘 zip 第 1 卷**（真样本实测，`222.z0…` 那一片的前 8 字节）：
  `50 4b 07 08 50 4b 03 04` —— **跨盘标记后面紧跟本地头签名，本地头就在 `+4` 处**，中间**没有**盘号字段。
  旧实现在这个形态下读 offset 6-7，那两字节落在本地头签名的后半里，与"加没加密"毫无关系。
- 引擎侧对照（无密码 `7z l -slt`）：普通 zip `Encrypted = -`；`-p` 的 zip 每个条目 `Encrypted = +`；
  `-mhe` 的 7z **一条都不列**。

### 33.3 根因（`文件:行号` 级）

1. **ZIP 漏报**：`src/ArchiveFixer/Services/ArchiveDetectService.cs:1295` 的 `IsZipProbablyEncrypted(header)`
   只读 `header` 的 offset 6-7（= **第一个本地头**的通用位标志 bit0），两个调用点在 `:936`（`ZIP`）与 `:966`（`ZIP_SPANNED`）。
   "第一个条目不是加密的"被当成了"整包没加密"—— 而 ZIP 允许**逐个条目**加密。
   跨盘那一档更错：`PK\x07\x08` 形态下 offset 6-7 压根不是 flags。
2. **7z 整档漏报**：识别阶段只有 `DetectByHeader` 的 6 字节魔数（`src/ArchiveFixer/Services/ArchiveDetectService.cs:875`），
   7z 的块结构一个都不解析 ⇒ `-p` / `-mhe` 两档都看不出。
3. **多卷 7z**：元数据在最后一卷，而当时的判据入口（`ApplyRarEncryptionVerdict`）只拿得到单文件路径。

### 33.4 修法（唯一出口仍然是同一个方法）

- 新增**共享词表** `src/ArchiveFixer/Detection/ArchiveEncryption.cs`：
  `ArchiveEncryptionState { Unknown, NotEncrypted, DataEncrypted, HeadersEncrypted }` + `ArchiveEncryptionReading`
  （`State` / `Basis` / `BytesRead` / `IsEncrypted`）。**RAR 那一版也改成用它**（原来的 `RarEncryptionState` /
  `RarEncryptionReading` 两个类型删掉，13 条用例只是机械改名、断言一个字没动）—— 结论词表从此**只有一套**。
- 新增 `src/ArchiveFixer/Detection/ZipEncryptionReader.cs`：`Read(path, startOffset = 0)` 从文件尾往前找 EOCD
  （窗口 ≤ 64 KiB + 22，逐个候选做自洽校验）→ ZIP64 走定位器 → 定位中央目录（绝对位置 = `startOffset + 相对偏移`，
  越界即失败）→ **分块扫中央目录，见到第一个 bit0 就停**（4 KiB 缓冲 + 变长部分 seek 跳过，
  扫过的字节硬上限 **1 MiB**，超了 ⇒ 读不出来）。
- 新增 `src/ArchiveFixer/Detection/SevenZipEncryptionReader.cs`：读起始头 32 字节 → 校验签名与布局
  （`32+off+size > 文件长度` ⇒ Unknown）→ 读 next header 前 `min(size, 64 KiB)` → **结构化解析**
  （⛔ 不是全文搜 `06 f1 07 01`：文件名是 UTF-16LE，理论上撞得上）：
  `kHeader(0x01)` → `[kArchiveProperties(0x02)] [kAdditionalStreamsInfo(0x03)] [kMainStreamsInfo(0x04)]`，
  `StreamsInfo` = `[kPackInfo(0x06)] [kUnPackInfo(0x07)：kFolder(0x0B)] [kSubStreamsInfo(0x08)] kEnd(0x00)`；
  coder = flags（低 4 位 ID 字节数 / `0x10` 复杂 / `0x20` 属性）→ ID → 可选入出流个数 → 可选属性；
  数字是 7z 变长编码（首字节高位连续 1 的个数 = 后续字节数）。**只解析到能判定 coder 就停**。
- **出口扩成 `ArchiveDetectService.ApplyEncryptionVerdict(result, filePath, offset = 0, volumePaths = null)`**
  （原 `ApplyRarEncryptionVerdict`），按 `result.Format` 分派 RAR / ZIP / 7z；
  **四个调用点**都走它：`:244` 缓存命中、`:252` 常规、`:413` 尾部内嵌、以及 `ApplyDetectResultAsync` 里
  `task.IsEncrypted = …` 那一刻（**多卷 7z** 带卷组再走一遍同一个出口）。

### 39.2 根因一句话

## 41. 已修：跨盘 ZIP 多分了几片就解不开（"本体干净、续卷被改坏"那一档没人管）（2026-10-01 第七报）

### 41.1 用户报什么

> 「又出现了问题 `…\DDD\ArchiveFixer-本次操作_20261001_180915.txt`，我这次将 zip 多分了几个卷你就弄不了了」

盘上现场（`DDD`）：

```
DDD\111\111\            5 个 mp4（4 卷 RAR 正常解完 ✓）
DDD\222\222.z0删1       200 MB   ← 续卷，名字里塞了「删」
DDD\222\222.z除02       200 MB   ← 续卷，塞了「除」
DDD\222\222.z文03       200 MB   ← 续卷，塞了「文」
DDD\222\222.zip          49 MB   ← 本片（干净的标准名）
DDD\222\222\            不存在（这一单失败了，什么都没产出）
```

日志（`ArchiveFixer_20261001_180804.log` 第 70-73 行）：

```
├ 第 0 层：222.zip：引擎调用：7z x -bsp1 -sccUTF-8 222.zip -y -aos -p******
├ 第 0 层：222.zip：7-Zip 原话：ERROR = Missing volume : 222.z01 ｜ Sub items Errors: 6
├ 第 0 层：222.zip：解压失败：分卷压缩包缺少必要分卷
```

⇒ 222 那一单落 Failed，四个源包一个都没进其余物（红线：失败不动源，这是对的；但**它本来不该失败**）。

### 41.2 根因：名字那条路的**两个入口**都把这个形状挡在外面

| 挡在哪 | 判据 | 为什么挡掉了 |
|---|---|---|
| ① 协调器入口 | `FileNameHelper.IsVolumePartFileName("222.zip")` | `.zip` 是**本体后缀**、不是卷标记 ⇒ **false** ⇒ 名字那条路压根没跑（真机 DDD 的 111 组能修，正因为它的任务是 `111.part删1.rar`，`part删1` 算卷标记） |
| ② 计划内部 | `PlanJunkTailGroup` 的 `TrySplitDisguised("222.zip")` | 这一档要求**自己**的名字里带垃圾；本体是标准名 ⇒ false ⇒ 走不到"整组改"那条路 |
| ③ 老的单卷路 | `RawSplitStreamDetector.FindSiblingVolumes` | 它按**标准名**找兄弟（`.z01`/`.002`）⇒ 认不出 `222.z0删1` 这种"垃圾塞在卷标记里面"的续卷 ⇒ `Cannot(NoSiblings)` |
| ④ 内容那条路 | `VolumeNumberFromContent` 对跨盘 ZIP | 末片 EOCD 有盘号、**非末片只有跨盘标记** ⇒ 只有 **2 片**能用消去法定序 ⇒ **4 片判不出顺序** |

四条一起 ⇒ 一个名字都不改 ⇒ 7-Zip 找不到 `222.z01` ⇒ 整包解不开。用户那句「多分了几个卷你就弄不了了」精确到位：**2 片时内容路能救，3 片以上就没人管了**。

### 41.3 修法

1. `Extraction/VolumeNameRepair.cs` 新增 **`PlanDisguisedVolumesBesideStandardSelf`**，排在
   「名字里得有卷号」「必须是第 1 卷」那两道门**之前**（这两道门是为"**本体自己**被改坏"设计的）：
   - 自己去杂质后是标准名（`TrySplitDisguised` 为 false）；
   - 同目录里找"去杂质后与**自己的基名**逐字相等"的兄弟
     （基名唯一出口 `OutputPlacement.ResolveArchiveBaseName`：剥卷标记 + 剥已知归档后缀，
     `222.zip` → `222`；`222.z0删1` 去杂质后基名也是 `222` ⇒ 同组）；
   - 每一卷改成 `基名.规范卷标记`（`222.z0删1` → `222.z01`、`222.z除02` → `222.z02`…）；
   - ⛔ 判据只用名字：卷标记必须**互不相同**（两个文件还原成同一个卷名 ⇒ 有歧义 ⇒ 整组不动）、
     **目标名一个都不许被占**（占了 ⇒ 整组不动）、⛔ 只改名字、内容一个字节不动、全成或全不成
     （执行体仍是 `TryApply` + 倒序回滚）。
   - ⚠ `CurrentPath/TargetPath` 必须指向**真要改的那一卷**（按名字序取第一卷），
     ⛔ **不能**指向调用方手上那个已经标准名的本体 —— `TryApply` 见到"源 == 目标"会判
     `AlreadyStandard` 把整份计划拒掉（这一步是写的时候踩到才想起来的）。
2. `ExtractionCoordinator.NormalizeDisguisedVolumeNamesAsync` 的入口判据加一档：
   `IsVolumePartFileName(自己) || task.IsVolumeGroup` —— **账上已经归过组就该问一句**。
   （计划仍然只在"名字能定序"时成立；问不出结果的照旧退回内容那条路，行为不倒退。）

## §42 跨盘 zip 的「按归档自己的索引定盘」（2026-10-01 真机 `FFF\111`，用户造了样本）

### 42.1 用户给的东西与要求

- 原话：「**`H:\BaiduNetdiskDownload\测试\FFF\111` 可以用真实文件操作，我已经备份了**」
  「**最后一片是 .zip，你这个不是可以识别到末卷吗，我也进行了伪装**」
  「**你之前的修改了吗，如果没修改就测完一起修，之前的两个记着要修的和我设计的专属算法，
  这种统一的算法不要丢，这个可以弄一个保底的**」。
- 样本：两个目录 `FFF\111` 与 `FFF\222`，**每个目录 7 份文件**，全部叫 `222` + 一段被塞了中文的名字
  （`222` / `222.删除C` / `222.z0删除A` / `222.z删除B` / `222.z删除E` / `222.zDDD` / `222.zi删除p`），
  6 份 100 MiB + 末片 46.76 MB。**名字里一个卷号都没有** —— 这正是他上一轮答应造的"我设计的专属算法"的输入。

### 42.2 只读侦察（先把事实钉死，再写代码）

- 逐份读**真实字节**：只有 `222.z0删除A` 开头是 `50 4b 07 08 50 4b 03 04`（跨盘标记 + 本地头 ⇒ 第 1 盘）；
  末片 `222.zi删除p` 的文件末尾正好是 EOCD（离末尾 22 字节），**自述盘号 6 / 中央目录起盘 6** ⇒ 一共 **7 片**。
- 解析末片的**中央目录**（6 条记录：1 个目录条目 + 5 个 `222/*.mp4`，全部 AES-256 + deflate）：
  每条都写着"本地头在**第几盘**、离那一盘开头多少字节"——
  `111.mp4` 盘 0@38、`222.mp4` 盘 0@87506922、`333.mp4` 盘 **2**@65622982、`444.mp4` 盘 **4**@103335692、
  `555.mp4` 盘 **5**@98771138。**这就是每一片的身份证**。
- 用这些身份证逐份验：`222.z0删除A`=盘 0（命中 3 条锚点）、`222.删除C`=盘 2、`222.z删除E`=盘 4、
  `222`=盘 5、`222.zi删除p`=盘 6；剩下 `222.z删除B` 与 `222.zDDD` **一条锚点都不命中** ——
  它们的内容里"一个文件都没开始"（整段夹在某个 mp4 的数据中间），**在字节上完全对称**。
- 扫描期归组实测：**0 组**（`VolumeGroupDetector.Group` 对这 7 份一份都归不进组；
  `TryGetVolumeIndex` 只认得出末片 `222.zi删除p` → 卷序 1 / 首卷名 `222.zip`，可它旁边没有标准名兄弟 ⇒ 不成组）。

### 42.3 三条结论（决定了怎么写）

1. **能定**：末片的中央目录给了"每一片该在哪个偏移上有一个本地头" ⇒ 名字全废也能把片认出来，
   **不需要引擎、不需要密码**（中央目录本身不加密）。
2. **定不了就说定不了**：某一片里一个条目都没开始时，它和另一片同样空白的片**字节上对称**，
   ⛔ 不许按名字 / 时间戳猜 —— 只剩下"排列 + 让引擎真解一遍"这一条路（用户 2026-10-01 的"专属算法"）。
3. **入口也得改**：老入口（名字带卷标记 / 账上归过组）在这组上**两条都不成立**（实测 0 组）
   ⇒ 再准的算法也轮不到跑。多一条与名字无关的事实：**目录里真有一片自述是末片**。

### 42.4 落地（⛔ 统一算法一个字没动，它是保底）

- 新增 `Detection/SpannedZipIndex.cs`：读末片 EOCD + 中央目录 → 每条记录变一条**锚点**
  （盘号 + 盘内偏移 + 文件名的**原始字节**，⛔ 比字节不比解码后的字符串）；
  `Pin(candidates)` 把候选按锚点与"满片尺寸"分配到各盘，三种状态**分得很清**：
  钉住（锚点唯一命中）/ 定不下来（那一盘没有锚点）/ 缺（有锚点却没人对得上，点名第几片）。
- `Extraction/VolumeProbeVerifier.VerifySpannedZipOrderAsync`：**试拼定序** ——
  把整组按候选顺序硬链接成标准卷名（`volprobe.z01…volprobe.zip`），让引擎**测试**（`t`）一遍。
  ⛔ 列目录验不出顺序（中央目录在末片里、不看中间片的数据，实测）；顺序错必然 CRC 错。
  密码只在内存里流转，而且**一旦某次失败不是密码错**就记住那个密码给下一个排列用
  （省掉把密码本重跑一遍的代价）。
- `Extraction/VolumeNameRepair.PlanSpannedZipByIndexAsync`：排在三条统一算法**之前**；
  不适用（不是跨盘 zip / 片数 < 3 / 候选对不上）返回 `null` 原样往下走；判不出来只出结论、**一个字节不动**。
  排列上限 **3 片（6 种）** —— 再多就不是"试一下"而是暴力搜索（一组 675 MB 要解几十遍）。
- 「末片不在了」诊断：清一色满片 + 恰好一片开头是跨盘标记 ⇒ 结论是"缺的是**末片**（`.zip`）"，
  由 `VolumeNameRepairPlan.SpannedTailMissing` 带出去，`ExtractionCoordinator` 对这一档写一行 INFO
  （用户要的"在 7-Zip 报缺卷之前就说清缺的是第几片"）。
- 入口放宽：`ExtractionCoordinator.NormalizeDisguisedVolumeNamesAsync` 的判据加第三档
  `VolumeNameRepair.HasSpannedZipTailNearby(current)`。

### 42.5 ⚠ 实测把「末卷更小」这条直觉否掉了一半

用户 2026-10-01 提的规则是"**末卷通常更小**"。真造样本逐个数字节的结果：

| 内容 | 切分 | 盘上 |
|---|---|---|
| 3 × 100 KB | `-v64k` | `.z01=65536` / `.z02=65536` / **`.zip=176532`**（末片比满片大一倍多） |
| 20 × 100 KB | `-v64k` | `.z01…z02=65536` / `.zip` 同样是"剩下的全塞进去" |
| 20 × 40 KB | `-v64k` | `.z01…z12=65536` / `.zip=34K`（这一档末片确实更小） |
| 5 × 1.5 MiB | `-v1m` | 8 片，除末片外每片都是 1 MiB（与真机 `FFF` 同形状） |

⇒ **「末片一定更小」不成立**（WinRAR 在条目比切分大小还大时会把剩下的全塞进末片）。
所以代码里只用了**真成立的那一半**：**除末片外每一片彼此等大**（喂候选池的"满片尺寸 = 众数"），
⛔ 没有拿"末片更小"当闸门 —— 拿一条不成立的规律当门，只会把真组挡在外面。

### §44.2 跨盘 zip 一超过 4 GiB 就必然带 ZIP64 收尾，而两道闸门都不认它

**只读实测**（用户盘上那个残件 `…\111\一只顶美.z删除ip`，1,621,744,784 字节）：尾部 22 字节是 EOCD（盘号 5、本盘 250 个条目、中央目录 66,746 字节 @1,621,677,940），紧挨着它前面是 ZIP64 定位器（`PK\x06\x07`，自述"ZIP64 EOCD 在第 5 盘、共 6 片"）与 ZIP64 EOCD 记录（56 字节）⇒ 中央目录结束在 1,621,744,686，**与 EOCD 之间正好隔着 76 字节 ZIP64 收尾**。

同一份文件、同一时刻，四条判据各说各话：

| 判据 | 修前 | 修后（同一份文件只读复核） |
|---|---|---|
| `ArchiveDetectService.DetectAsync`（识别） | `Unknown`：「文件尾部没有自洽的 ZIP 收尾（EOCD 与中央目录位置对不上）」 | `ZIP_SPANNED`：「这是一片跨盘 ZIP（本盘号 5、中央目录在第 5 片、共 250 个条目）」 |
| `EmbeddedArchiveDetector.Detect` | `Found=false` | `Found=true`、`IsVolumePart=true` |
| `SpannedZipIndex.TryRead`（专属算法） | `null`（读不出索引） | **250 个锚点**、`DiskCount=6` |
| `VolumeNumberFromContent.Read` | Zip / 是成员 / 号 6 | 同（它只看 EOCD 的盘号字段，本来就读得出） |

**为什么这是"类"而不是个例**：跨盘 zip 只要总量超过 4 GiB，偏移就放不进 EOCD 的 32 位字段 ⇒ 生产者**必然**写 ZIP64 收尾 ⇒ 这两道闸门在**所有真机大包**上都判不出。合成小样本（FFF 那 7×100 MB）永远撞不到它 —— 这正是"必须真样本"那条验收规则又一次救回来的东西。

⚠ **仍未做（如实记）**：更一般的那道保险 —— 「其余物里放着某个分卷组的一片、而同组另一片还在成品目录里 ⇒ **绝不允许整份删除其余物**」还没加；AGENTS 里那条红线目前只覆盖"改名 / 搬运计划"那一档，没覆盖"链尾整份删除其余物"这一档。

## §45 2026-10-02 真机「14 个任务里 6 个白没做」+ 两处体验缺陷

用户原话：「**我刚刚又试了一次这次有非常大的错误**」（`H:\BaiduNetdiskDownload\111\ArchiveFixer-本次操作_20261002_095919.txt`，
14 个任务 / 09:18:28 → 09:59:07 / 成功 9 失败 6），随后补两条：「**我知道最后面会有一个内容物的检验，而且本次就是我看到解压完成到真正的解释有个 8 分钟的差距**」、
「**我导入的文件比较多，他一开始就卡死了，未响应有一分多钟**」。

### §45.1 主要缺陷：启动前空间不够被当成"失败"，拒了再也没人回头看

**现场（逐条从日志抄的）**：并发档 8、盘上 35.86 GiB 可用。前 8 个任务一开跑，
账本里"已经在跑的任务预留"就顶到 **35.11 GiB**（那 8 个各自的全额需求之和本来就接近整块盘）。
于是第 9 个包 `（3399）2027考研，数学基础，利用基本极限求极限.mp4` —— 它自己**只要新写 851.45 MiB** ——
被判「**还差 9.77 MiB**」当场记成失败。同样被拒的还有 5 个（差 2.62 / 13.11 / 13.97 / 15.49 / 18.24 GiB）。

那 8 个要跑 30 多分钟，其间陆续跑完、把预留一笔笔放出来（最大的 `P.7z.001` 一个人就放开 **15.71 GiB**，
它在 09:51:58 结束），可被拒的那 6 个**再也没人回头看**：批末「成功 8 / 失败 6」、
诊断「磁盘空间不足：6 个」、6 个视频一个都没解（源包一个字节没动，数据是安全的）。

**判据上的错**：**"此刻空间不够"是一个会变的瞬时事实，不是一个终态。** 启动循环把
`!gate.Allowed` 直接当成"这个任务做不成"，而这只是"**现在**排不上"。

**改法**：拒下的任务进一张"等空间"名单（**不记失败、不改状态**，只写一行 INFO 说清它在等什么），
**每跑完一个任务就重试一遍**（那一刻预留刚被释放、空间是真变多了）；没人跑了 ⇒ 空间不会再变多 ⇒
剩下的才走 `MarkSpaceBlocked` 如实报「空间不足」。放行判据一个字没放宽（仍然只走 `TryReserve`）。

**踩到的两个坑（都留了注释）**：
1. **补跑环必须与"等所有任务结束"写在同一个环里**：第一版把它放在那个 `while` **之后** ——
   轮到它时 `runningTasks` 已经空了，那个 `while` 一次都不进，被拒的任务照样在批末被记成「空间不足」
   （红检现场：用例里第二个包一直是"未处理"）。
2. **每跑完一个要当场重探一次可用空间**：账本平时由空间侦察每 5 秒刷一针，而"任务收尾释放预留"是立刻发生的；
   不重探就会拿着 5 秒前的旧数字白等一轮（真机形态：大包明明跑完了、空间已经回来，小包还在等）。

**用例**：`SpaceTightModeTests.启动前空间不够_先排队不记失败_等腾出空间后自动补跑` —— 假盘先只剩 210 MiB
（够第一个 200 MiB 的包、两个一起不够），200 ms 后"腾空"；断言 ①出现「先排队等空间」②出现「腾出空间了，现在补跑它」
③两个都成功 ④**一个都不许**落到「空间不足，未解压」。
**红检**：把那条改回 `MarkSpaceBlocked(...) + continue` ⇒ 用例当场变红。

### §45.2 进度条在第 0 层到 100% 之后就不动了（用户说的"8 分钟差距"）

**现场**：`P.7z.001` 第 0 层 **09:47:18 到 100%**，09:47:23 才开始解内层包 `P.ra`，
到 **09:51:57** 整条链才结束 —— 中间 **4 分 34 秒**界面上停在 100%、日志里一条进度都没有
（日志里那段也确实空着，只有"空间变化"每 5 秒一针）。

**根因**：进度条记的是"引擎最后一次报的百分比"，第 0 层结束时它是 100%；第 1 层从头开始时
**没有任何一帧把基准拉回来**，于是那一层跑多久、界面就停在 100% 多久。

**改法**：`RecursiveExtractor.ExtractLayerAsync` 每一层开头先合成一帧
`Percent = 0、当前条目 = "第 N 层：<内层包名>"` ⇒ 进度条从这一层重新起算，日志里也多一行
「进度 0%（当前：第 N 层 …）」。⛔ 只补这一帧，引擎报的进度一个数都不改。

### §45.3 导入文件多时界面「未响应一分多钟」

**根因**：识别一次要做三件 CPU 密集的事 —— 解析文件头、**扫尾部**（认不出格式时要顺序扫到 512 MiB）、
加密判读；它们过去全都跑在**调用方线程**上，而调用方就是 UI 线程（只有文件 I/O 是 `await` 出去的）。
于是每读一个文件 UI 就卡一段，几百个文件排队走完就是"未响应"。
（用户那次 22 个任务的导入只用了 1 秒 —— 这条按"几百个文件"那一档才显形。）

**改法**：`ScanCoordinator.ScanTasksAsync` 里把整段识别放进 `Task.Run`（`await` 一返回自动回到 UI 线程，
