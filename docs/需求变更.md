## 2026-09-21 ｜ M1 冒烟测试发现并修复两个改名 bug

- **提出人**：agent 发现（M1 验收测试 `ArchiveFixer.Tests/BaselineSmokeTests.cs` 跑出来的，不是猜的）
- **类型**：修正行为（缺陷修复）
- **归属里程碑**：M1
- **内容**：

  1. **分卷文件会被"智能修正后缀"改名，直接切断分卷链（严重）**
     `volume.7z.001` 被识别为 7Z 后，多重后缀修正把文件名改成 `volume.7z` ——
     而 7z 只认 `.001` 这一套命名，改完之后整组分卷再也解不开。
     修复：新增 `ExtensionHelper.IsVolumePartExtension()` 与 `FileNameHelper.IsVolumePartFileName()`
     （覆盖 `.001`–`.999`、`.z01`–`.z99`、`.r00`–`.r99`、`.part1`/`.part01`），
     在 `RenameService.BuildFixByDetectedFormatFileName()` 开头拦截：分卷文件一律不改名。
     同时 `FileNameHelper.IsMultiExtensionSuspicious()` 不再把分卷报成"多重后缀疑似伪装"
     （改判为"后缀不匹配"；设计.md §七 要求的独立"分卷后缀"状态留到 M2 与分卷组识别一起做）。

  2. **路径写法差异会把"无需改名"变成"改成 `名字(1).ext`"**
     `RenameService.BuildPreview()` 用**原始字符串**比较新旧路径。只要路径写法有差异
     （正斜杠、冗余分隔符、大小写），`File.Exists(newPath)` 就会把文件自己当成"已存在的目标"，
     于是 `data.tar.gz` 这种本来不用改的文件被预览成 `data.tar(1).gz`。
     修复：改用已有的 `SafePathHelper.PathEquals()`（内部走 `Path.GetFullPath` 规范化）比较 ——
     涉及 `RenameService.BuildPreview()`、`RenamePreviewItem.CanRename`、`RenamePreviewItem.SyncNewPathFromNewFileName()` 三处。

- **影响**：`Helpers/ExtensionHelper.cs`、`Helpers/FileNameHelper.cs`、`Services/RenameService.cs`、
  `Models/RenamePreviewItem.cs`；新增回归测试 3 个（分卷不得改名、复合后缀不得被破坏、识别与后缀状态）。
  不变量 1（不破坏源文件）与不变量 3（改名规则）由此得到实际保障。
- **验收判据**：`dotnet test` → 64 通过 / 0 失败（原 43 个单元测试 + 21 个基线冒烟测试）。

## 2026-09-21 ｜ M4「递归解压」+ M5「安全与恢复」完成

- **提出人**：agent（按 AGENTS.md §10 执行）
- **类型**：里程碑完成
- **归属里程碑**：M4、M5
- **交付内容**：

  | 方向 | 落地 |
  |---|---|
  | 递归（§6 第 8 条、设计.md §十–§十四） | `Detection/IArchiveProber`；`Extraction/ExtractionWorkspace`（分层工作区 `layer-NNN/output` + report.json + 发布）；`Extraction/RecursiveExtractor`（三种模式、单链启发式、多分支询问、previousDecision 续跑、硬上限、停因细分） |
  | 安全（§6 第 4 条、设计.md §二十五） | `Security/ArchivePathGuard`（条目风险分类 + 落点校验）；`Security/ResourceBudget`（解压前预算 + 运行时跟踪）；`Storage/SpaceChecker`（可用空间、FAT32 4GiB 提前拦截） |
  | 接入 | 解压前：列目录（最多试 3 个密码候选）→ 路径预检 → 资源预算；解压后：落点校验 → 结果校验 → 归集 → 可选清理；递归模式走 `RecursiveExtractor`，完成后同样走校验/归集/清理 |
  | 界面 | 设置界面新增：嵌套压缩包模式（只解当前层／单链自动展开／展开所有分支）、最大嵌套层数、结果归集开关与目标目录、清理源包开关（带不可逆警告）、旁路说明文件开关、7z.exe 自定义路径；主界面新增「一键处理」与「导出失败清单」 |
  | 中断与恢复 | 工作区位于 `%AppData%\ArchiveFixer\work`；部分完成/取消时不发布、不清理，产物留在工作区；启动时报告未完成的工作区数量（只报告，**不自动删** —— 不变量 13） |

- **测试**：**343 通过 / 0 失败 / 0 跳过**；构建 0 警告 0 错误。
- **过程中发现并修复的缺陷**（都是跑测试跑出来的）：
  1. 7z 格式的目录条目**没有 `Folder` 键**（只有 `Attributes = D`），我的解析器把它当文件计数 ——
     而这个数正是「清理源包」的前置校验值，数错会导致该删的不删 / 误判通过；
  2. 递归续跑用**上一次工作区的绝对路径**过滤用户点名的分支，而续跑会新建工作区（前缀必变）→ 用户的选择被静默丢掉；
  3. 内层归档数量上限的检查排在"要不要问用户"之后 → `TooManyInnerArchives` 永远不可达；
  4. 入队层号用"已解层数 + 队列长度"计算 → 宽树（多分支）会被假报 `MaxDepthReached`；
  5. `Publish` 只发布最后一层 → 多分支展开后只有一支的产物落盘；
  6. 旁路说明文件的标签式正则在分隔符可选时会把整行密码 `pass1` 切成 `1`。
- **两处口径收敛**（按设计意图，不是为过测试）：`MaxDepth` 统一按**层号**（0 起算）判定；`Publish` 由"最后一层"改为"**叶子层集合**"（单链行为不变）。
- **验收判据**：`dotnet build` 0 警告 0 错误；`dotnet test` 343 通过；`main` 推送完成。
