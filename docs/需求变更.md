## 2026-09-21 ｜ M1 冒烟测试发现并修复两个改名 bug

- **提出人**：agent 发现（M1 验收测试 `ArchiveFixer.Tests/BaselineSmokeTests.cs` 跑出来的，不是猜的）
- **类型**：修正行为（缺陷修复）
- **归属里程碑**：M1
- **内容**：

  1. **分卷文件会被"智能修正后缀"改名，直接切断分卷链（严重）**
     `volume.7z.001` 被识别为 7Z 后，多重后缀修正把文件名改成 `volume.7z` ——
     而 7z 只认 `.001` 这一套命名，改完之后整组分卷再也解不开。
     修复：新增 `ExtensionHelper.IsVolumePartExtension()` 与 `FileNameHelper.IsVolumePartFileName()`
     （覆盖 `.001`–`.999`、`.z01`–`.z99`、`.r00`–`.r99`、`.part1`/`.part01`），
     在 `RenameService.BuildFixByDetectedFormatFileName()` 开头拦截：分卷文件一律不改名。
     同时 `FileNameHelper.IsMultiExtensionSuspicious()` 不再把分卷报成"多重后缀疑似伪装"
     （改判为"后缀不匹配"；设计.md §七 要求的独立"分卷后缀"状态留到 M2 与分卷组识别一起做）。

  2. **路径写法差异会把"无需改名"变成"改成 `名字(1).ext`"**
     `RenameService.BuildPreview()` 用**原始字符串**比较新旧路径。只要路径写法有差异
     （正斜杠、冗余分隔符、大小写），`File.Exists(newPath)` 就会把文件自己当成"已存在的目标"，
     于是 `data.tar.gz` 这种本来不用改的文件被预览成 `data.tar(1).gz`。
     修复：改用已有的 `SafePathHelper.PathEquals()`（内部走 `Path.GetFullPath` 规范化）比较 ——
     涉及 `RenameService.BuildPreview()`、`RenamePreviewItem.CanRename`、`RenamePreviewItem.SyncNewPathFromNewFileName()` 三处。

- **影响**：`Helpers/ExtensionHelper.cs`、`Helpers/FileNameHelper.cs`、`Services/RenameService.cs`、
  `Models/RenamePreviewItem.cs`；新增回归测试 3 个（分卷不得改名、复合后缀不得被破坏、识别与后缀状态）。
  不变量 1（不破坏源文件）与不变量 3（改名规则）由此得到实际保障。
- **验收判据**：`dotnet test` → 64 通过 / 0 失败（原 43 个单元测试 + 21 个基线冒烟测试）。

  | 中断与恢复 | 工作区位于 `%AppData%\ArchiveFixer\work`；部分完成/取消时不发布、不清理，产物留在工作区；启动时报告未完成的工作区数量（只报告，**不自动删** —— 不变量 13） |

- **测试**：**343 通过 / 0 失败 / 0 跳过**；构建 0 警告 0 错误。
- **过程中发现并修复的缺陷**（都是跑测试跑出来的）：
  1. 7z 格式的目录条目**没有 `Folder` 键**（只有 `Attributes = D`），我的解析器把它当文件计数 ——
     而这个数正是「清理源包」的前置校验值，数错会导致该删的不删 / 误判通过；
  2. 递归续跑用**上一次工作区的绝对路径**过滤用户点名的分支，而续跑会新建工作区（前缀必变）→ 用户的选择被静默丢掉；
  3. 内层归档数量上限的检查排在"要不要问用户"之后 → `TooManyInnerArchives` 永远不可达；
  4. 入队层号用"已解层数 + 队列长度"计算 → 宽树（多分支）会被假报 `MaxDepthReached`；
  5. `Publish` 只发布最后一层 → 多分支展开后只有一支的产物落盘；
  6. 旁路说明文件的标签式正则在分隔符可选时会把整行密码 `pass1` 切成 `1`。
- **两处口径收敛**（按设计意图，不是为过测试）：`MaxDepth` 统一按**层号**（0 起算）判定；`Publish` 由"最后一层"改为"**叶子层集合**"（单链行为不变）。
- **验收判据**：`dotnet build` 0 警告 0 错误；`dotnet test` 343 通过；`main` 推送完成。

     - 旧行为：产物越出目标根目录时**只写一行 ERROR 日志**，任务状态照样"解压成功"，
       而且照样归集产物、照样清理源包 —— 越界的产物被搬进结果目录、源包被删掉，程序却报一切正常。

  7. **中间工作区成功后要清理**（缺陷修复，P1；端到端验收实测）
     - 现场：双面文件（内嵌归档）要先按偏移把尾部那段真正的 ZIP 抠进 `data\work\<任务名>\` 再解压，
       一次**成功**的一键处理就在那里留下近 **1 GB** 中间件（实测 733 MB + 167 MB 两个包）；
       这些是从源文件可再生的派生数据，跑几批就把盘吃掉，而且启动时还会被算进"未完成的工作区"造成假警报。
     - 现在：**解压成功 + 输出校验通过 + 未取消**之后，清理本任务自己的那个工作区目录，删前删后各写一条日志
       （路径 + 理由）。取消 / 部分完成 / 校验失败 / 越界检出**一律保留** —— 与 §9.5 的清理语义对齐。

       越界什么都不删）；目录里出现子目录就放弃（抠出来的中间件只会是文件；任务名恰好叫 `recursive` 时会撞上
       递归工作区的容器目录）；删失败（占用 / 权限）只写日志，绝不让已经成功的任务变成失败。

     `data\work\recursive\<任务号>\` 在成功后**永不清理**——一次成功就可能留下几百 MB；

  2. **修法**：由 `RecursiveExtractor` **自己持有本次运行的工作区实例**
     （`CurrentWorkspace`，就是本次 `ExtractAsync` 开头建出来的那一个），

     取消可能在最后一层解完之后才到（队列已空、结论仍是 Completed），所以判据里**再看一眼取消令牌**。

     `data\work\recursive` —— 那种实现会在并发解压时端掉另一个任务正在写的工作区。
     容器内校验两道：`ArchivePathGuard.IsInsideRoot(工作区根, 任务目录)` 先查一遍，

     生产环境里工作区根就是 `<程序目录>\data\work\recursive`，所以"在工作区根之下"即"在 data\work 之下"。

### 设计上刻意做的取舍（都有测试钉住）

1. **粗估 + 精估两级**：排序用"只 stat 文件"的粗估（50–200 个包不能为排序去逐个列目录），
   硬门用解压前那一遍 list 算出的精估（**绝不为它多跑一次 7z**：加密包每多列一次目录就多一次失败机会）。
2. **取不到可用空间时不拦**（只写 WARN）：把"探测失败"说成"空间不足"是指错方向
   （与 `ResourceBudget.CheckFreeSpace` 同一口径）；但**也不算通过** —— 自测里这一条判"不通过"。
3. **"单独跑也放不下" ≠ "这一批挤不下"**：前者才是"因为空间不足被跳过"，
   后者只是排队。把它们混起来会把"等一会儿就能跑"的任务报成跳过（`BlockedAtPlanTime` 只收前者）。
4. **危险模式删的路径只用"定稿那一刻记下来的那一条"**（`ArchiveTask.RestDirectoryPath`），
   **不现场重算**：源包搬进其余物之后 `CurrentPath` 已经变了，现场解析在共享输出根模式下会退化成
   "整个 `其余物\`"，一删就是同目录里所有包的中间件。加两道校验兜底（必须在自己输出根之内 + 路径形状必须是其余物）。
5. **自测真的走完整管线**，不另写精简流程：另写一条只能证明"精简版没问题"。
6. **两次红色确认**：第一次同意的是"拿这几个文件试"，第二次同意的是"以后整批都这么干"。
7. **`KeepInPlace` 档下自测直接拒绝**：其余物里没有源包，危险模式省不出最主要的那一份空间 ——
   让它通过等于让用户白担风险。
8. **凭证保留**（关闭模式不清凭证）：清掉只会逼用户再删一批源包（自测本身也是不可逆的）。

### 顺手修掉的一个真实缺陷（由测试暴露）

`task.CurrentPath`（决策 D-12 的要求）—— 于是**搬之前**与**搬之后**是两格，
自测读证据时拿到的是全新的一份（`RestPurged=false`、可用空间 -1），
表现为"明明删掉了却报没删"。改成用**任务对象本身**做键（引用相等）后修复。

> 这两个都不是新写的代码引入的，而是**并发 ≥2 一直都在、只是默认值 1 让它很少被走到**。
> 默认值提到 4 之后它们变成常态路径，所以必须在本轮修掉（第一个是本轮测试自己抓到的）。

1. **同名包并发时抢同一个新目录**（`ExtractionCoordinator.ClaimOutputDirectory`）。

## 2026-09-22 · 自测凭证只覆盖它跑过的那一档并发（对危险模式的收紧）

### 为什么

协议原话是"**并行解压是五个，你就要拿十个文件做这样的测试**" —— 自测的结论天然只对它跑过的那一档成立。
原实现只用"凭证非空"当闸门，于是存在一条**绕过协议**的路：
在并发 1 下自测通过（2 个样本），之后把「最大并发解压数」调到 8 再开危险模式 ——
等于**没测过就用了**，而这条路上源包的删除是不可逆的。

### 改了什么（三处，同一套判定）

1. `DangerModeSelfTestStamp.Covers(stamp, parallelCount)`：凭证里记的并发数 ≥ 当前档位
   **且**样本数 ≥ 2 × 当前档位才算盖得住。手写/写坏的凭证、样本数被手改小的凭证一律盖不住。
   **单调方向是刻意的**：调**小**并发仍然算盖得住（少并行只会更安全，不该逼用户再删一批样本源包）。
2. `ExtractionCoordinator.PrepareDangerModeForBatch(maxParallel)`：批首把"本批到底生不生效"定一次。
   盖不住 → **本批一个字节都不删**（其余物照常进回收站），并在批首写一条 WARN 说明"没生效 / 为什么 / 怎么办"。
   ⚠ 刻意**不做**成"偷偷把开关关掉"：静默降级会让人以为边解边删在起作用，
   于是放心把盘塞满 —— 那才是真正的危险。所以是"本批不生效 + 界面上说在明处"。
   `IsDangerModeActive` 也随之从"每次读设置现算"改成"批首定一次"，默认 false：
   没经过批首的路径（单独解压一个包）永远不删东西。
3. `MainViewModel.DangerModeNotCovered / DangerModeCoverageText`：常驻红横幅里多一行加粗红字
   （"已开启但凭证盖不住当前档，本批不生效"）。「全速」开着时按**勾选任务数**判（协调器就是这么算的），

### 两个关键决策（都是"不许撒谎"那一类）

1. **分卷默认 512 MiB**：用户那两句话唯一的自洽解 —— 1 GB 内容切出 `.001`+`.002`、

## 2026-09-23 · 修掉一个顺序相关的偶发失败 + GBK 密码本真的能读了

### 现象与根因（真查到底了，不是"重跑一次就好了"）

全量测试里偶发一条红：`PasswordBookTests.ParseFile_非UTF8内容触发编码回退且不静默丢行`，
报 `Assert.Contains() Failure: Filter not matched in collection`。**两次出现都在加了打包功能之后**。

根因有两条，都是真问题：

1. **进程级的注册被散在了一个 runner 里**：GB18030 这类代码页编码在 .NET Core 上必须先
   `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` 才能用，而这句话原来写在
   `Packing/PackProcessRunner.ResolveOutputEncoding` 里（按控制台代码页解码 rar 输出时顺手注册）。
   注册是**进程级、一次性、全局**的 → "哪个测试先跑"决定了 `Encoding.GetEncoding("GB18030")`
   在别处成功还是抛异常。那条测试正是先 try 一次、失败就 `return`（等于没测），成功才走到断言。
2. **那条断言写的是一句并不存在的文案**：它要求回退警告里含"编码"两个字，而实现里的原文是
   「密码本文件不是有效的 UTF-8，已按 GB18030（GBK 超集）重新读取。」—— **没有"编码"**。
   于是"注册成功了"反而让它必然红：这既是偶发失败的机制，也是一条**假的判据**。

### 改了什么

- 新增 `Helpers/CodePageEncodingBootstrap.EnsureRegistered()`：**幂等**的一次性初始化（重复调无害、失败不抛），
  并真取一次 `GB18030` 才算数。三处调用：`App.OnStartup`（进程第一步）、`PasswordBookParser.ParseFile`
  （回退之前，所以单测/未来的 CLI 直接调也对）、`PackProcessRunner`（不再就地注册）。
- `PasswordBookParser` 的文档注释同步改掉那句已经过时的"本项目没有引入 CodePages 包，不一定注册得上"。
- 两条测试改成**确定性**的：那条偶发红的用例自己先显式注册（拿不到就明说跳过），
  并按警告要表达的事实断言（说了"不是 UTF-8"或说了回退到什么编码）；新增
  `代码页编码注册是幂等的_而且解析器自己会确保它`（幂等 + GBK 密码本真的按映射式读出条目，
  而不是靠一条警告糊过去）。

### 顺带说清一件用户能感知的事

`docs/使用说明.md` 早就写着「UTF-8 最好，**GBK 也认**」—— 在这条修好之前，那句话只在
"启动路径恰好注册过代码页"时成立，否则回退会静默降级成系统默认编码（.NET Core 上就是 UTF-8），
中文 Windows 用记事本存的 **GBK 密码本会被读成乱码**，用户只会看到"密码全都不对"。
现在解析器自己确保注册，这句话是真的了。

### 另一件顺手补上的"设置谎言"

`IncludeHiddenFiles` / `IncludeSystemFiles` / `MaxFileSizeLimit` 三项**一直有实现**
（`FileScanService` 真的按它们过滤），但设置窗口里没有入口 ——"配置里能改、界面里找不到"对用户就是一句谎。

## 2026-09-23 · 不变量 11 落地：源文件变化后不得继续使用旧识别结果

### 不变量（AGENTS.md §6 第 11 条 / 设计.md 不变量 11）

任务开始时记录源文件**大小 / 修改时间**快照，处理中变化即停下并报「源文件已变化」。
这是 `AGENTS.md` §6 里**最后一条没有落地**的红线（`README.md` 的「已知限制」原来就写着
"无源文件变化检测 —— 尚未实现"）。

**它防的是什么**：识别（扫描）那一刻得出的格式 / 后缀 / 分卷结论，是**针对当时那个文件**的。
文件在扫描之后被换掉 / 改掉 / 删掉时，继续拿那份结论去解压，结局通常是
「密码错误 / 文件损坏」这种**指错方向**的结论 —— 用户会去反复核对密码本，
而真正该做的是重新识别一遍。更糟的是把用户刚换进去的那一份当成原来那份处理。

### 落点（四条，都是"唯一收口"）

1. **快照**：新增 `ArchiveFixer/Storage/SourceFileSnapshot.cs`（**不引用 WPF**）。
   在 `Models/` 与 `Storage/` 之间选后者的理由就是分层铁律：Domain 只放纯模型，
   **碰磁盘的事（`FileInfo` stat）归 Storage**。一组记录 = `ArchiveTask.CurrentPath` + `VolumePaths`
   整组，每条记 `Length` + `LastWriteTimeUtc` + **"记的时候文件是否存在"**
   （最后这一项是必须的：没有它，一个**一开始就不存在**的路径会被每一次比对都报成"文件不见了"，
   任务永远开工不了 —— 这条是写完测试才发现的真缺陷）。
2. **什么时候拍**：`ScanCoordinator` 里识别一完成就拍（`ScanTasksAsync` 与「重新扫描此文件」两条路径都拍）
   —— 快照要保护的正是识别结果，基准必须与它同一时刻产生，且**早于任何解压动作**。
   取不到快照（老任务 / 测试直接 `new` 出来的任务）时**在开工前补拍一次**（`EnsureSourceSnapshot`），
   **不因此拦下任务**：把"我们没记录"说成"你的文件变了"会把一个本来能跑的任务拦死，而用户完全无从理解。
3. **什么时候比**：`ExtractionCoordinator.ExtractSingleTaskAsync` 里两道 ——
   ① 方法**最前面**（挡住"扫描之后就被改过"的包，同时也挡住引擎在"分卷缺失补卷""格式未知试列"里被碰到）；
   ② 真正开工**之前**（挡住中间那段窗口：冲突询问可以停在屏幕上等用户点，
   而这期间用户完全可能自己把那个包换掉）。递归模式下**每一层**开工前还会再问一次
   （`RecursiveExtractor` 新增注入式检查口，**只对第 0 层**——第 1 层起解的是我们自己从内层抠出来的中间件）。
4. **停下意味着什么**：引擎**一次都没被调用**、源包一个字节都不动、`其余物` 不生成、
   不发布任何产物、不留中间品（**不变量 1 的红线照旧**）。状态落「源文件已变化」，
   `ErrorMessage` 点名"哪一个文件、哪一项变了"并给出一条出路（右键「重新扫描此文件」——
   与「分卷缺失」给的是同一条出路）：`大小 1.2 GiB → 1.3 GiB` / `修改时间 … → …` / `文件不见了`。
   分卷组则点名**是哪一个卷**（`分卷 · 文件不见了` / `666.7z.002（分卷 · 大小 … → …）`）。

### 两个刻意的设计取舍

1. **按"位"比对，不按"路径"**：比对是"快照第 N 项 vs 现在第 N 项"。理由是**改名**（智能修正后缀）
   与**源包搬进 `其余物`** 都会让路径变、而文件本身没变 —— 按路径比会把这两件**正常操作**
   报成"源文件被换了"，用户每次改完后缀都得重新扫描一遍。路径不是不变量 11 要保护的东西，
   大小与修改时间才是。
2. **补齐分卷 / 重新扫描会重拍基准**：分卷缺失的补救出口（「我手动指定缺失卷所在目录」）
   会往 `VolumePaths` 里加新卷、重扫会重新识别 —— 这两件事都是"改变源文件组的正当操作"。
   不重拍的话新卷会被算成"新出现的文件"，用户按提示补齐反而被拦，而且补多少次都一样
   （**死循环**）。所以这两条出口都重拍一次基准。

### 已知边界 / 遗留

1. **只比大小与修改时间，不比对内容哈希**（刻意的：全量读一遍几百 GB 的分卷组是不可接受的代价）。
   两条边界如实写进 `README.md` 与 `docs/使用说明.md` §15：① 被别的工具"摸"过时间戳
   （甚至只是被某个程序打开过一次）也会触发；② 被换成**大小和修改时间都恰好一样**的另一份检测不出来。
2. **比对点是"每次任务开工前"**，不是"解压全程持续监控"：解压**进行中**源文件被改，那一次已经在跑
   （与"压缩炸弹拦不住已写出的那一次"同一性质）。下一个任务 / 下一次运行照样会拦住。
3. **内层包（第 1 层起）不比对**：它们是我们自己从内层抠出来的中间件，本来就不在源文件快照里。
   真正被保护的是**用户给的源包**。
4. **快照不落盘**：它只活在进程内存里（跟着 `ArchiveTask`）。程序重启后列表重建、重新扫描，
   基准自然重拍 —— 这个功能保护的是"同一次运行里识别与解压之间"的那段窗口。
