# 并发调度（全自动）

## 对外行为

- 界面没有并发设置（2026-11-02 已把「并发与空间」卡片整卡删除），⛔ 没有手动并发档/全速/建议按钮。
- 用户不配置；程序按本机实测决定同时跑几个包。
- 单包解压本身基本单线程（7-Zip 只有多 chunk 才多线程，RAR 单流），所以并发只跨包。

## 算法（延迟梯度 + AIMD）

对每个完成的任务记 `归一化延迟 = 耗时 / 源包GB`；每个窗口（≥5 秒或任务完成时）取中位数：

```text
baseline = minLatency × (1 + 20%)
gradient = baseline / sampleLatency
target   = round(gradient × limit + √limit)
limit    = clamp(target, 1, 8)
```

- `minLatency`：低并发下测到的基线；本批没有 profile 时由首批任务学习。
- `headroom = √limit`：避免并发停在过小值（Envoy 同款）。
- 加档要连续 2 个窗口同向；降档立即生效。
- 护栏：UI 停顿 >0 ⇒ 降档；空间见底 ⇒ 降到 1；有失败 ⇒ 本窗口不加；总吞吐比上一窗口跌 >10% ⇒ 拒绝加档；每批最多调整 8 次，超过即冻结。

### 起点

- SSD：`clamp(核数/2, 2, 4)`（首次），之后继承本机 profile。
- HDD/未知：**1**（先拿干净基线；设备类型只影响起点，不是固定规则）。
- 上限统一 8（与外部引擎全局闸门对齐）。

### 本机 profile

- 文件：`%LOCALAPPDATA%\ArchiveFixer\concurrency-<卷+设备哈希>.json`。
- 只存 `LastGoodLimit`（本批起点/降档后的**保守值**）和 `MinLatencySecondsPerGb`；不记录文件名/路径、不上传。
- 本批从 1 起步、中途加到 2 ⇒ 存 1：加档只证明“这一批混合跑更快”，不证明“下一批从 2 冷启动更好”。
- 换卷/换设备键不同，自然失效；文件损坏按无 profile 处理。

## 已验证（2026-11-02）

### H: EAGET 固定盘（4×600 MiB 加密 7z）

结果取日志“开始批量解压→一键处理完成”：

| 配置 | 批量耗时 |
|---|---:|
| 固定 1 | 96 s |
| 固定 2 | 154 s |
| 固定 4（旧默认） | 149 s |
| 固定 8 | 144 s |
| 自动（从 1 起步，两次） | 59 s / 99 s |

- 自动均从 1 起步；第一次 `1→2` 后保存 profile=1（保守值），第二次仍从 1 起步。
- 旧的“把中途加到的 2 写回 profile”实测会让下一批从 2 冷启动变成 136–153 s；已改为只写保守值。
- 每批调整 ≤1 次；无 UI 停顿 >500ms。

### E: 本机 SSD（4×600 MiB 加密 7z）

| 配置 | 批量耗时 |
|---|---:|
| 自动（起点 4） | 6 s |
| 固定 1 | 9 s |
| 固定 2 | 12 s |
| 固定 4（旧默认） | 7 s |
| 固定 8 | 9 s |

自动 6 s ≤ 固定 4 的 7 s（满足“快盘不低于固定 4 的 95%”）；本批未发生调整。
