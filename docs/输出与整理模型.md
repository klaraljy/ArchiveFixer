## 0. 产品要替掉的那套手工劳动（来自 bat 考古）

用户过去在 `111/222/` 里放几十到 200+ 个包，然后依次跑：

| 原脚本 | 干了什么 | 产品化后对应 |
|---|---|---|
| `解压7z分卷文件1.bat` | 对当前目录每个 `*.7z.001` 执行 `7z x … -y`（**静默**），按原结构解压到当前目录 | 「一键处理」的解压引擎（已具备，改造为**先入独立目录**） |
| `删除7z分卷文件.bat` | `del *.7z.0??` 删掉所有分卷 | §9.5 清理源包（已有，默认关） |
| `移动文件夹1.bat` | 把所有**第二层**子文件夹搬进一个扁平 `11111` | 「其余物集中」（§3.2） |
| `移动文件夹2.bat` | 仅当第一层子文件夹里**只有一个子文件夹且没有其它文件**时，把那个子文件夹提上来 | 「单链塌缩」（§3.3 情形 3） |
| `删除空文件夹.bat` | 删掉"任意层级都没有文件"的第一层子文件夹 | **空文件夹清理**（新功能，§5） |

**一句话**：用户真正要的不是"解压"，而是**"把一堆包变成一堆干净的内容物文件夹"**。

> ⚠️ 隐私红线：bat 里写着明文解压密码。**任何代码、日志、文档、提交信息、测试数据都不得包含该密码**（§8）。
> 密码只能来自密码本 / 用户输入，且只存内存。

## 1. 目标根目录解析（用户诉求第 2 点："输出在哪，疯狂完善"）

### 1.1 三种落点模式（互斥，设置项 `OutputPlacementMode`）

| 模式 | 枚举值 | 源包 `111\222.rar` 的产物落点 | 说明 |
|---|---|---|---|
| 同名子文件夹（**默认**） | `PerArchiveSubfolder` | `111\222\内容物` | 与 WinRAR 默认一致：地基不能丢 |
| 当前目录 | `SourceDirectoryFlat` | `111\内容物` | 用户明确要的第 2 种 |
| 自定义位置 · 单独建文件夹 | `CustomRootPerArchive` | `<自定义根>\222\内容物` | 用户明确要的第 3 种（前半） |
| 自定义位置 · 直接解到该目录 | `CustomRootFlat` | `<自定义根>\内容物` | 用户明确要的第 3 种（后半） |

**硬要求**：`CustomRootPerArchive` 与 `CustomRootFlat` 必须是**两个独立可选项**，不能只做一个（用户原话："这个也要有单独的文件夹和解压到此目录之分"）。

### 1.2 路径推导公式（唯一实现处）

```
destRoot  = 模式 ∈ {PerArchiveSubfolder, SourceDirectoryFlat} ? dir(源包) : 自定义根
destDir   = 模式 ∈ {PerArchiveSubfolder, CustomRootPerArchive}
              ? destRoot \ SafeName(源包基名)      // 去掉所有后缀：222.rar / 222.7z.001 / 222.part1.rar → 222
              : destRoot
```
- `SafeName` 必须走既有 `FileNameHelper` 清洗（Windows 保留名、结尾空格/点、非法字符）——复用，不要新写。
- 分卷组：**基名取整个分卷组**（`222.7z.001` → `222`），不是 `222.7z`。已有 `VolumeGroupDetector` 的结果可直接用。
- 冲突处理沿用不变量 3：默认"跳过或自动重命名"，**不得默认覆盖**。
- `SourceDirectoryFlat` 下若 `111/内容物` 与已有文件冲突，一样走冲突策略（不是往 `111/222` 里塞）。

### 1.3 与现有设置的关系
现在的 `ExtractToOriginalDirectory`（布尔）+ `CustomOutputDirectory` + `KeepArchiveNameFolder` **表达不了上面四种**，
按 1.1 重构为单一枚举（旧布尔组合迁移到新枚举：`true`→`PerArchiveSubfolder`、`false`+空根→`PerArchiveSubfolder`、
`false`+有根→`CustomRootPerArchive`），旧配置必须能平滑迁移，不得让用户升级后行为突变。

## 2. 一键处理的两阶段模型（用户诉求第 2.4 点）

用户原话：**"一键处理先解压到单独的文件夹，然后就是在文件夹内处理"**；现状被批"多弄了四个文件夹、分卷文件被解压到外面来了、文件一多根本分不清"。

### 2.1 阶段一：入仓（stage）
- 每个任务在**私有暂存目录**里完成所有中间动作：抠内嵌归档 → 解第一层 → 解内层分卷 → …
- 暂存目录：`<dataRoot>\work\<taskId>\`（已存在，且**不得落 C 盘**）。
- **暂存期间绝对不往源目录写任何东西**：分卷中间件、部分产物、临时文件全部留在暂存区。
  （现状缺陷：分卷被解到用户可见的目录里，用户"分不清"。）

### 2.2 阶段二：定稿（commit）
- 只有当"最终内容物已确定 + 输出校验通过"时，才把结果**一次性**落到 §1 算出的 `destDir`。
- 定稿是**搬运**（同盘 move，跨盘 copy+delete），不是"原地解压"。
- 定稿完成后，按顺序做三件事（**每一步都以"上一步成立"为前提**）：
  1. 按 §3 归置内容物（判定表 1–4）；
  2. 按 §3.2 把中间件集中进 `其余物`；
  3. 按 §3.4 处理**源包**（默认移入 `其余物`，可关；见决策 D-9/D-11/D-12）。
- **失败/取消时**：`destDir` 里不得留下半成品（要么没有，要么完整）；源包**一律不动**、`其余物` 不生成；暂存区保留供排查（不变量 12/13）。

## 3. 从尾巴倒着判定落点（用户诉求第 3 点，核心）

思路：**先看最终内容物长什么样，再决定目录结构**，而不是"解到哪算哪"。

设解压链的**终端内容物**（最后一层归档里的东西）为 `T`，任务目标目录为 `D`（= §1 的 `destDir`）：

### 3.1 判定表（必须按顺序判，先命中先返回）

| # | 终端形态 | 落法 | 例子（源包 `111\222.rar`） |
|---|---|---|---|
| 1 | `T` = **单个文件**（如一个 mp4） | 直接放 `D\` 下；`D` 的名字就是包名（`222`） | `111\222\666.MP4` |
| 2 | `T` = 多个文件 / 多个文件夹 / 自带一层文件夹 | 在 `D\` 下**套一层**，文件夹名取"最后一层归档内最外层那个文件夹名"，没有就取终端归档基名 | `111\222\666\多数内容物` |
| 3 | `T` 被**多重空目录嵌套**包裹（`…/999/内容物`，中间层只有空目录/仅一层文件夹） | 把**最后那个有意义的文件夹**提上来当 `D` 的直接子层 | `111\222\999\内容物` |
| 4 | 终端归档本身**只有一条单链**（每层都只有一个文件夹、没有别的文件） | 塌缩为最深层那个文件夹名（等价于原 `移动文件夹2.bat` 的规则） | `111\222\<最深名>\内容物` |

**用户可选项（`TerminalLayoutMode`）**：
- `KeepLastFolder`（默认）：`111\222\666\内容物` —— 保留最后一层文件夹名；
- `UseArchiveName`：`111\222\内容物` —— 用包名当最后一层，少一层点击。

两种都必须保留 `111\222\其余物`（见 §3.2）。

### 3.2 其余物（用户诉求第 3.5 点；2026-09-22 由「过程物」改名，源包也移进来）

> 用户原话："我一开始的想法是源包也要放在过程物里面，现在你提醒了一下，改为'**其余物**'
> 其余物/源包+过程物，这样删除对用户就更方便一点"。
>
> 期望的样子：
> ```
> 111\
>      内容物A  内容物B  内容物C
>      其余物\
>            222\源包+过程物
>            333\源包+过程物
> ```

- **定义**：除内容物之外**剩下的东西** ——
  ① 为得到内容物而产生的中间件（内层归档、分卷、抠出来的中间 ZIP、纯壳文件夹、对不上内容物的杂物）；
  ② **源包本身**（含分卷整组）。
- **改名**：目录名固定叫 `其余物`；旧名 `过程物` **只用于识别，不再用于新建**
  （老版本已经在用户目录里留下了 `过程物\`，删除功能必须还能清掉它们）。
  名字的唯一来源是 `ProcessArtifactLayout.ArtifactDirectoryName` / `LegacyArtifactDirectoryName`。
- **位置（D-10 的唯一实现处 = `ProcessArtifactLayout`）**：

| 落点模式 | 其余物落在哪 | 例（源包 `111\222.7z`） |
|---|---|---|
| `PerArchiveSubfolder`（默认） | `destDir\其余物\` | `111\222\其余物\` |
| `CustomRootPerArchive` | `destDir\其余物\` | `<根>\222\其余物\` |
| `SourceDirectoryFlat` | `destDir\其余物\<包基名>\` | `111\其余物\222\` |
| `CustomRootFlat` | `destDir\其余物\<包基名>\` | `<根>\其余物\222\` |

  **为什么分两档**：包本来就有自己目录的模式再按包名分一层，就是用户最反感的"凭空多弄一个文件夹"；
  而多个包共用同一个根时不分层，几十上百个包的分卷和中间件会在同一个 `其余物\` 里互相撞名、
  也分不清是谁的（原决策 D-2 的理由）。
- **重名兜底**：内容物那一层正好也叫 `其余物`（或旧的 `过程物`）时，其余物目录改用 `其余物(1)`。
- **体积**：通常较小，但可能很大（分卷 + 源包）→ 详情的日志要报总大小。
- **清理**（用户明确两档）：

| 档 | 行为 | 安全要求 |
|---|---|---|
| 默认 | 移入**回收站** | 操作前**必须让用户确认**（列出路径数量与总大小）；回收站不可用时降级为"不删 + 明确告知" |
| 激进 | **彻底删除** | ① 必须在界面上用**红色**标识；② 必须二次确认（勾选"我知道不可恢复"）；③ 每次删除写日志（路径+理由+总大小）；④ 取消/部分完成时**一律不删** |

- **绝不允许**：把其余物和内容物混在同一层、或把其余物散落在源目录/内容物目录之外。

### 3.3 批量场景（用户诉求第 4 点，产品初衷）
- 场景 A：`111\222\` 下有 50–200+ 个包（大多结构相同，少量是更新的）→ 逐个产出 `111\222\<包名>\内容物`。
  → 直接由 §1.1 默认模式 + §3 判定表得到，**不需要额外规则**。
- 场景 B：`111\222\<名字>\<名字>.rar`（数百个子文件夹，每个里一个包）→ 产出 `111\222\<名字>\内容物`。
  → 注意：这里 `destDir` = 包子文件夹所在目录 + 包基名 = `111\222\<名字>\<名字>`，
    与用户期望 `111\222\<名字>\内容物` 差一层。**规则**：当"包基名 == 其所在目录名"且该目录下只有这一个包时，
    `destDir` 取父目录（即塌缩掉重复的一层），产物落在 `111\222\<名字>\内容物`。此规则必须可关（设置项），默认开。
- 两场景都必须**单任务失败不中断整批**、结果可追溯（不变量 9/14）。

### 3.4 源包处理（2026-09-22 用户拍板：默认移入其余物）

> ⚠ 这一节是**不变量 1（默认不改源文件）的唯一例外**，而且例外范围被用户显式限定为
> "**一键处理** + `SourceHandling = MoveToRest / DeleteAfterVerify`"。

- **设置项**：`SourceHandling`（字符串存枚举名，`AppSettings.ParseSourceHandling` 容错，空/非法 → `MoveToRest`）

| 值 | 一键处理里怎么处理源包 |
|---|---|
| `MoveToRest`（**默认**） | 整组源包（分卷组 = 全部卷）移入其余物 |
| `KeepInPlace` | 留在原地，一个字节都不动 |
| `DeleteAfterVerify` | 沿用既有 §9.5 清理（回收站 / 彻底删除按既有设置；只有"解压成功 + 校验通过"才删） |

- **两条路径行为一致**（用户 2026-09-22 二次拍板，**推翻**早先"地基路径永远不动源包"的版本一）：
  **一键处理**与**手动「只解压」**都按 `SourceHandling` 处理源包 —— 成功了就移入 `其余物`，失败了就原地不动。
  原话："**如果成功了你就直接将源包放在其余物里面**" + "**地基路径也照这条走**"。
  代码上：`ExtractionCoordinator.StartExtractAsync`（地基）与 `StartExtractForOneClickAsync`（整理路径）
  **共用同一套源包处理**；`KeepInPlace` 档仍是"永不搬"的出口。
- **动源包的四个前提（缺一不可）**：① 内容物已定稿；② 输出校验通过；③ 未取消；④ 属于本任务分卷组。
  任何一个不成立 → 源包原地不动、`其余物` 不生成（**这条是红线，不变**）。
- **搬运规则**：整组一起移；同名冲突加 `(1)(2)`，**绝不覆盖**；
  跨盘走"**复制成功后再删原件**"（复制失败源包一个字节都不动，绝不"先删后移"）；每次搬运写日志（从哪到哪 + 大小）。
- **搬不动时**（只读 / 被占用）：任务标「**部分完成**」并写明"内容物已好，源包未能移入其余物"，
  **内容物结论不受影响**（产物、校验、归集都照旧）。
- **搬完要回写任务路径**：`task.CurrentPath` / `VolumePaths` 改到新位置 ——
  一键处理的续解扫描靠它把"刚搬走的源包"排除掉，否则源包会被当成新的内层包再解一遍（内容物凭空多一份）。
- 续解出来的**内层包**不参与源包处理：它的"源文件"是我们自己产出的中间件，已经在其余物里了。

## 4. 地基（用户强调："一定不能少"）
- **WinRAR 式基础解压必须始终可用**：选一个包 → 解压到同名子文件夹 → 完事。这条路径不得被"智能整理"挡住或变慢。
- **地基路径也按同一套源包规则**（手动「只解压」按钮走的就是它）：成功 + 校验通过 → 源包移入 `其余物`；
  失败/取消 → 原地不动；`KeepInPlace` 档 → 一律不搬。这是不变量 1 的例外**之内**（§3.4）。
- 增强项（定稿整理、其余物集中、源包搬运、自动续解）都必须是**可关的**，关掉后行为 == 传统解压器。
- 默认值取"最不意外"：`PerArchiveSubfolder`（同名子文件夹）+ 终端落法 `KeepLastFolder` + 其余物集中**开**。

## 5. 空文件夹清理（原 `删除空文件夹.bat`）
- 规则：删除"**任意层级都没有文件**"的目录（只剩空目录树的目录）；只要任意层级有文件就保留（与原 bat 一致）。
- 默认**关**；执行前二次确认；**移入回收站**；删除前写日志。
- 作用于"本次任务的目标根目录"内，**禁止越出**（走 `ArchivePathGuard.IsInsideRoot`）。
- 与其余物清理是两个独立动作，不得合并成一个开关。

## 6. 不变量（本模型新增/强调）
1. 暂存期间不往源目录写任何东西。2. 定稿前 `destDir` 不得出现半成品。
3. 其余物只允许出现在 §3.2 表格里的那一处（包自己目录下的 `其余物\`，或共用根下的 `其余物\<包名>\`）。
4. 彻底删除必须红色标识 + 二次确认 + 写日志；回收站不可用时不删。
5. 基础解压路径（同名子文件夹）永远可用且是默认；它的**源包处理与整理路径同一套规则**（§3.4）。
6. 输出根解析只有一处实现（`OutputPlacement`）、其余物落点只有一处实现（`ProcessArtifactLayout`），
   禁止在别处再拼路径。
7. 源包只有在"定稿 + 校验通过 + 未取消 + 属于本任务分卷组"四条同时成立时才可能被移动/删除（§3.4）。
8. **任何"修复 / 重建"产物必须另存为新文件、绝不覆盖原件**（通用原则，来自 `docs/WinRAR功能参考.md` §2 J 组）：
   将来真做"修包 / 重建索引 / 换封装"这类动作时，产物一律落到**新文件**（同名冲突加 `(1)`），
   原件一个字节都不动 —— 与我们"失败时源包原地不动"（§3.4）是同一个价值观：
   宁可多一个文件让用户自己比，也绝不接受"原件被程序改坏了"。这条同样约束第二引擎（`docs/引擎与外部工具.md`）。

## 7. 决策记录（连续作业期间由主代理拍板，用户醒后可改）

> 依据：全局 `AGENTS.md` 作业模式规矩 7「连续作业期间不逐步征求确认，纯技术选型/顺序/命名/措辞自己定」。
> 每条给出「为什么这样定」，用户若要改只需改这一行。

| # | 问题 | 决策 | 理由 |
|---|---|---|---|
| D-1 | 单文件终态默认落在哪 | **`111\222\666.MP4`**（直接放任务目录下），`TerminalLayoutMode=KeepLastFolder` 只影响"多文件/自带文件夹"情形 | 用户原话就是 `111/222/666.MP4（内容物）`；少一层点击 |
| D-2 | 模式 B（解压到当前目录）时中间件放哪 | **`<源目录>\其余物\<包名>\`** | 模式 B 下多个包共用源目录，集中到一个 `其余物` 会互相撞名；按包名再分一层既集中又可追溯（D-10 把它推广到模式 D） |
| D-3 | 一键处理是否改成"先全进工作区再定稿" | **改**（用户明确要求） | 这是"分卷被解到外面"的唯一根治办法；基础解压路径不受影响，仍是默认 |
| D-4 | 批量里遇到"无法判定终态/多分支" | **静默走保守落点（多套一层文件夹）+ 写 WARN 列出任务**，不逐个弹窗 | 用户场景是 50–200+ 个包，逐个问等于不可用；保守落点不丢数据，用户事后能自己挪 |
| D-5 | `readme.txt` / `*.url` / 论坛推广 txt 算内容物还是其余物 | **默认算内容物**；提供设置项「把说明文件/网址快捷方式视为其余物」**默认关** | 自动删文本文件风险高（可能是真说明）；用户要删时一键勾选即可 |
| D-6 | 包基名里 `.7z.001` 的处理 | **`222.7z.001` / `222.part1.rar` / `222.001` → 一律取 `222`**，唯一实现放 `OutputPlacement.ResolveArchiveBaseName` | 见 §8 的根因；`GetArchiveBaseName` 只去最后一个后缀，是本项目"多套一层目录"的历史根因 |
| D-7 | 自定义根为空时怎么办 | **报错让用户重选，绝不回落到程序安装目录** | 现状 `PathService.BuildOutputPath` 会回落到 `AppBaseDirectory`，会把内容物解进程序目录（C 盘/安装目录），既难找又违反"缓存不落 C 盘"的精神 |
| D-8 | 「过程物」改名与老目录 | **改名 `其余物`**；`ProcessArtifactLayout.ArtifactDirectoryName` 是唯一来源，**旧名 `过程物` 保留为"识别用"**（`LegacyArtifactDirectoryName` / `IsArtifactDirectoryName` / `FindExistingArtifactDirectories`） | 源包也进来了，"过程物"这词不再准确；老版本已经在用户盘上留下 `过程物\`，删除功能必须还能清掉它 |
| D-9 | 源包怎么处理 | **默认 `MoveToRest`（移入其余物）**，可关（`KeepInPlace`）或改成 `DeleteAfterVerify`；**两条路径（一键处理与手动「只解压」）行为一致：成功即搬，失败/取消不搬** | 用户原话："其余物/源包+过程物，这样删除对用户就更方便一点"；后续又明确"**如果成功了你就直接将源包放在其余物里面**"+"**地基路径也照这条走**"（**推翻**早先"地基路径永远不动源包"的版本一） |
| D-10 | 其余物要不要按包名分层 | **只在"多个包共用一个输出目录"时分层**（模式 B `SourceDirectoryFlat` / 模式 D `CustomRootFlat` → `111\其余物\222\`）；包本来就有自己目录的模式（默认 `PerArchiveSubfolder` / `CustomRootPerArchive`）直接 `111\222\其余物\` | 共用根不分层会互相撞名、分不清是谁的；包有自己的目录再分层就是用户最恨的"多弄了文件夹" |
| D-11 | 什么时候才允许动源包 | **内容物已定稿 + 输出校验通过 + 未取消 + 属于本任务分卷组**，四条缺一不可；失败/部分完成/取消 → 源包原地不动、`其余物` 不生成 | 与 §9.5 清理源包同一套门槛；源包是用户唯一无法再生的东西，宁可不动 |
| D-12 | 搬运本身的规则 | **整组一起移**（分卷全卷）；**跨盘 = 复制成功后再删原件**；**绝不覆盖**（同名加 `(1)(2)`）；每次搬运写日志（从哪到哪 + 总大小）；搬不动 → 任务标「部分完成」并写明"内容物已好，源包未能移入其余物"，内容物结论不受影响 | 半组卷散在两个目录里比"晚一点停"糟得多；"先删后移"在复制失败的瞬间就把用户的包弄丢了；部分成功不得显示为成功（不变量 6） |

## 8. 已定位的历史根因（来自 bat + 旧代码考古）

1. **"分卷被解压到外面、多弄了四个文件夹"**：
   - 旧 `FileNameHelper.GetArchiveBaseName` 只去**最后一个**后缀 → `a.7z.001` → `a.7z`、`001.part1.rar` → `001.part1`；
   - 旧 `ArchiveDetectService` / `FileScanService` **通篇没有分卷组概念**（一卷 = 一个任务），
     于是每个分卷各自解压、各自建目录。
   - **当前仓库仍有前半段**：`GetArchiveBaseName` 只处理 `.tar.gz/.tar.bz2/.tar.xz`，其余只去最后一个后缀。
     **证据**：2026-09-21 端到端产物里出现的目录就是 `17274362.7z\岳母交换计划 1.mp4`（应为 `17274362\`）。
   - 修法：`OutputPlacement.ResolveArchiveBaseName` 成为唯一实现；`FileNameHelper.GetArchiveBaseName` 改为转调或补上分卷后缀处理（由 R2/R3 的负责人接线）。
2. **"四个文件夹"的后半段**：续解把内层包当成**独立任务**、各自拿自己的输出目录 →
   必须合并成"一个源包 = 一个最终目录"（§2.2 / R3）。
3. **`ExtractionWorkspace` 已有 90%**：`layer-NNN/output`、`Publish`、`Cleanup`、`WriteReport` 都在，
   缺的只是 `final/` 与 `process/` 两个子目录 —— 阶段化改造优先复用它，不要另造工作区。
4. **回收站 API**：`Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile/DeleteDirectory`
   （`RecycleOption.SendToRecycleBin`）与 `SHFileOperation` P/Invoke 都不是 NuGet 依赖，两种都可行；
   实现时按"能测、失败可降级"选一种，并在 README 的已知限制里写明网络盘/策略禁用时不可用。

## 9. 一键处理的"本次选项"面板（待实现，来自 `docs/WinRAR功能参考.md` 采纳项 B12/B13）

用户诉求的由来：WinRAR 把"解压到"做成**每次操作可临时选**的运行期选项，而我们四种落点只能进设置里改——
**逼用户"进设置 → 改 → 回来"是最典型的冗余操作**，而落点恰恰是最常需要临时改的一项。

### 9.1 面板内容
点「一键处理」时，**先弹一次本次选项面板**（不是每次都弹：给"不再询问，直接按上次的来"的勾选项，默认记住）：

| 项 | 默认值 | 语义 |
|---|---|---|
| **本次落点** | 取设置里的当前值 | 四种模式四选一；**只在本次生效**，不写回设置 |
| 指定位置 | 取设置里的当前值 | 仅"指定位置"两种模式需要 |
| 终端落法 | 取设置里的当前值 | 保留最后一层文件夹名 / 改用包名 |
| 源包处理 | 取设置里的当前值 | 移入其余物 / 保持原位 / 校验后删除 |
| ☐ **把本次选择存为默认** | 不勾 | 勾上才写回 `appsettings.json` |

### 9.2 硬要求
1. **值只有一处解析**：面板产出的"本次落点"必须仍经 `OutputPlacement` 唯一实现；
   面板只是把用户的选择**临时覆盖**当前运行的设置快照，**不得**在别处再拼一次路径（§6 不变量 6）。
2. **不写回、不污染**：不勾"存为默认"时，`appsettings.json` **一个字节都不许改**（有测试钉住）。
3. **批只问一次**：一次一键处理只弹一次（50–200 个包的场景不容许逐个问，与 D-4 一致）。
4. **无 UI 宿主不弹窗不死等**：直接取设置值继续（降级路径必须有测试）。
5. **不改变默认行为**：默认档 = 与现在完全一致（四种落点的设置值 + KeepLastFolder + 源包移入其余物）；
   关掉面板（勾"不再询问"）后的行为也必须是"按设置走"。
6. **可追溯**：本次实际用的落点要写进日志与任务详情（用户要能回答"这次为什么解到这里"）。
