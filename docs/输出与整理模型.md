## 0. 产品要替掉的那套手工劳动（来自 bat 考古）

用户过去在 `111/222/` 里放几十到 200+ 个包，然后依次跑：

| 原脚本 | 干了什么 | 产品化后对应 |
|---|---|---|
| `解压7z分卷文件1.bat` | 对当前目录每个 `*.7z.001` 执行 `7z x … -y`（**静默**），按原结构解压到当前目录 | 「一键处理」的解压引擎（已具备，改造为**先入独立目录**） |
| `删除7z分卷文件.bat` | `del *.7z.0??` 删掉所有分卷 | §9.5 清理源包（已有，默认关） |
| `移动文件夹1.bat` | 把所有**第二层**子文件夹搬进一个扁平 `11111` | 「其余物集中」（§3.2） |
| `移动文件夹2.bat` | 仅当第一层子文件夹里**只有一个子文件夹且没有其它文件**时，把那个子文件夹提上来 | 「单链塌缩」（§3.3 情形 3） |
| `删除空文件夹.bat` | 删掉"任意层级都没有文件"的第一层子文件夹 | **空文件夹清理**（新功能，§5） |

**一句话**：用户真正要的不是"解压"，而是**"把一堆包变成一堆干净的内容物文件夹"**。

> ⚠️ 隐私红线：bat 里写着明文解压密码。**任何代码、日志、文档、提交信息、测试数据都不得包含该密码**（§8）。
> 密码只能来自密码本 / 用户输入，且只存内存。

## 1. 目标根目录解析（用户诉求第 2 点："输出在哪，疯狂完善"）

### 1.1 落点模型 v2（2026-09-27 用户拍板，**当前唯一口径**）

> 用户原话（2026-09-24，仍然有效）：「我们是有两个选项的，选择文件或者选择文件夹……
> **我们解压绝对不能将原来的文件夹给弄混乱**」。
> 2026-09-27 第二轮又一次性定下三条（这版把早先的"两档落点 + 四条规则"收敛成一个模型）：
> ① **终点落法不再让用户选** —— 固定为"保留压缩包自带的那一层内层文件夹，外面再套一层以包名命名的文件夹"；
> ② **一律不塌缩** —— 他原话："不行，如果 `111\222\` 这层文件夹里面还有很多的东西呢，这不就是将文件夹弄混乱了吗"；
> ③ 要"平铺"只剩一条路：①页「手动操作」里的「**解压到当前文件夹**」，只对那一次点击生效。

判定只有两个维度：**用户选中的是文件还是文件夹**（`SourceSelectionKind`，导入那一刻记在任务上）
× **有没有指定位置**（`OutputPlacementMode`，只剩两档）。

| 选中对象 | 有没有指定位置 | 落点 | 名字取自 |
|---|---|---|---|
| **文件** `111\222.rar` | 未指定 | `111\222\内容物` | 去掉所有后缀的**包名**（`222`） |
| **文件夹** `111\222\` | 未指定 | 就在 `222\` **里面**：`111\222\a\内容物`（每个包一层） | 各包自己的**包名** |
| **文件** `222.rar` | 指定 `BBB` | `BBB\222\内容物` | 去掉所有后缀的**包名**（`222`） |
| **文件夹** `AAA\` | 指定 `BBB` | `BBB\AAA\**子路径**\包名\内容物`（每个包一层、**相对子路径原样保住**） | **选中的文件夹名** + 子路径 + 包名 |

- **"文件夹 + 未指定"**（用户原话："倘若是选中 222 文件夹，`111\222` 在本地解压，我们就在 222 文件夹里面操作，
  不将东西往外面扔"）：产物一律落在**所选文件夹里面** —— ⛔ 不新建 `111\222\222\` 这一层，
  ⛔ 一个字节都不扔到 `111\` 或更外面。
- **"文件夹 + 指定位置"（方案 A，2026-09-27 改正）**：**保留选中文件夹名那一层**，再把
  "这个包相对选中文件夹的那一段子路径"原样搬过去，**每个包再占自己一层**（包名）：
  `AAA\新建文件夹_20260916_152637\解压软件\rar-android-722.132.apk`
  → `BBB\AAA\新建文件夹_20260916_152637\解压软件\rar-android-722.132\`。
  子路径里的 `..` / 绝对路径 / 盘符一律不认（拒绝后按"包直接在选中文件夹里"处理），
  纯字符串运算、不碰磁盘（`OutputPlacement.ResolveRelativeSubPath`）。
  ⛔ 这一档**不再"多个包共用一层"**：`SharesDestinationWithOtherPackages` 恒为 `false`。
- **一律不塌缩**：`111\222\222.rar` → `111\222\222\内容物`。旧「场景 B」那条
  "包名 == 所在目录名且目录里只有这一个包就塌掉一层"**已退役**（判据里不再有"扫目录"这一环，
  落点对用户完全可预期：永远多这一层、永远不乱）。
- **手动档「解压到当前文件夹」**（`ExtractOptions.ExtractIntoSourceFolder`，语义 = WinRAR 右键那一句）：
  `111\222.rar` → `111\内容物`，**不建包名那一层**、包内自带的文件夹照旧保留。
  ⛔ **只有 ①页那颗按钮会打开它**（一键处理 / 继续解 / 批量永远套包名那一层）；
  ⛔ 不许摊在盘根上（盘根的源包直接判失败、给明确原因）；
  同名冲突按当前覆盖档处理（摊平更容易撞名 —— 这个代价用户 2026-09-27 明确接受，日志里会提醒一句）。
- **包名取法**只有一处实现（`OutputPlacement.ResolveArchiveBaseName`）：分卷组取整组基名
  （`222.7z.001` → `222`）、伪装后缀接着剥（`222.rar.jpg` → `222`）、内嵌归档（双面文件）按可见名字取
  （`222.mp4` → `222`）—— 复用 `FileNameHelper.StripVolumeMarkers`，不另写一份。
- **枚举值刻意保留 0 与 2**（不重新编号）：旧值 1 = 摊平到当前目录、3 = 直接解到指定目录，
  编号一变会让旧配置**静默**落到别的落点。迁移在 `OutputPlacement.NormalizeLegacyMode` /
  `ParsePlacementMode` / `AppSettings.Normalize` 三处收口（读旧 `appsettings.json` 不炸、也不抛）。

### 1.2 路径推导公式（唯一实现处）

```
destRoot = 未指定位置 ? dir(源包) : 指定位置
包名     = 指定位置 且 选中对象是文件夹 ? SafeName(选中的文件夹名)
           : SafeName(包基名)                 // 分卷组 = 整组基名
destDir  = 选中文件夹 + 指定位置 ? destRoot \ 选中文件夹名 \ 相对子路径 \ 包基名
           : destRoot \ 包名                  // 其余三档都只建这一层
手动档   = 解压到当前文件夹 ? dir(源包)       // 不建包名那一层；盘根直接判失败
```
- `SafeName` 走既有 `FileNameHelper` 清洗（Windows 保留名、结尾空格/点、非法字符）——复用，不要新写。
- 冲突处理沿用不变量 3：默认"跳过或自动重命名"，**不得默认覆盖**。
- ⚠ 落点解析是**纯函数**：不查磁盘、不扫目录（"不塌缩"之后连"这一层里还有没有别的包"都不需要知道了）。

### 1.3 与旧设置的关系
落盘仍是**两个布尔**（`ExtractToOriginalDirectory` + `CustomOutputDirectory` + `KeepArchiveNameFolder`），
旧版本也读得懂；但第二个布尔**已作废**（没有"不建子文件夹"的档了），`AppSettings.Normalize` 里归一成 `true`。
旧配置迁移口径（`OutputPlacement.FromLegacyFlags`，**唯一实现处**）：

| 旧写法 | 原来是 | 现在落到 |
|---|---|---|
| `true` + 任意根 | 同名子文件夹 / 摊平到当前目录 | `PerArchiveSubfolder`（`111\222\`） |
| `false` + 有根 | 指定位置（建/不建子文件夹两种） | `CustomRootPerArchive`（`BBB\222\`） |
| `false` + 空根 | 旧代码回落**程序目录**（绝不再沿用） | `PerArchiveSubfolder` |

## 2. 一键处理的两阶段模型（用户诉求第 2.4 点）

用户原话：**"一键处理先解压到单独的文件夹，然后就是在文件夹内处理"**；现状被批"多弄了四个文件夹、分卷文件被解压到外面来了、文件一多根本分不清"。

### 2.1 阶段一：入仓（stage）
- 每个任务在**私有暂存目录**里完成所有中间动作：抠内嵌归档 → 解第一层 → 解内层分卷 → …
- 暂存目录在**本批工作区根**下一单一个目录（`<工作区根>\<taskId>\`）。⚠ **工作区根落在这一单的目标目录里**：
  **唯一来源** = `<目标目录>\.ArchiveFixer.work`（点开头 + `Hidden` 属性，2026-09-30 用户明确指示：
  不再在盘根另开一个顶层目录；⛔ **没有任何设置项 / 参数能改它** —— 用户原话"用户没有定工作区的权力"）；
  ⛔ 目标位置不可用就**报错停手并说清是哪一个位置**，**绝不回落 C 盘 / 程序目录**
  （唯一实现 `Storage/WorkspaceRootResolver.cs`，**不得落 C 盘**、**不得与源包同层**）。
  检验等级 L0–L6 见 `docs/检验等级.md`（⛔ 别在这里再抄一份）。
  ⚠ 工作区**落在目标目录里面**，所以凡"扫产物 / 数内容物 / 找内层包 / 校验落点"的判据都必须排除
  它那棵树（唯一出口 `Storage/WorkspaceTree.cs`）。
- **暂存期间绝对不往源目录写任何东西**：分卷中间件、部分产物、临时文件全部留在暂存区。
  （现状缺陷：分卷被解到用户可见的目录里，用户"分不清"。）

### 2.2 阶段二：定稿（commit）
- 只有当"最终内容物已确定 + 输出校验通过"时，才把结果**一次性**落到 §1 算出的 `destDir`。
- 定稿是**搬运**（同盘 move，跨盘 copy+delete），不是"原地解压"。
- 定稿完成后，按顺序做三件事（**每一步都以"上一步成立"为前提**）：
  1. 按 §3 归置内容物（判定表 1–4）；
  2. 按 §3.2 把中间件集中进 `其余物`；
  3. 按 §3.4 处理**源包**（默认 `KeepInPlace` 一个字节都不搬；选了"放入其余物"才搬）与**其余物**
     （默认留着；`RecycleBin` / `Delete` 两档才动手）。见决策 D-9/D-11/D-12 与 §3.4.1。
- **失败 / 取消 / 部分完成时**：`destDir` 里不得留下半成品（要么没有，要么完整）；源包**一律不动**、
  `其余物` 不生成；**暂存区默认整份删掉（含空壳）** —— 失败 / 取消 / 部分完成收尾时，把这一单自己的
  任务工作区目录整份删除（含 stage、内嵌归档副本、已解出的中间件），递归逐层工作区同样清掉
  （唯一实现处 `Storage/WorkspaceCleanupService`；删除前两道容器内校验，越界只写 WARN、一个字节都不删）。
  ⚠ 只有 `KeepFailedWorkspace`（**默认 false**，③页「工作区残留 → 失败时保留中间产物（排查用）」）
  打开时才保留现场供排查，并写 INFO 说清在哪 / 几个 / 多大（不变量 12/13）。
  ⚠ 程序被**强杀 / 断电**是另一回事：来不及收尾，那份工作区**会留着**，下次启动只报告位置、不自动删。

## 3. 从尾巴倒着判定落点（用户诉求第 3 点，核心）

思路：**先看最终内容物长什么样，再决定目录结构**，而不是"解到哪算哪"。

设解压链的**终端内容物**（最后一层归档里的东西）为 `T`，任务目标目录为 `D`（= §1 的 `destDir`）：

### 3.1 判定表（必须按顺序判，先命中先返回）

| # | 终端形态 | 落法 | 例子（源包 `111\222.rar`） |
|---|---|---|---|
| 1 | `T` = **单个文件**（如一个 mp4） | 直接放 `D\` 下；`D` 的名字就是包名（`222`） | `111\222\666.MP4` |
| 2 | `T` = 多个文件 / 多个文件夹 / 自带一层文件夹 | 在 `D\` 下**套一层**，文件夹名取"最后一层归档内最外层那个文件夹名"，没有就取终端归档基名 | `111\222\666\多数内容物`（`666\` 那一层就是套出来的） |
| 3 | `T` 被**多重空目录嵌套**包裹（`…/999/内容物`，中间层只有空目录/仅一层文件夹） | 把**最后那个有意义的文件夹**提上来当 `D` 的直接子层 | `111\222\999\内容物` |
| 4 | 终端归档本身**只有一条单链**（每层都只有一个文件夹、没有别的文件） | 塌缩为最深层那个文件夹名（等价于原 `移动文件夹2.bat` 的规则） | `111\222\<最深名>\内容物` |

**终端落法（2026-09-27 起固定，不再让用户选）**：
- 固定档 = `KeepLastFolder`：保留压缩包自带的那一层内层文件夹，外面再套一层以包名命名的文件夹 ——
  `111\222\666\内容物`。内容物**直接摊在归档根上**（包内没有自带文件夹）时，那一层就用**包名**
  （落点末段已经叫包名时不重复套，见下）。
- 早先那一档 `UseArchiveName`（用包名当最后一层）与那个"包名与所在目录同名就去掉一层"的勾选框
  **已从设置与界面上删除**（`AppSettings.TerminalLayoutMode` / `CollapseRepeatedFolderLayer` 两个键不再存在，
  旧配置里留着它们也能正常读入、不报错、不影响行为）。
  枚举 `TerminalLayoutMode` 与 `ParseTerminalLayoutMode` 仍留在 `OutputPlacement` 里当**内部契约**
  （其余物布局等路径还在用这个参数），但生产路径一律传固定档。

⚠ 两条**防止重复层**的既有判断继续生效（都是"路径本身"就能判的事实）：
① 套出来的那一层名字**等于落点最后一段**时不套（`111\222\222` 这种重复层是用户点名抱怨过的形状）；
② 续解那一层如果**已经在落点路径里**（忠实档给每一层都建了层）就不再套（否则 `666\666`）。

⚠ **它与 §3.5 的「特定解压」有优先级关系**：特定解压的规则**优先**。规则生效时判定表里"要套的那一层"
根本不套（`111\222\内容物`），终端落法连上场的机会都没有；规则没生效（总开关关着 / 规则没开 /
包内不止一个文件夹）时才按上面那档走。
⚠ 手动档「解压到当前文件夹」下**规则不参与**：那一档本来就不套包名层，规则想省的那一层已经不存在了
（要省就只能去拆归档自带的结构，与"按包内原样解开"冲突）。

⚠ **它和 §1.1 的落点规则是两个互不干扰的轴**（别把两者混为一谈）：
§1.1 决定的是**任务落点 `destDir`**（产物落在哪个目录、那层目录叫什么），
终端落法决定的是 **`destDir` 里面**再套出来的那一层叫什么 —— 什么时候套见上面的判定表（只有"多文件 / 自带一层文件夹"才套）。
所以落点规则里的 `111\222\`、`BBB\AAA\…\包名\` 一个字都不会因为终端落法而变。

两种都必须保留 `111\222\其余物`（见 §3.2）。

### 3.2 其余物（用户诉求第 3.5 点；2026-09-22 由「过程物」改名，源包也移进来）

> 用户原话："我一开始的想法是源包也要放在过程物里面，现在你提醒了一下，改为'**其余物**'
> 其余物/源包+过程物，这样删除对用户就更方便一点"。
>
> 期望的样子：
> ```
> 111\
>      内容物A  内容物B  内容物C
>      其余物\
>            222\源包+过程物
>            333\源包+过程物
> ```

- **定义**：除内容物之外**剩下的东西** ——
  ① 为得到内容物而产生的中间件（内层归档、分卷、抠出来的中间 ZIP、纯壳文件夹、对不上内容物的杂物）；
  ② **源包本身**（含分卷整组）。
- **改名**：目录名固定叫 `其余物`；旧名 `过程物` **只用于识别，不再用于新建**
  （老版本已经在用户目录里留下了 `过程物\`，删除功能必须还能清掉它们）。
  名字的唯一来源是 `ProcessArtifactLayout.ArtifactDirectoryName` / `LegacyArtifactDirectoryName`。
- **位置（D-10 的唯一实现处 = `ProcessArtifactLayout`）**：
  判据不是"落点模式"，而是**这个落点目录是不是同一次导入里多个包共用的**
  （`OutputPlacementResult.SharesDestinationWithOtherPackages`）。
  ⚠ **2026-09-27 起这个事实恒为 `false`**：最后一档会共用的落点（"选文件夹 + 指定位置"）已经改成
  **每包一个目录**（§1.1 方案 A），所以生产路径上只会出现下面第一行那种形状；
  第二行那条规则**留着当契约与兜底**（老目录、外部调用方、单测都在用），⛔ 别顺手删。

| 落点 | 其余物落在哪 | 例（源包 `111\222.7z`） |
|---|---|---|
| 每包一个目录（**现在所有档都是这种**） | `destDir\其余物\` | `111\222\其余物\` |
| ~~共用落点~~（已退役，参数仍在） | `destDir\其余物\<包基名>\` | `<根>\222\其余物\222\` |

  **为什么原来分两档**：包本来就有自己目录的落点再按包名分一层，就是用户最反感的"凭空多弄一个文件夹"；
  而多个包共用同一个目录时不分层，几十上百个包的分卷和中间件会在同一个 `其余物\` 里互相撞名、
  也分不清是谁的（原决策 D-2 的理由）。现在没有"共用"这一档了，所以恒取第一行。
- **重名兜底**：内容物那一层正好也叫 `其余物`（或旧的 `过程物`）时，其余物目录改用 `其余物(1)`。
- **体积**：通常较小，但可能很大（分卷 + 源包）→ 详情的日志要报总大小。
- **清理**（用户明确两档）：

| 档 | 行为 | 安全要求 |
|---|---|---|
| 默认 | 移入**回收站** | 操作前**必须让用户确认**（列出路径数量与总大小）；回收站不可用时降级为"不删 + 明确告知" |
| 激进 | **彻底删除** | ① 必须在界面上用**红色**标识；② 必须二次确认（勾选"我知道不可恢复"）；③ 每次删除写日志（路径+理由+总大小）；④ 取消/部分完成时**一律不删** |

> **多任务：合并成 1 次确认**（用户 2026-09-22 拍板，原话："**要合并成 1 次确认，不要有冗余操作**"）。
> 勾了 N 个任务时不再"每个任务弹一次预览 + 一次确认"（勾 5 个 = 5 次点击），而是：
> ① 先把 **全部**目标各预览一遍（后台），合成一个确认框 —— 逐个列出**每个任务的作用范围（哪个目录）**、
> **合计**条目数与字节数、以及**哪些任务含源包**（含就点名，因为删了要重新下载）；
> ② 用户**只确认一次**（红色 + 「改为彻底删除，不进回收站」勾选项，措辞按多任务调整）；
> ③ 激进档的**二次确认**整批也只来一次（不可逆操作仍需显式确认）；
> ④ 确认后**逐个执行**，**单个任务失败不中断整批**；
> ⑤ 最后给**一次**汇总：成功 N / 失败 M（各自原因）/ 释放字节数 —— 有任何一项没删掉就**不得**显示成全部成功。
> 「删除本目录全部其余物」保持整目录语义（同目录只算一次），它的确认框本来就要点名"影响该目录下 N 个包"。

- **绝不允许**：把其余物和内容物混在同一层、或把其余物散落在源目录/内容物目录之外。

### 3.3 批量场景（用户诉求第 4 点，产品初衷）
- 场景 A：`111\222\` 下有 50–200+ 个包（大多结构相同，少量是更新的）→ 逐个产出 `111\222\<包名>\内容物`。
  → 用户用「添加文件夹」选 `111\222`：直接由 §1.1 的"文件夹 + 未指定位置"那一条 + §3 判定表得到，
  **不需要额外规则**；产物全部留在 `222\` 里面。
- 场景 B（**2026-09-27 改口径**）：`111\222\<名字>\<名字>.rar`（数百个子文件夹，每个里一个包）→
  产出 `111\222\<名字>\<名字>\内容物`。
  → 旧规则在这里"塌掉重复的一层"（落 `111\222\<名字>\内容物`），**已退役**：用户原话
  "不行，如果 `111\222\` 这层文件夹里面还有很多的东西呢，这不就是将文件夹弄混乱了吗" ——
  那一层里完全可能还有几十个小文件、说明、别的素材。现在**一律不塌缩**：
  `destDir` 永远 = 所在目录 + 包基名，产物永远在 `名字\名字\` 里面，谁也混不到一起去。
- **反向红线**（用户原话："我们解压绝对不能将原来的文件夹给弄混乱"）：未指定位置时，
  源目录里**除了新出现的产物子文件夹，不许新增任何东西**，更不许把产物扔到上一层去。
  测试用"跑前跑后对比源目录第一层条目"来钉（`PlacementRulesTests`）。
  手动档「解压到当前文件夹」是**唯一**的例外：那是用户显式点的一次动作，落点就是源包自己那一层。
- 两场景都必须**单任务失败不中断整批**、结果可追溯（不变量 9/14）。

### 3.3.1 续解（嵌套）层：首尾必留，中间看开关（2026-09-27 用户拍板）

一键处理会顺着"包里还有包"往下解（每批最多 `MaxRecursionDepth` 轮，默认 5）。
**每一层的产物落在哪一层目录**由两个档位决定，用户在②页「嵌套与覆盖」里挑：

| 档位（设置项） | 形状 | 说明 |
|---|---|---|
| **忠实档**（`OmitMiddleContinuationLayers = false`，**默认**） | `111\222\333\444\555\666\内容物` | **干净的单链过路层**（那一层只装着下一个包、自己没有内容物）各占一层，层名 = 那个包的包基名 |
| **简洁档**（`true`） | `111\222\666\内容物` | 连过路层也省掉：第一层（源包名）与最后一层（装着内容物的那一层）保留 |

- **父层已经出了内容物 → 两种档位都不另建层，内层包的东西并进父层那一个目录**（2026-09-27 真机拍板）。
  用户原话："最后的结果应该和上一层文件在同一个目录里面的，但是你直接把他放进去了，这个就非常的危险了"。
  现场：`（T250）经济2\国考资料.txt`（外层内容物）旁边本该就是 `老王宣传\…`（内层包 `Sociology.7z` 解出来的真内容），
  而我们给内层包又造了一层 `Sociology\`，把真内容埋深了一层。
  ⚠ 这条**优先于"中间层省不省"**：它是"内容物该和谁并排"的问题，不是"省不省"的问题。
- **同一个父任务这一轮认出多个内层包 → 一律各占一层**（两种档位都一样）：
  它们是**并列的分支**，挤进同一层会互相撞名；这条压过上面那条。
- ⛔ **过程物名不成层**（红线）：这一层本身就是分卷组的一卷时（真机现场 `59768866.001/.002`），
  它的包基名是**过程物**的名字、不是用户认得的包名 —— 绝不拿它当文件夹名
  （真机上那个 `…\包名\59768866\真内容` 就是这么造出来的）。这一档下分卷组的内容物归父任务那一层。
- ⛔ **层名被内层包自己那个文件占着时不另建**（物理约束，2026-09-27 真机测试逮到）：
  **名字被改坏、剥不出后缀**的包（`user.jp删除g`、`222.ra删除r`）包基名 == 文件名，
  于是 `<父层>\user.jp删除g` 既是那个文件、又要当这一层的目录 —— Windows 同一条路径不许两样并存，
  不挡这一下任务会落成"最终目录不存在且创建失败"。处置：这一层不另建，内容落进父任务那一层里，
  并在扫描日志里写一句说明（⛔ 绝不静默）。正常包（`333.7z` → 层名 `333`）永远不命中这条。
- 实现只有两处、互为补充：
  `OneClickCoordinator.ResolveContinuationOutputDirectory`（怎么拼那一层 + 防重复）、
  `OneClickCoordinator.ShouldAddContinuationLevelLayer`（该不该加那一层，唯一判据）；
  "定稿要不要再套包名层"读**路径本身**这一个事实
  （`ExtractionCoordinator.IsContinuationLayerAlreadyInPath`：落点最后一段就是本层包基名 → 已带层、不再套）。
  ⚠ 判据里的"父任务自己产出了内容物"读的是 **`ArchiveTask.ContentFileCount`（定稿搬出去的内容物文件数）**，
  ⛔ **不是** `ContentDirectoryPath` —— 后者是"内容物那一层在哪"，只出过程物的那一层也算成落点目录本身，
  拿它当判据会把简洁档判成忠实档（端到端用例当场逮到过，见 §3.3.1 的测试说明）。
- 其余物照旧：每一层的 `其余物` 在**那一层自己的目录**里（忠实档：`111\222\333\其余物\`；
  简洁档的过路层没有自己的目录，就并进父任务那一层）。

### 3.4 源包处理 + 删除操作（2026-09-22 拍板；**2026-09-25 第 32 条按用户口述重做成两档组合**）

> ⚠ 这一节是**不变量 1（默认不改源文件）的例外**，而且例外范围被用户显式限定为
> "**一键处理 / 手动「只解压」** + `SourceHandling = MoveToRest`（+ 要删的话再叠 `RestHandlingAfterVerify`）"。
>
> ⚠ **例外有两条，不是一条**：① 上面这条（搬进 `其余物`，**默认档不会发生**）；
> ② §3.4.2 的「空间不足」**运行期覆盖** —— 那一档在定稿 + 校验通过时**当场永久删除源包**
> （不进回收站、也不进 `其余物`，`ViewModels/ExtractionCoordinator.PurgeLayerSourcePackage`
> （`LayerPurgeTrigger.SpaceTight`）→ `Extraction/SourceCleanupService`）。两条都要求同样四条前提，
> 失败 / 部分完成 / 取消一律一个字节都不动。⚠ 2026-10-03 起这条删法还要多过一道**「半套分卷」闸门**
> （`Extraction/RestVolumeCompletenessGate.DescribeLayerReclaimBlocker`：同组还有一片留在成品目录树里
> ⇒ 一个字节都不删）。
>
> 用户 2026-09-25 原话（唯一需求来源）：「首先分 **1.源包操作**（1_原来的位置不动，2_放入其余物当中）、
> **2.删除操作**（1_不动其余物，2_动，但是只删除在回收站的位置，3_动，而且是彻底删除，直接节约空间）」，
> 且"**默认是源包原来位置不动和其余物不动**"；手动档"就和选项卡里面的一致"。

- **两个设置项**（都是字符串存枚举名，解析容错在 `AppSettings` 一处）：

| 设置项 | 值 | 默认 |
|---|---|---|
| `SourceHandling`（1 源包操作） | `KeepInPlace` 原来的位置不动 / `MoveToRest` 放入其余物当中 | **`KeepInPlace`** |
| `RestHandlingAfterVerify`（2 删除操作） | `Keep` 不动其余物 / `RecycleBin` 只进回收站 / `Delete` 彻底删除 | **`Keep`** |

- ⛔ 旧的第三档 `DeleteAfterVerify` **退役**；旧值在 `Normalize` 里迁移成
  "放入其余物 + 移入回收站"。`ParseSourceHandling` 读不懂时**回落 `KeepInPlace`**
  （兜底只能落在"什么都不做"上 —— 这一档是不可逆的）。
- **两条路径行为一致**（用户 2026-09-22 二次拍板 + 2026-09-25 第 32 条再次确认）：
  **一键处理**与**手动「只解压」**读**同一套**设置。
  代码上：`ExtractionCoordinator.StartExtractAsync`（地基）与 `StartExtractForOneClickAsync`（整理路径）
  **共用同一套源包处理**。
- **动源包的四个前提（缺一不可）**：① 内容物已定稿；② 输出校验通过；③ 未取消；④ 属于本任务分卷组。
  任何一个不成立 → 源包原地不动、`其余物` 不生成（**这条是红线，不变**）。
- **搬运规则**：整组一起移；同名冲突加 `(1)(2)`，**绝不覆盖**；
  跨盘走"**复制成功后再删原件**"（复制失败源包一个字节都不动，绝不"先删后移"）；每次搬运写日志（从哪到哪 + 大小）。
- **搬不动时**（只读 / 被占用）：任务标「**部分完成**」并写明"内容物已好，源包未能移入其余物"，
  **内容物结论不受影响**（产物、校验、归集都照旧）。
- **搬完要回写任务路径**：`task.CurrentPath` / `VolumePaths` 改到新位置 ——
  一键处理的续解扫描靠它把"刚搬走的源包"排除掉，否则源包会被当成新的内层包再解一遍（内容物凭空多一份）。
- 续解出来的**内层包**不参与源包处理：它的"源文件"是我们自己产出的中间件，已经在其余物里了。

#### 3.4.1 「删除操作」那一档什么时候动手（第 32 条落地的关键）

- **唯一执行体** `Storage/RestItemPurger.Purge`，五道门槛缺一不可
  （机器终态 = 完成 + 输出校验通过 + 未取消 + 路径是**定稿时记下的那一条** + 在自己的输出根之内且形状是 `其余物`）。
- **一键处理留到整条续解链跑完**（`CompleteRootSourcePackagesAfterChainAsync` → `ApplyRestHandlingAfterChainAsync`）：
  任务收尾那一刻 `其余物` 里躺着的正是下一层要解的内层包，当场删会把链断掉（实测 `ContinuationLayers` 掉成 0）。
  ⛔ 批级档位必须**活到这一批自己的链尾钩子跑完**（曾经在批次 `finally` 里清回 `Keep` → 静默降级）。
- **手动「只解压」是单层路径**：当场按档处理。
- **必须说清**：批首一条（本批怎么处理）+ 每任务收尾一条（保留 / 回收站 / 彻底删除，含路径与条目数 / 释放字节）。

#### 3.4.2 「空间不足」模式的**运行期覆盖**（用户 2026-09-27 拍板；⛔ 不改上面那两个设置）

> 这一节是 §3.4 的一个**只作用于一次运行**的例外：设置里的两档一个字都不改，
> 但**这一批**按另一套跑。判据出口只有一处：`ExtractionCoordinator._spaceTightThisBatch`
> （批首从 `MainViewModel.SpaceTightMode` 钉死，批尾清掉），它同时管四件事：

| 被覆盖的东西 | 这一批按什么跑 |
|---|---|
| 并发档（`MaxParallelExtractCount`）与 `RunAtFullSpeed` | **都不生效**：数量由 `ExtractionScheduler.ResolveSpaceTightParallelCount` 算（体积相近的小包 ≥5 → 5，其余 → 3；再与空间建议取小；取不到可用空间 → 1） |
| 执行顺序 | 按**净占用**（`TaskSpaceEstimate.NetOccupancyBytes` = 内容物）从小到大（`ExtractionScheduler.Build` 的 `sortKey` 参数）。⚠ **只改顺序**：`FitsAlone` / 空间门仍按**峰值** |
| 源包（`SourceHandling`） | **每一层**定稿 + 校验通过 → **立刻永久删除那一层的源包**，**不进其余物**（同盘搬运回收不了空间 = 等于这个模式什么都没省）。最外层 = 用户给的包，续解层 = 上一层交出来的内层包（2026-09-29 第 1 条：四层链的峰值因此是"当前层 + 下一层"，不是"四倍单层"）。执行体 = `Extraction.SourceCleanupService`（项目里唯一会删用户源文件的那一处；**2026-10-03 起它在管线上有两个调用点**，都由 `ExtractionCoordinator.PurgeLayerSourcePackage` 承载：本模式的 `LayerPurgeTrigger.SpaceTight` 与**普通档「删除操作 = 彻底删除」的 `LayerPurgeTrigger.LayerReclaim`**），门槛：定稿成功 + 校验通过 + 未取消 + 可证完整 + **「半套分卷」那道闸门**（`RestVolumeCompletenessGate.DescribeLayerReclaimBlocker`）+ 清单只来自任务自身 |
| 其余物（`RestHandlingAfterVerify`） | 强制 `Delete`（`PrepareRestHandlingForBatch` 里覆盖）—— 管的是**过程物**：它在链尾按既有口径删 |
| 多层 + 空间小的提前预警 | 见 `Storage/MultiLayerSpaceRiskRules`：本批允许解多层且各包需求之和超过可用空间时，批首 WARN + 一键确认框 `NoticeEcho` 各写同一句话（`StatusText.MultiLayerSpaceRiskFormat`）；⛔ 只是提醒，不拦任务、不改设置 |
| 中途撞上空间不足 | 那一单**不启动**（状态「磁盘空间不足」，一个字节都不动），整批照跑；一键档弹**一次**纯提示（`DialogService.ShowSpaceBlockedNotice` → 非模态 `Show()`，不阻塞后续任务；`_spaceBlockedNoticeShown` 一批一次），手动档只写日志 |

- 覆盖必须**被说出来**（用户最恨"我以为它按默认跑的"）：批首一条 WARN +
  一键处理确认框里一条红字（`StatusText.SpaceTightConfirmText`，正文那两行也换成覆盖后的值）+
  ②③页各一条橙色提示（`StatusText.SpaceTightOverrideNotice`）。
- **失败 / 部分完成 / 校验不过 / 取消 → 一个字节都不删**（不变量 1 的红线不随模式放松）。
  ⚠ **某一层失败只影响那一层**（2026-09-29 第 4 条）：失败那一层的源包留着，**已经收走的更外层不回滚**
  —— 用户明确接受这一点（"原包是已经没有了但是留下的不会破，他有可能是第二层或者第三层"），
  ⛔ 别把它当成 bug 去"修"。用例 `ChainSpaceReclaimTests`。
- ⚠ 与 §3.4 那个"第一层只出过程物时留到链尾补搬"的差别：这一档**当场就删** ——
  安全性来自同一个事实：那一刻内层包已经完整落在其余物里，续解从头到尾都不需要再碰源包。

### 3.5 特定解压例外档（用户 2026-09-24 第 24 条，**同一张判定表的例外**）

> 用户原话：「假如 `222\` 里面有 100 个 .rar 压缩包，而且每个压缩包里面又压缩了两次，
> 如果按照之前的方式是这样的 `222\1111\内容物最近的一层文件夹\内容物`，这种情况就不符合我想要做到的情况，
> **我想要的是这种 `222\1111\内容物`**，……所以这种可能就要单独出一个多相同文件的解压方式」。
>
> 他第 22 条的红线：「为了防止弄混乱文件夹，**内容物外面必须套一层文件夹**」——
> 两条同时成立的做法是：**包名那一层永远保留**（`222\1111\`），本例外档只动**包名层里面**再套的那一层。

**它是什么**：②「解压方式」页新增的一栏，**按注册表渲染**的一组可加规则
（`Extraction/SpecialExtractionRules.cs` + ①页的总开关 `AppSettings.UseSpecialExtraction`）。
第一条规则 Id = `SingleContentLayer`（「每个包只留一层内容」），默认勾上。
**关掉总开关 = 与没有这个功能逐字相同**（规则清单里写着什么都不参与运算）。

**两条路径（源包 `111\222.rar`，落点 `destDir = 111\222`）**：

```
规则关（判定表 3/4 的老行为）        规则开（本例外档）
111\222\内容文件夹\内容物            111\222\内容物          ← 内容物直接落在包名那一层里
111\222\内容文件夹\其它东西          111\222\其它东西
111\222\其余物\222.rar               111\222\其余物\222.rar  ← 其余物位置一个字不变
```

⛔ **两条都不会出现 `111\内容物`**：`destDir` 由 §1 算出，本例外档**没有任何改 `destDir` 的权力**
（反向断言在 `SpecialExtractionTests` 与 `SpecialExtractionPipelineTests` 里各钉了一条）。

**什么时候才塌（判据）**：包内**只有一条单链** —— 最里面那一层**并列的文件夹个数 ≤ 1**
（纯空壳目录不算分支，`AnalyzeContent` 早就摘掉了）。等价说法（用户的话）："只有一个内容文件夹
（可再套多层单链），或只有内容文件、没有并列的多个文件夹"。

**什么时候**不塌（每条都写一条 WARN 说清原因，**绝不静默**）：

| # | 不塌的理由 | 为什么 |
|---|---|---|
| 1 | 总开关关着 / 这条规则没开 | 根本走不到这里；行为必须与以前逐字相同 |
| 2 | 包内有**两个及以上并列的文件夹** | 再去掉一层就分不清哪个才是内容物 —— 保守套一层，宁可多一层 |
| 3 | 落点是**同一次导入里多个包共用**的（旧"添加文件夹 + 指定位置"那一档 `BBB\222\`） | ⚠ **2026-09-27 起这一档不再存在**（每包一个目录，`SharesDestinationWithOtherPackages` 恒 false）—— 判据与 WARN 留着当兜底，不会有包命中 |

**冲突口径不变**：同名仍按设置里的冲突档处理，**默认自动改名（`名字(1)`），绝不覆盖**（不变量 3）。
⚠ 2026-09-27 起"塌缩之后撞名"这个组合没有了（塌缩退役、续解每层各占一层），
但定稿搬运的同名冲突照样按冲突档走 —— `ConflictAskTests` 里那几条（定稿阶段询问 / 取消 /
无 UI 宿主降级）现在走的是**手动档「解压到当前文件夹」**那条落点。

**可追溯**：日志一条 `特定解压 —— <规则名>`；定稿结论在规则真的生效时改成
"特定解压「X」生效：不再套那一层，内容物直接落在 …"（不许再报判定表 3/4 那句话——它与实际落法相反）；
`task.RunOptionsNote` 追加同一句（失败清单第二级与「复制任务信息」都读它）；
一键处理的确认框正文里多一行「特定解压：<规则名>」。

**以后加规则**：加一条描述（注册表）+ 一个效果（`SpecialExtractionEffect` 与 `ResolveEffect` 的分派）
+ 它的实现（管线）—— **界面骨架一个字都不用动**（①页开关、②页那一栏都只认注册表）。

## 4. 地基（用户强调："一定不能少"）- **WinRAR 式基础解压必须始终可用**：选一个包 → 解压到同名子文件夹 → 完事。这条路径不得被"智能整理"挡住或变慢。
- **地基路径也按同一套源包规则**（手动「只解压」按钮走的就是它）：读的是 ③页那两档（§3.4），
  默认 `KeepInPlace` **一个字节都不搬**；选了"放入其余物"才搬，失败了 / 取消了原地不动。
  这是不变量 1 的例外**之内**（§3.4）。
- 增强项（定稿整理、其余物集中、源包搬运、自动续解）都必须是**可关的**，关掉后行为 == 传统解压器。
- 默认值取"最不意外"：`PerArchiveSubfolder`（同名子文件夹）+ 终端落法固定 `KeepLastFolder`
  + 续解中间层**不省**（忠实档）+ 其余物集中**开**
  + 源包操作 **`KeepInPlace`** + 删除操作 **`Keep`**（2026-09-25 第 32 条用户拍板的两个默认档）。

## 5. 空文件夹清理（原 `删除空文件夹.bat`）
- 规则：删除"**任意层级都没有文件**"的目录（只剩空目录树的目录）；只要任意层级有文件就保留（与原 bat 一致）。
- 默认**关**；执行前二次确认；**移入回收站**；删除前写日志。
- 作用于"本次任务的目标根目录"内，**禁止越出**（走 `ArchivePathGuard.IsInsideRoot`）。
- 与其余物清理是两个独立动作，不得合并成一个开关。

## 6. 不变量（本模型新增/强调）
1. 暂存期间不往源目录写任何东西。2. 定稿前 `destDir` 不得出现半成品。
3. 其余物只允许出现在 §3.2 表格里的那一处（包自己目录下的 `其余物\`；旧"共用根"那一档已退役）。
4. 彻底删除必须红色标识 + 二次确认 + 写日志；回收站不可用时不删。
5. 基础解压路径（同名子文件夹）永远可用且是默认；它的**源包处理与整理路径同一套规则**（§3.4）。
6. 输出根解析只有一处实现（`OutputPlacement`）、其余物落点只有一处实现（`ProcessArtifactLayout`），
   禁止在别处再拼路径。
7. 源包只有在"定稿 + 校验通过 + 未取消 + 属于本任务分卷组"四条同时成立时才可能被移动/删除（§3.4）。
8. **任何"修复 / 重建"产物必须另存为新文件、绝不覆盖原件**（通用原则，来自 `docs/WinRAR功能参考.md` §2 J 组）：
   将来真做"修包 / 重建索引 / 换封装"这类动作时，产物一律落到**新文件**（同名冲突加 `(1)`），
   原件一个字节都不动 —— 与我们"失败时源包原地不动"（§3.4）是同一个价值观：
   宁可多一个文件让用户自己比，也绝不接受"原件被程序改坏了"。这条同样约束第二引擎（`docs/引擎与外部工具.md`）。

## 8. 已定位的历史根因（来自 bat + 旧代码考古）

1. **"分卷被解压到外面、多弄了四个文件夹"**：
   - 旧 `FileNameHelper.GetArchiveBaseName` 只去**最后一个**后缀 → `a.7z.001` → `a.7z`、`001.part1.rar` → `001.part1`；
   - 旧 `ArchiveDetectService` / `FileScanService` **通篇没有分卷组概念**（一卷 = 一个任务），
     于是每个分卷各自解压、各自建目录。
   - **当前仓库仍有前半段**：`GetArchiveBaseName` 只处理 `.tar.gz/.tar.bz2/.tar.xz`，其余只去最后一个后缀。
     **证据**：2026-09-21 端到端产物里出现的目录就是 `17274362.7z\岳母交换计划 1.mp4`（应为 `17274362\`）。
   - 修法：`OutputPlacement.ResolveArchiveBaseName` 成为唯一实现；`FileNameHelper.GetArchiveBaseName` 改为转调或补上分卷后缀处理（由 R2/R3 的负责人接线）。
2. **"四个文件夹"的后半段**：续解把内层包当成**独立任务**、各自拿自己的输出目录 →
   必须合并成"一个源包 = 一个最终目录"（§2.2 / R3）。
3. **`ExtractionWorkspace` 已有 90%**：`layer-NNN/output`、`Publish`、`Cleanup`、`WriteReport` 都在，
   缺的只是 `final/` 与 `process/` 两个子目录 —— 阶段化改造优先复用它，不要另造工作区。
4. **回收站 API**：`Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile/DeleteDirectory`
   （`RecycleOption.SendToRecycleBin`）与 `SHFileOperation` P/Invoke 都不是 NuGet 依赖，两种都可行；
   实现时按"能测、失败可降级"选一种，并在 README 的已知限制里写明网络盘/策略禁用时不可用。

## 9. 一键处理的"本次选项"面板（**已实现**，来自 `docs/WinRAR功能参考.md` 采纳项 B12/B13）

用户诉求的由来：WinRAR 把"解压到"做成**每次操作可临时选**的运行期选项，而我们只能进设置里改——
**逼用户"进设置 → 改 → 回来"是最典型的冗余操作**，而落点恰恰是最常需要临时改的一项。

### 9.1 面板内容
点「一键处理」时，**先弹一次**这个框 —— 标题是 `StatusText.OneClickConfirmTitle` =「**一键处理 · 确认**」
（⚠ 旧面板叫「一键处理 · 本次选项」，那个名字已经不用了）。
正文只回答用户点名的那两件事（内容物落点 / 其余物怎么处理），要改才展开**默认收起**的折叠区
`StatusText.OneClickConfirmExpanderHeader`：「**本次改一下（落点 / 源包操作 / 删除操作）**」，里面**三组**：

| 分组（XAML `GroupBox.Header`） | 项 | 默认值 | 语义 |
|---|---|---|---|
| （正文之外，折叠区第一组）「本次落点」 | 「以包名命名的子文件夹（默认）」 / 「解压到指定位置，并建立同名子文件夹」（二选一） | 取设置里的当前值 | **只在本次生效**，不写回设置 |
| 「指定位置」 | 一个路径框 + 「浏览…」 | 取设置里的当前值 | 只对上面那一档「解压到指定位置」生效 |
| 「1 源包操作（成功之后，源包放哪）」 | 「原来的位置不动（默认）」（副行：程序一个字节都不碰你的源包） / 「放入其余物当中」（副行：成功 + 校验通过之后才搬；失败 / 取消一律原地不动） | 取设置里的当前值 | 与 ③页「1 源包操作」同一档、同一个值（§3.4） |
| 「2 删除操作（成品目录里的「其余物」怎么办）」 | 「不动其余物（默认）」 / 「移入回收站（可还原；空间要等清空回收站才释放）」 / 「彻底删除，直接省空间」（红字） | 取设置里的当前值 | 选「彻底删除」时下面挂一条**关不掉**的红提示（`RestDeleteNotice`：彻底删除不可恢复……失败 / 部分完成 / 取消的任务一个字节都不删） |
| ☐「把本次选择存为默认（写入设置文件，下次启动仍是它）」 | 勾选框 | 不勾 | 勾上才写回 `appsettings.json` |
| ☐「以后不再询问，按当前设置直接开始（可在「解压方式」页再打开）」 | 勾选框 | 不勾 | 写进设置 `AppSettings.SkipOneClickConfirm`；要去②页把「一键处理前不再弹确认框（直接按当前设置开始）」取消勾选才恢复弹框 |

> ⚠ 2026-09-27 起面板里**没有"终端落法"**那一项了（用户把那一档整个删掉，落法固定，见 §3.1）；
> "续解中间层省不省"在②页（**不在**这个面板里 —— 它是设置项，不是每次运行的临时覆盖）。

### 9.2 硬要求
1. **值只有一处解析**：面板产出的"本次落点"必须仍经 `OutputPlacement` 唯一实现；
   面板只是把用户的选择**临时覆盖**当前运行的设置快照，**不得**在别处再拼一次路径（§6 不变量 6）。
2. **不写回、不污染**：不勾"存为默认"时，`appsettings.json` **一个字节都不许改**（有测试钉住）。
3. **批只问一次**：一次一键处理只弹一次（50–200 个包的场景不容许逐个问，与 D-4 一致）。
4. **无 UI 宿主不弹窗不死等**：直接取设置值继续（降级路径必须有测试）。
5. **不改变默认行为**：默认档 = 与现在完全一致（落点取设置值 + 终端落法固定档 + 源包原地不动）；
   关掉面板（勾"不再询问"）后的行为也必须是"按设置走"。
6. **可追溯**：本次实际用的落点要写进日志与任务详情（用户要能回答"这次为什么解到这里"）。

## 红线（用户 2026-09-30 真机）：**最少两层文件夹，两层都不许省**

- **最外层 = 以包名命名的目录**（保证里面的续解/中间产物不会散到上一层去）；
- **最里层 = 以"最后一个压缩包"那一层命名的目录**（保证内容物不会直接摊在包名目录下）。
- ⛔ **不许**把内容物（`P`、`V` 这种子文件夹或一堆文件）直接搬到包名目录下 ——
  判定表里那些"塌缩 / 不套层 / 提上来"的分支**一律不许吃掉最里层**。
- 现场（`26081118.7z`）：包里是 `小小绘 推特大合集`（内层包）→ 解出
  `T 小小绘 推特大合集 330P+454V-9.31G\P|V`，定稿却把 `T …` 那一层塌掉、只留 `P`、`V`
  直接躺在 `…\26081118\` 下 —— 用户原话："最外一层和最里面一层的文件夹都不能省"。
