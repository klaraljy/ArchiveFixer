## 1. 它做什么（一句话）

把**一个文件夹**（或**一个文件**）变成一个**带密码的压缩包**：里面的内容是"这份东西的 7z 加密分卷"。

```
1111\（用户选的源文件夹）                     111.mp4（用户选的单文件）
      │ ① 7z 加密分卷（-mhe=on：连文件名一起加密）      │ 0) 旁边建同名文件夹，把文件硬链接进去
      ▼                                              ▼
1111(1)\1111.7z.001、.002、…                 111(1)\111.7z.001、.002、…
      │ ② 装分卷的文件夹（**其余物**，默认删掉）        │
      ▼
1111.rar（最终产物；本机没装 WinRAR 时是 1111.7z）  ← ③ 外层容器压一层（带密码、连文件名一起加密）
```

**统一流程**（他 2026-09-26 口述，本文件的全部设计都以它为准；⚠ 落点那一步当天**追加改过口径**）：

```
① 选一个文件夹 —— 或者选一个文件
② 填密码：两层一样就填一个框（默认）；不一样才出现「第一层」「最外层」两个框
③ 在**页面上**选「最终压缩包放在哪」：**默认（源旁边）** / 指定位置
④ 点「打包…」→ 弹一个小窗：**只确认**原包操作 + 其余物操作（落点只显示、不能在这里改）
⑤ 确认之后才开始干活 —— 取消 = 服务一次都没调、盘上什么都没多
⑥ 干完：只剩一个压缩包（其余物按你选的档处理，默认删掉）
```

> ⚠ **2026-09-26 追加改口径**（用户原话："**选择还是得放在页面**"、"**默认放在源文件目录旁边**"）：
> 原来"本地 / 指定位置"的单选在**弹窗**里，他打开⑤页时问"怎么没有文件指定的压缩位置" ——
> 现在落点的**选择**挪到⑤页（单选 + 目录框 +「选择…」），弹窗那一块变成**只显示**
> （显示的是页面上选好的那个目录）。
> 默认那一档 = **源文件所在的那个目录（源旁边）** —— ⛔ **不跟①页「输出位置」**
> （中间按"跟输出位置"做过一版，他明确纠正为源旁边；`PackingTargetMode` 只有
> `Local`（默认=源旁边）/ `Custom`）。

两层加密是**用户明确要求**的：外层容器是"运输容器"，内层 7z 分卷是"内容 + 分卷"。

## 2. 分卷：**按卷数**（用户 2026-09-26 拍板的 (B) 方案）

| 内容大小 | 目标卷数 | 每卷上限 |
|---|---|---|
| &lt; 1 GiB | **2** | ⌈内容 ÷ 2⌉ **向上取整到整 MiB** |
| ≥ 1 GiB | **3** | ⌈内容 ÷ 3⌉ **向上取整到整 MiB**（夹在 1 MiB – 16 GiB） |

实现 = `Packing/PackingOptions.cs` 的 `PackingVolumeRule`（纯计算，可测）。

- ⛔ **不承诺"平均分成几卷"** —— 用户原话："**这个可以，但不一定是要平均分成，我记得 7z 这个不是平均分成的**"。
  他记得对：`7z -v<大小>` 的行为是**每卷装满到上限、最后一卷拿余数**（本机实测：1 MiB 分卷 →
  `.001` 正好 1,048,576 字节 + `.002` 是零头）。所以"目标卷数"是**上限**：
  内容能压缩时成品更小，实际可能切出**更少**的卷（更小是好事，不是出错）。
- 日志里**两个数都写**（目标 N 卷 / 实际 M 卷），⛔ 不假装实际就是目标数。
- 1 GiB 那条夹取（16 GiB 上限）是为了 FAT32 那类单文件 4 GiB 的文件系统与"内容极大时别切出几十 GiB 的单卷"；
  夹了之后**卷数会多于目标卷数**，这一点由 `Describe` 如实说出来。
- ⛔ 上一版"512 MiB 上限 + 界面上填 MiB"那一套**退役**：它按体积猜卷数，而他要的是
  "**小包两卷、大包三卷**"这个直观形状（这也是他 2026-09-22 举的两个例子）。

## 3. 密码（必填；两层默认同一个）

- **必填**：空密码 / 只有空格 → **拒绝开始**并说清"必须设密码"（用户原话："密码必须有"）。
- 默认**两层同一个密码**（界面上就一个框）；勾「两层用不同的密码」才出现
  「第一层」与「最外层」两个框，**两个框都能从密码列表里挑**（`PasswordPickerWindow`）。
- ⛔ 不再要"确认密码"第二遍（2026-09-26 删掉）：那是防手滑的旧习惯，而他真正要的是"能复用密码本里的密码"。
- **绝不落盘**：密码只在内存里活到本次打包结束（不变量 5 —— 密码只存内存）。
  日志里一律写"已设置密码"，**不写密码本身**，也不写 `-p<明文>` / `-hp<明文>`（命令行里会带上，
  这是外部工具命令行的固有限制 → 与解压侧同一口径写进「已知限制」）。
- 打包结束后界面上提供"复制密码"按钮（用户自己也要用）。

## 4. 落点与命名（**以源名为准**）

| 项 | 规则 |
|---|---|
| 源 | 一个**文件夹**（打它里面的东西）或一个**文件**（在旁边建同名文件夹，硬链接进去） |
| 落点 | **本地**（默认）= 源**旁边**那一个目录；或**指定位置**（弹窗里挑一个目录） |
| 装分卷的文件夹（其余物） | 落点目录下 `源名`（`1111`）；撞名 → `1111(1)`、`1111(2)`… |
| 分卷 | `其余物\源名.7z.001`、`.002`… |
| 最终产物 | **永远** `源名.rar`（`1111.rar`）；撞名 → `1111(1).rar`；本机没 `Rar.exe` 时是 `源名.7z` |
| 其余物 | 装分卷的文件夹（**单文件时还有那个新建的同名文件夹**）—— 默认**彻底删除**（§6） |

- ⛔ 旧版的 `源名_打包` 后缀**取消**（"最终的还是以源文件夹的名字来"）。
  装分卷的文件夹之所以要让位成 `1111(1)`，正是为了**不与源文件夹撞名**
  （他原话："如果用户选择不操作原包，那就是 `1111(1)` 文件夹"）——
  撞名的后果是分卷落进**正在打包的源文件夹**里，越打越多。
  单文件时那个 wrapper（`111`）也是"马上要建、现在还不存在"的一个保留名，同样参与让位。
- 判据只看**磁盘上有没有**同名文件/文件夹（`PackingNaming`），⛔ 绝不覆盖任何已有文件。
- ⛔ **绝不在源目录里"顺手"写东西**：分卷只写进"其余物"那个文件夹；本地档下它与源**同级**，
  单文件档下 wrapper 会临时出现在源的旁边（这是"把文件装进文件夹"的必要步骤，弹窗里逐字写明）。

## 5. 外部工具：7z 一定在；`Rar.exe` 有就用，没有就**自动 7z**

| 干什么 | 用什么 | 拿不到时 |
|---|---|---|
| 建 7z 加密分卷（一定会有） | 内置 `tools\7zip\7z.exe`（LGPL，**随程序分发**） | 理论上不会没有；确实缺 → 报"没找到 7-Zip 程序"，并提示改设置或重新解压一份程序 |
| 外层容器 = **rar** | **`Rar.exe`**（WinRAR 的命令行程序，共享软件）—— 只检测、只调用、**绝不分发**（AGENTS.md §3.1） | **自动改用 7z 外层**（产物 `源名.7z`），日志 / 结果 / 弹窗**都如实写明**"本机没有 `Rar.exe`" |
| 外层容器 = **7z**（自动回落的那一档） | 同上那个内置 `7z.exe` | 同上 |

> ⚠ **2026-09-26 改口径**：上一版是"选了 rar 而没有 `Rar.exe` → **明确报错 + 三条出路**"，
> 现在改成**自动用 7z**（他看完说明后拍板："**那就弄 7z 吧**"）。
> 理由：他机器上没装 WinRAR 是**常态**（§5.1 的许可边界），而他每次都要的其实是"**一个带密码的压缩包**"；
> 为后缀名把整件事卡住没有意义。

- ⛔ **绝不拿 7z 假装做出一个 `.rar`**：7-Zip **不能创建 RAR**（RAR 的压缩算法是专有的），
  把文件名改成 `.rar` 是**伪造**，用户拿去用时会直接坏掉。产物名**跟着实际容器走**（`.7z`），
  并且日志与结果区都写明"外层用 7z（本机没有 `Rar.exe`）"。
- ⛔ 也**不内置** `Rar.exe`（许可不允许随包分发，见 §5.1）。
- 定位沿用 `ToolLocator`（唯一来源）：`Rar.exe` 先找**用户自选路径**（**②「解压方式」页 → 引擎**里的那一格）
  → 再找已装 WinRAR 目录 → 都没有就走上表第二行（自动 7z）。
- `PackOuterContainer.None`（不做外层）**不再是用户可选的一档**：模型里还留着（历史 + 便于回退），
  但⑤页与本条流程都不会产生它 —— 结果只有一个压缩包，这是他要的形状。

命令行（三条都在实现里写死参数模板，**只允许出现在 `Packing/` 内部**，与 §3.1 的"四条禁止项"同一口径）：

```text
# ① 加密分卷（-mhe=on 连文件名一起加密；-v512m 分卷；输出到 B）
7z.exe a -t7z -mx=5 -mhe=on -bsp1 -sccUTF-8 -y -p<密码> -v512m "<B>\<A名>.7z" "<A>\*"

# ②a 外层 rar（-hp 连文件名一起加密；-r 递归；-ep1 保留 B 这一层）
Rar.exe a -hp<密码> -r -ep1 -y "<B>.rar" "<B>"

# ②b 外层 7z（-mhe=on 连文件名一起加密；参数给的是 B 而不是 B\*：7z 会把 B 这一层带进归档）
7z.exe a -t7z -mhe=on -mx=5 -bsp1 -sccUTF-8 -y -p<密码> "<B>.7z" "<B>"

# ③ 校验（按容器走）
Rar.exe lb -p<密码> "<B>.rar"          # bare list：一行一个条目名
7z.exe  l -slt -sccUTF-8 -y -p<密码> "<B>.7z"   # 技术信息：一行一个「键 = 值」
```

> 为什么 7z 那一边用 `-slt` 而不是默认表格：默认输出是给人看的表格（列宽随内容变、带汇总行），
> 钉进代码等于把"某一版 7-Zip 的排版"当契约。`-slt` 的第一块描述**归档自己**，分隔线之后才是条目
> —— `PackingVerifier.ParseSevenZipSltList` 按分隔线切掉第一块，否则归档路径会被当成"计划外条目"，
> 产物校验会**永远不通过**（有单测钉住）。

### 5.1 许可依据：为什么 `Rar.exe` 不能随包，而"外层 7z"必须存在

用户 2026-09-23 问过"能不能随包发 `Rar.exe`（他不是商用、会完全开源）"。查 RARLAB 官方 EULA，**不能**：

| 条款 | 原文要点 |
|---|---|
| §3.1 | Nobody may distribute separate parts of the package, **with the exception of the UnRAR components**, without written permission |
| §3.2 / §3.3 | 不得放进任何其它软件包内；必须 pure and unpaired，**Any bundling is interdicted** |
| §10 | 不得分发 licensed software 的 **any subset**；也不得拿 RAR/UnRAR 二进制去重建 RAR 压缩算法 |

结论（边界不变）：`Rar.exe` / `WinRAR.exe` 只允许"**用户自装、自选路径、程序只检测与调用**"，
⛔ **绝不随包分发**；`UnRAR.exe`（RARLAB freeware，许可第 2 条明确允许随其它软件包分发）仍然可以内置。

正因如此，"本机没装 WinRAR"是**常态而不是异常**，所以外层容器必须有不依赖 WinRAR 的选项：
**7z 外层**（内置 7-Zip，LGPL）与**不做外层**。这不是"顺手加的功能"，
而是许可边界逼出来的产品决定。

## 6. 取消、失败、清理与"不变量"

| 情形 | 行为 |
|---|---|
| **取消确认弹窗** | **服务一次都没调**（`PackingUiFlowTests` 有红检），盘上**什么都没多** |
| 用户中途取消 | **杀掉自己启动的那个 PID 及其子进程**（绝不按名字杀 `7z.exe`/`Rar.exe`，不变量 10）；产物按下面"清理"那一条处理（外层没成就什么都不动） |
| ① 失败（切分卷） | 报错；已切出的分卷按设计保留（重试可能还要用），日志写明"分卷已生成、外层未生成" |
| ② 失败（外层） | 分卷保留（同上）；明确说外层没做成与原因（`7z` / `Rar.exe` 的退出码） |
| 成功 | 界面给出：**外层产物路径 + 容器类型 + 大小** + 分卷清单 + 清理结果；日志里同一条 |
| 校验 | 完成后**按实际容器**列一遍条目（`.rar` 用 `Rar.exe lb`，`.7z` 用 `7z l -slt`）：确认里面有"装分卷的文件夹"这一层且分卷数对得上；对不上就报"产物不对"，**不显示成功**（不变量 6 同一口径） |
| 空间 | 开始前算一次需求（内容 × 2.02 + 32 MiB 余量），与目标盘可用空间比；不够就**不开始**，报"需要/可用/差"（与解压侧同一套 `SpaceGate` 口径） |

### 6.1 原包 / 其余物：**只在外层容器生成 + 校验通过之后**才动（`Packing/PackingCleanup.cs`）
| 用户选的两档 | 默认 | 什么时候执行 |
|---|---|---|
| 原包操作 = 不动 / 移入其余物 | **不动** | 成功之后（"其实不动原包是对的"） |
| 其余物操作 = 不动 / 移回收站 / 彻底删除 | **彻底删除** | 成功之后（"其余物可以默认删掉，因为这个对用户来说一点用没有"） |

五道闸门（`PackingCleanup.Run(plan, succeeded, outerArtifactPath)`）：

1. **不是成功**（失败 / 取消）→ 一个字节都不动；
2. **没有外层产物** → "其余物"那一档**不执行**（那种情况下那里面装着这次唯一的结果）；
3. 要搬进其余物的原包**本来就在那个文件夹里** → 拒绝（`PackingPaths.IsInside` 判容器）；
4. 删除失败**只警告**（不把一次成功的打包翻成失败）；
5. 危险组合（原包移入其余物 **+** 其余物要删）→ 弹窗里**当场红字**：
   "这等于**连你的原文件夹/原文件一起彻底删除**"，并给出"只想留 `.rar` 就把原包操作改成不动"
   （`PackingRunOptions.WouldDeleteSource` / `SourceLossWarning`）。

> "不显示成功"这句在结论里是**机器可判**的：`PackingResult.State` 只有 `Succeeded` 算成功，
> 而 `Describe()` 一定带容器类型与**实际**产物路径（`rar 外层 → 1111.rar` / `7z 外层 → 1111.7z`），
> 用户不会看到一个光秃秃的"完成"。

### 7.2 确认弹窗（`Views/PackingConfirmWindow.xaml`，点「打包」才出现）

| 区块 | 内容 |
|---|---|

### 7.3 弹窗的三条"不许撒谎"铁律（2026-09-26 收尾自查补上）

1. **那句"最终产物"必须是 `rar` 还是 `7z` 由实际容器决定** —— 没装 `Rar.exe` 时是 `.7z`。
   这个结论只有一处计算：`Packing/PackingOptions.cs` 的 `PackingOuterContainerResolver`
   （`PackingService` 与 `PackingViewModel.EffectiveOuterContainer` 引的是同一份）。
   ⛔ 以前服务内部自己算、界面按"请求里那个"写，于是没装 WinRAR 的机器上弹窗写着 `1111.rar`、
   跑完却得到 `1111.7z`（典型的"界面撒谎"，第 36/45 条那一类）。
2. **那句"最终产物"要跟着落点实时重算**：用户在弹窗里改成「指定位置」之后，
   抬头那行立刻换成那个目录里的路径（`PackingConfirmRequest.BuildHeadLines(options)`，
   与规划层共用 `PackingPaths.ResolveTargetDirectory` + `PackingNaming.ResolveUniqueFilePath`）。
3. **确认之前不建任何目录**：落点合法性先判（含"落点在源文件夹里面"这种当场拦下），
   目标目录由 `PackingService` 在**校验通过之后**建（`Directory.CreateDirectory` 会连父级一起建）。
   ⛔ 原来弹窗里先 `CreateDirectory` 再校验 —— 落点非法时会在源目录里留一个我们造的空壳。

## 8. 不做（明确写下来，免得被"顺手加上"）

- 不做 zip/7z 之外的格式选择、不做恢复记录、不做固实块调优、不做**多源批量打包**（一次一个源）
- 不做"分卷大小按目标网盘限制自动选"（没有联网功能）；⛔ 也不做"平均分成 N 卷"（§2：`7z -v` 不是那么切的）
- 不做打包历史 / 模板 / 计划任务
- 不做 `PackOuterContainer.None`（不做外层）的界面入口 —— 模型里留着，流程不用它（§5）
- **不做"打包后自动删源"的默认档**：它现在是"原包操作 = 移入其余物 **+** 其余物操作 = 删除"这个**显式组合**
  （§6.1），⛔ 默认档下程序一个字节都不碰源
- 不做"既没 `Rar.exe` 也没内置 7-Zip 时还能出外层" —— 那种情况**当场说清并拒绝**
  （`PackingOuterContainerResolution.Impossible`，⑤页摘要与点「打包」都会拦住，⛔ 不许写成"不做外层、结果就是分卷"）

### 10.2 与设计稿的偏差（两处，都往"更保守"的方向）

### 11.4 收尾自查（"检查清楚"那一轮，2026-09-26）

用户让我"检查清楚还有什么没弄好的"，于是把**用户看得见的每一句话**与**程序真正会做的事**逐条对了一遍，
逮到 6 处"界面 / 日志撒谎"，逐条修掉（症状 / 根因 / 修法见 `docs/需求变更.md` §46 的"收尾自查"表）：

1. 没装 WinRAR 时弹窗与摘要写 `.rar`、实际产出 `.7z` → 唯一出口 `PackingOuterContainerResolver`（§7.3 第 1 条）；
2. 弹窗那句"最终产物"不跟着落点变 → 实时重算（§7.3 第 2 条）；
3. 弹窗先建目标目录再校验 → 确认之前不建，落点在源里面当场拦（§7.3 第 3 条）；
4. 旧模型文案（"B" / `_打包` / "外层 rar"）留在日志、失败清单、结果区 → 全部改成点名实际文件夹；
5. 既没 `Rar.exe` 也没 7-Zip 时界面说"结果就是分卷"、服务却失败 → `Impossible` 单独一档、点打包先拦；
6. 默认档（其余物已删）结果区仍写"分卷在 X、你可以自己删 X" → 按收尾结论分档说。

回归 = `PackingUiFlowTests` 5 → **10 条**；⛔ 红检实测（把结果区那句改回无条件拼上 → 立刻变红）。

**第 7 处（同一轮）**：打包以前**不打**"本次操作开始"这条标记（第 38 条那套：`LogService.MarkOperationStart`），

在**用户确认之后、调服务之前**触发一次，⛔ 取消时零次（两条用例钉住，红检实测）。
