# 「部分完成」也把内容放进目标目录：会撞上什么（方案与冲突分析）

> **这份文件是什么**：用户 2026-10-01 真机 `giu910`（19 GB 的 7z `-mhe`，解压到 98% 时**只有一个** mp4 的 CRC 失败，
> 557 个文件都好好的）之后，他问的两件事之一 ——
> 「**关于部分完成我们就要有很大的空间讨论了，因为我们现在目前所有的程序都没有考虑到部分解压的问题，
> 你找找看会有什么冲突的吗**」。
> 他当场定的口径：**现在不做**（「不用，要不然空间不好弄」）+「**这个东西记住，以后我们肯定会修改的**」。
> 所以这份文件**只是把冲突先摸清**，⛔ 不是实施计划，⛔ 也**不许**据此去放宽任何红线。

## 1. 这件事到底在说什么

现在这条路是**全有或全无**：

- 解压成功 **且** 结果校验通过 **且** 未取消 ⇒ 定稿发布 + 按设置处理源包（移入 `其余物` / 删除）；
- 只要有一样不成立（含"只有个别条目 CRC 失败"）⇒ **一个字节都不发布**：暂存目录整份删掉、源包原地不动。

`giu910` 那一单的代价就是：**13 分钟、17.7 GiB 已经解出来的内容，因为 1 个 mp4 的 CRC 失败而全部丢弃**。
"部分完成发布"要做的，是把"已经解出来、而且**每一条都通过了引擎自己的 CRC**"的那部分（557/558）
放进目标目录，同时**如实标成「部分完成」**。

## 2. 会撞上的冲突（逐条：现状判据 → 为什么冲突 → 要动什么）

### 2.1 发布闸门（不可逆路径的第一道）

- **现状**：定稿发布排在 **L4「可证完整」+ L5 复核通过** 之后（唯一出口 `Extraction/ResultCompleteness.cs`、
  `Extraction/ResultFinalizer.Plan`，见 `docs/检验等级.md`）。判不出完整性 ⇒ 不发布（`Undeterminable` ⇒ 什么都不做）。
- **冲突**：部分完成**在定义上就不可能"可证完整"**。要发布就得另开一条入口。
- **⛔ 不许这么改**：不允许把 L4 判据放宽成"差不多就行"——那等于把红线拆掉。
  **只能新增一条并列的、判据完全不同（也更窄）的入口**：它只证明"**已经落地的这些文件本身没坏**"，
  绝不去证明"整包完整"。

### 2.2 落点与套层规则

- **现状**：落点最少两层（最外层=包名目录、最里层=**最后一个内层包那一层**），唯一出口
  `Extraction/PackageLayerRules.cs` + `ResultFinalizer.Plan(..., suppressPackageFolderLayer:)`。
- **冲突**：部分完成时**那个内层包本身可能正是坏的/没解出来的那一个** ⇒ "最里层"判不出来 ⇒
  按现有规则要么报错、要么把最里层吃掉（而"吃掉最里层"是明令禁止的）。
- **要动什么**：部分完成的落点**不能走这条规则**，得有一个与它并列、且**固定不动既有规则**的落法（见 §3 口径 A）。

### 2.3 结果校验口径

- **现状**：`Extraction/OutputVerifier` 按"清单 vs 实际"（文件数 / 字节数）判完整，判否 ⇒ 整份计划作废。
- **冲突**：部分完成**必然**判"不完整" ⇒ 同一份判据不可能既当"能不能发布"的门、又当"完不完整"的报告。
- **要动什么**：部分发布只做**非空 + 落点校验**（现有那两道），发布之后**照样**如实写
  「无法确认完整性」（`StatusText.CompletenessUndeterminableFormat`），⛔ 不许让"发布了"读成"解压成功"。

### 2.4 终态与报告（三处必须同时改）

- **现状**：状态三处同步（`StatusText` + `StatusToBrushConverter` + `TaskSummaryService`）；终态唯一出口
  `Models/TaskOutcomeClassifier.cs`；批末色带 `BatchSummarySeverityRules`、批末诊断
  `BatchSummaryDiagnosticsRules`、一键那一行 `OneClickCoordinator.BuildSummaryLine` 都只读机器终态。
- **冲突**：`PartiallyCompleted` 这一档**已经存在**（多分支不展开 / 用户中断会用），但它的语义现在是
  "没做全、**盘上什么都没有**"；而新的部分是"没做全、**盘上已经有一大堆内容**"。
  ⇒ ①页/批末必须**说清内容在哪、缺的是什么**，否则用户看到「部分完成」会以为白跑了（这一单的现实就是"没白跑，98% 都在"）。
- **要动什么**：文案与诊断各加一档（仍走既有出口），⛔ 不新造第二套分类。

### 2.5 源包与其余物（红线）

- **现状**：**失败 / 部分完成 / 取消 ⇒ 源包原地不动、`其余物` 不生成**（不变量 1）。
- **冲突**：部分完成发布**不改变**这条 ✓，但会带出一个新问题：**已经建出来的过程物（其余物/工作区）怎么办**？
  现在"成功才处理"。部分完成若不处理，用户盘上就多留一份过程物 —— 这正是他自己说的「**要不然空间不好弄**」。
  ⇒ **用户 2026-10-02 定了口径：留"最外层源包 + 已解出的内容物"，其余物里其他项与工作区都删**（见 §6.1③）。

### 2.6 空间账（他点名的最大顾虑）

- **现状**：源包**不进"要从可用空间里新写多少"**（`TaskSpaceEstimate.FreeSpaceDemandBytes` =
  内容物 + 过程物，因为成功路径跑完会回收源包）；空间门的唯一出口是它（`SpaceGate` / `ReconcileReservation`）。
- **冲突（三处）**：
  1. **峰值变了**：成功路径"跑完就回收源包"，部分完成**不回收** ⇒ 峰值 = 源包 + 已解出的内容 + （若保留）过程物，
     比成功路径多一整个源包。⇒ 空间门的判据要不要按"部分完成也占着"算？**算的话会拦下本该能跑的任务**；
     **不算的话就可能中途写满**。
  2. **再跑一次同一包**：目标目录里已经躺着上一次的部分内容 ⇒ 引擎那边 `-aos`（已存在就跳过）、
     我们这边"绝不覆盖 + 让位"⇒ 会生成 `名字(1)` 这种副本，而且**再占一份空间**。
     而"再跑一次"恰恰是修好那个坏条目之后最自然的动作。
  3. **「空间不足」模式**：它靠"定稿 + 校验通过后当场永久删源包"回收空间；部分完成不满足这个条件 ⇒ 这一档的
     回收预期失效，`Storage/MultiLayerSpaceRiskRules` 的提醒数字（`Σ FreeSpaceDemandBytes`）也要跟着重新算。

### 2.7 续解链（多层包）

- **现状**：链尾收尾读**叶子层**清单（`Extraction/ChainManifestResolver.cs`），拿不到 ⇒ 如实「判不出」+ 点名哪一层；
  链尾闸门 `ChainCompletionGate` 决定能不能收其余物。
- **冲突**：部分完成的那一层里，**内层包可能只解了一半**（或那个内层包正是坏的）⇒"叶子层清单"取不到 ⇒
  现有裁决一路走"判不出"（什么都不做），部分完成发布就成了"发布了但什么都没收尾"。
- **要动什么**：链尾要新增一支"**部分完成**：内容已发布、过程物按 X 处理"的明确裁决，⛔ 不许静默不动（§11.6 的老规矩）。

### 2.8 同名冲突档

- **现状**：确认框里有"覆盖 / 跳过 / 自动改名"；「覆盖」的语义是"先移到临时名 → 再删 → 再落位"（不变量 3）。
- **冲突**：目标目录里那份同名内容**可能正是上一次部分完成的成果**；按「覆盖」语义会被**删掉**。
  部分完成这一档要不要**一律不许覆盖**（只让位）？我倾向：**部分完成发布永远只让位、绝不覆盖**（比成功路径更严）。

### 2.9 清理与删除（③页）

- **现状**：删除/回收只在成功且可证完整时发生；工作区失败即清（`KeepFailedWorkspace` 打开才留）。
- **冲突**：部分完成要不要保留工作区（现场）？保留 = 又多一份空间占用；不保留 = 用户拿不到"坏在哪个条目"之外的现场。

### 2.10 文案与用户预期

- 必须新增一类句子，且只走 `StatusText` 一处出口、用「」不用 Markdown（§9.3），至少说清三件事：
  **① 哪些内容已经放进去了；② 缺的是什么（哪个条目 / 多少字节 / 哪一条判据）；③ 源包没动、下一步该干什么。**

### 2.11 验收与红线（新增一支要连红线一起钉）

至少要新增这些守门用例：失败**仍然**不发布（红线）；部分完成**源包原地不动**（红线）；
部分发布**绝不覆盖**；**判不出完整性时**默认还是"什么都不做"（红线）；
L4 判据**一个字没放宽**（对照：合成一个"可证完整"的包，走老路）；空间账**不把源包算两遍**（§11.3 那条）。

### 2.12 阈值：什么样的"部分"才值得发布

557/558 当然值得。但 1/558 呢？没有一条阈值口径的话，"部分完成发布"会变成"什么都发布"。
候选口径（供拍板）：**清单读得出来** + **缺的条目数 ≤ N**（或**已解出的字节占比 ≥ X%**）+ **缺的条目能被点名**。

|---|---|---|---|
| **A（我推荐）** | 只发布到**独立子目录**：`<目标>\<包名>\部分完成\`（固定名字、不参与落点规则） | 不动落点/套层/校验任何既有判据；再跑一次**不会撞名**；用户一眼看得出这是"没做完的那一份" | 目录多一层；与"正常落点"不一致（但正是故意的） |

## 6. 用户 2026-10-02 追加的三个顾虑（当场定下的口径）

> 用户原话：「**有别的顾虑** 1.这种情况下，原包的删除操作是不是要统一保留
> 2.空间不足要和这个弄兼容吗，因为空间不足是比较危险的，空间不足，特别是空间不足加上大容量多相同文件一起开
> 3.这个的操作最少差不多就占了两份原包的空间要在开启界面详细写清楚」。

### 6.1 原包的删除：**统一保留，而且这是红线，不是可选项**

- 不变量 1 的原文就是：「**失败 / 部分完成 / 取消 ⇒ 源包原地不动、`其余物` 不生成**」——
  部分完成发布**一个字都不改这一条**。
- ⇒ 用户设的「源包操作 = 放入其余物 + 删除操作 = 彻底删除」在**部分完成这一单上不生效**，而且是**刻意的**：
  缺的那些文件**只存在源包里**，删掉等于把唯一一份完整数据删掉。
- 三条一起定，⛔ 不许只用其中一条：
  ① 源包**不搬也不删**；② **不生成**其余物；
  ③ ⚠ **用户 2026-10-02 当场改口径**（原话：「**我建议源包 + 已解出的内容物留着，其他的都删掉**」）：
  部分完成时 —— **留** = 本条链的**最外层源包** + 已解出并发布的内容物；
  **删** = 其余物里**除源包以外**的项（内层包等过程物）+ 这一单的工作区。
  ⇒ 盘上就是"两份"（源包 + 内容物），与 §6.3 那句承诺对得上。
  （我早先写的"链上已生成的其余物保留不动"与那句承诺**自相矛盾** —— 旧写法会让盘上多出第三份过程物，
  用户当场点出来了，**以用户这句为准**。）
  - ⛔ **安全闸门（这一条我来守，写死在判据里）**：**只有当"这条链的最外层源包还在盘上"时**，
    才清其余物里其他项；源包不在（已被删 / 路径失效）⇒ **一个字节都不删**（判不出 ⇒ 什么都不做）。
    理由：最外层源包是**唯一**能重建整条链的东西（内层包都能从它重新解出来）；
    它都不在了还清过程物，等于把最后一份可恢复路径也删掉。
- ⛔ 想改成"部分完成也删源包" = **改红线**，必须用户明确说；默认按上面办。

### 6.2 与「空间不足」模式：**不兼容 —— 空间不足模式开着时，部分发布强制不生效**

- 空间不足模式的**全部价值**就是"定稿 + 校验通过后当场永久删源包"回收空间（AGENTS §11.3）；
  而部分完成**天然回收不了源包**（见 6.1）⇒ 两者目的相反。
- 用户点名的危险组合：**空间不足 + 大容量 + 多份相同文件一起开** —— 每一份都可能留下
  "源包 + 内容物"两份、而且**一条都回收不了** ⇒ 中途写满的概率成倍放大。
- 口径（三条，一起做）：
  ① **硬互斥**：`SpaceTightMode` 开着时部分发布**不生效**（行为上当它没开），写一行 INFO 说明为什么；
  ⛔ **不偷偷改用户的设置**（勾还是勾着，只是这一轮不生效）。
  ② **空间账按"部分完成可能发生"算**：只要部分发布开着，`SpaceGate` 对每个任务的需求要加**一整个源包**
  （即 `FreeSpaceDemandBytes + 源包字节数`）—— 因为这一单跑完源包**还在盘上**，等于净新增占用。
  判据仍然只有一个出口（`Storage/TaskSpaceEstimate`），⛔ 不许在别处再算一遍。
  ⚠ 代价要说清：这样算会**拦下一些本来排得进的任务** —— 这正是"空间不足比较危险"该有的取向。
  ③ **发布前二次体检**：真要发布这一份之前**再探一次**可用空间；若发布会让剩余空间低于保留余量
  ⇒ **不发布**、源包原地不动、如实写一行（"空间不够，这一份先不发布"）。
  兜底永远落在"什么都不做"那一档。

### 6.4 盘上到底占几份（把"最多两份"这句承诺变成可核对的账）

| 情形 | 跑完之后盘上有什么 | 几份 |
|---|---|---|
| 成功 + 可证完整（老口径） | 内容物（源包按设置回收 / 删除） | **1 份** |
| **部分完成（新口径）** | **最外层源包（留）+ 已解出的内容物**（发布在 `<包名>\部分完成\`）；其余物里其他项与工作区都删 | **2 份** |
| 失败 / 取消（老口径，一个字不改） | 源包原地不动；什么都不发布 | **1 份** |

- 峰值那一刻（解压进行中）仍然是"源包 + 内容物 + 工作区中间件"，与今天**完全一样** ——
  部分完成**不改变峰值**，改变的是**跑完之后能不能回到 1 份**：成功路径回得去，部分完成回不去
  （所以 §6.2② 要求把源包算进空间账）。
- ⛔ 任何实现细节都不许让这张表多出第三份（"其余物也留着"就是第三份 —— 已被用户否掉）。
