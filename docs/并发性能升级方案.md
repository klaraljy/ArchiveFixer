# 并发性能升级方案（基于先例，不按单块盘调参）

> 状态：设计稿，待用户过目。当前代码：`1898c41`（吞吐版 AIMD，HDD/未知从 1 起步）。
> 依据：Envoy Adaptive Concurrency、Netflix concurrency-limits、SQL Server DOP feedback、.NET ThreadPool controller、7-Zip/robocopy 的线程事实。

---

## 0. 先例查到了什么（决定“应该干什么”）

### 0.1 Envoy Adaptive Concurrency（生产 HTTP 代理）

Envoy 不按 CPU 核数或机器型号定并发，而是**按延迟做闭环**：

- 周期性在**低并发**下测 `minRTT`（理想延迟）；
- 每个采样窗口汇总 `sampleRTT`（默认 p50，示例 p90）；
- `gradient = (minRTT + B) / sampleRTT`，`B = minRTT × buffer%`（默认 25%，容忍抖动）；
- `limit_new = gradient × limit_old + headroom`，`headroom` 固定为 `√limit`（防止 limit 停在过小值）；
- 有 `min/max concurrency`、`update_interval`、`minRTT` 重测间隔、**jitter**（默认 15%，防所有节点同时降档）；
- 并发降到最低连续 5 个窗口也会触发 minRTT 重测；minRTT 测量窗口会把并发压到 `min_concurrency`（默认 3）。

关键点：**用延迟梯度判断“再加并发有没有把系统压坏”**，不是只看总吞吐；固定常数（buffer、interval、min/max）是有的，但方向完全由测量决定。

来源：<https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/adaptive_concurrency_filter>

### 0.2 Netflix concurrency-limits（大规模微服务）

- 基本关系：`Limit = Average RPS × Average Latency`（Little's Law）；并发上限应由排队情况决定，而不是拍一个 RPS。
- **Vegas**：`queue = L × (1 − minRTT/sampleRTT)`；queue < alpha（2–3）就 +1，> beta（4–6）就 −1。
- **Gradient2**：长期/短期两个指数平均的背离度（divergence）识别排队趋势，趋势变坏时**激进降档**；解决 minRTT 基线漂移和突发流量。
- `BlockingAdaptiveExecutor` 会按测到的延迟**自动调整内部线程池大小**。
- 客户端可用 AIMD（丢包/失败驱动）或 delay-based。

来源：<https://github.com/Netflix/concurrency-limits>

### 0.3 SQL Server 2022 DOP feedback（数据库的“并发反馈”）

- 对**重复查询**按 `elapsed time` 与 `waits` 判断并行是否低效；
- 认为并行低效时，**主动把 DOP 调低**，下一次执行验证；
- 有性能回退就回到**上次已知好的 DOP**；用户取消也算回退；
- 只持久化验证过的反馈，且永远不会超过 `MAXDOP` 上限。

这是“**先试、验证、回退、记住**”最直接的工业先例，和我们要做的批处理并发几乎同构（重复任务、可比较耗时）。

来源：<https://learn.microsoft.com/en-us/sql/relational-databases/performance/intelligent-query-processing-degree-parallelism-feedback>

### 0.4 .NET ThreadPool 的 hill-climbing

- .NET 运行时本身用 hill-climbing 控制器按**吞吐**自动增减 worker 线程；说明“运行时闭环找拐点”是官方机制，不是黑科技。
- 参考实现/论文：`Optimizing Concurrency Levels in the .NET ThreadPool: A Case Study of Controller Design and Implementation`（Hellerstein & Way），以及 runtime 的 `hillclimbing.cpp`。

来源：<https://github.com/dotnet/runtime/blob/main/src/coreclr/vm/hillclimbing.cpp>
论文：<https://www.semanticscholar.org/paper/bc1f3c28678376d8689e8115fce4242baaf8cfc9>

### 0.5 工具侧事实（决定“并行放在哪一层”）

- 7-Zip：只有 LZMA2 流含多个独立 chunk 才能多线程解码（18.03 起），20.02 才把 solid block 默认 chunk 提到 64；RAR 基本单流。⇒ **单包加线程没用，并发必须放在“多个包”这一层**。
  来源：<http://www.developershome.com/7-zip/history.txt>
- robocopy `/MT:n`：默认 8 线程，固定值（1–128），不是自适应；说明系统工具常用固定并发，但不代表对异构磁盘最优。
  来源：<https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/robocopy>
- 磁盘差异真实存在：HDD 随机并发会互相抢磁头，SSD/NVMe 靠队列深度；同一条队列深度策略不能套所有盘（这也是不能只用 CPU 核数定并发的理由）。

### 0.6 结论：应该干什么

1. **不要再用“设备类型 → 固定并发数”当主判据**；设备只配当起点/安全上限。
2. **主信号改成“归一化延迟 + 排队趋势”**（Envoy/Netflix），吞吐只做护栏。
3. **低并发基线 + 周期重测**（Envoy minRTT，带 jitter）。
4. **试探 → 验证 → 回退 → 记住**（SQL DOP feedback 的持久化“上次已知好”）。
5. **保留上下限、冷却、变更预算**，避免抖动（Envoy/Netflix 都有）。
6. **单包不并行**；并发只跨包；I/O 完成端口/异步只用于内部复制/校验，不制造额外线程。

## 1. 目标与非目标

### 目标
- 任意机器（SSD/HDD/USB/NVMe、4–32 核）同一套算法；不出现“只对 H 盘有效”。
- 稳态总耗时 **≤ 旧固定 4**（在慢盘上应明显更好），且不出现 >500 ms 的 UI 停顿。
- 控制开销可测：每批调整次数有限，探测窗口占比有限。
- 第一轮学习后，**同一设备后续批次直接从上一次已知好值起步**（SQL DOP feedback 式持久化）。
- 可解释：日志能说清“为什么加/降、依据是什么”。

### 非目标
- 不做机器学习/贝叶斯优化（样本太少、收益不成比例）。
- 不改 7z/unrar 单包线程参数。
- 不追求“所有机器都跑满 CPU/磁盘”；目标是总耗时和稳定性。
- 不引入联网遥测。

## 2. 指标定义（先埋点，再控）

对每个**成功/失败**的根任务记录：

```text
startedAt, finishedAt, inputBytes, outputBytes, outcome
normalizedLatency = finishedAt - startedAt / max(outputBytes, 1)   // 秒/GB
workerThroughput  = outputBytes / elapsed                          // MB/s per worker
```

窗口（建议 5 s，或“每完成 N 个任务”取先到者）：

```text
sampleLatency = p50/p90(normalizedLatency of tasks completed in window)
aggregateThroughput = Σ outputBytes / windowSeconds
activeWorkers = 采样时正在跑的任务数
uiStallCount, diskSpaceLow, failureCount
```

为什么用归一化延迟：任务大小差 10 倍时，直接比“耗时”会把小任务误判成快；秒/GB 或 MB/s/worker 才能跨包比较。

## 3. 控制器设计（Gradient + AIMD 混合）

### 3.1 状态

```text
limit           当前并发（1..maxLimit）
maxLimit        硬上限（默认 8；按任务数取 min）
minLatency      低并发下的基线（minRTT 类比），秒/GB
lastGoodLimit   已验证优于当前的值（持久化）
cooldown        冷却窗口数
changesInBatch  本批调整次数（上限，如 8）
probeInFlight   是否处于“基线重测/试探”窗口
```

### 3.2 初始化（只在这里用设备先验）

1. 读本机持久化 profile（按卷序列号/设备类别建键）里的 `lastGoodLimit`；有则直接用。
2. 没有 profile：
   - SSD：起点 `clamp(核数/2, 2, 4)`；
   - HDD/未知：起点 **1**（先拿干净基线）；
   - maxLimit：默认 8（不是按设备写死 3/6，避免 H 盘调参痕迹）。
3. 批次任务数 < 3：并发对总耗时影响极小，直接 `limit = min(起点, 任务数)`，不探测。

### 3.3 窗口更新（核心公式，Envoy 式）

```text
baseline = minLatency × (1 + buffer)          // buffer 建议 0.15–0.25
gradient = baseline / sampleLatency           // sample 越慢，gradient 越小
target   = round(gradient × limit + sqrt(limit))   // headroom = √limit
next     = clamp(target, 1, maxLimit)
```

护栏（任一成立则拒绝“加档”，必要时降档）：

- `uiStallCount > 0` → `next = max(1, limit − 1)`，冷却 3 窗口；
- `diskSpaceLow` → 1，直到恢复；
- `sampleLatency` 连续 2 窗口高于基线 50% → 降一档；
- `aggregateThroughput` 比上一窗口下降 >10% → 不加，冷却 2 窗口；
- `failureCount` 增加 → 保持/降档（失败可能意味着盘/密码问题，不该加并发）；
- 每批 `changesInBatch > 8` → 冻结到批末（防抖动）。

应用变更需要**连续 2 个窗口同向**（Envoy 的稳定性 + 我们自己的冷却），且相邻两次变更至少间隔 2 窗口。

### 3.4 基线重测（minRTT 类比，带 jitter）

- 每 10 分钟，或 `limit` 连续 5 个窗口停在 1；
- 把 `limit` 压到 1，采 2–5 个任务（按任务完成，不按固定时间）；
- 更新 `minLatency = p50`（不用最小值，避免缓存/异常快样本污染）；
- 加 0–20% 随机 jitter 决定何时开始，避免和批处理节奏同步；
- 短批次（<5 任务）不重测，直接用上次 profile。

### 3.5 持久化（SQL DOP feedback 式）

- 本地文件 `%LOCALAPPDATA%\ArchiveFixer\concurrency-profile.json`：
  - 键：卷序列号 + 设备类别（不记录用户文件名/路径）；
  - 值：`lastGoodLimit`、`minLatency`、`updatedAt`、`sampleCount`；
- 只有“验证过更好”的值才写入；回退时删除该键或回退到旧值；
- 换盘/换机器自然失效（键不同）；
- ⛔ 不做网络上传。

### 3.6 为什么这能“至少不比旧固定 4 差”

- 短批次：并发几乎不影响总耗时，不会更差；
- 长批次：从 1/上次好值起步，每个窗口用梯度快速试探；旧固定 4 在慢盘上会因争抢变慢（H 盘实测 149–253 s vs 1 的 95–105 s），梯度会在延迟变差时回退；
- 快盘：梯度在延迟未恶化时按 `+√limit` 增长，能爬到 4–8；
- 持久化让同一台机器**第二次起**直接从上次好值开始，不再反复试探。
- 最终仍需 A/B 矩阵验收（见 §6），不能只靠论证。

## 4. 调度器接线

- 现有 `AutoConcurrencyController` 替换为 `AdaptiveConcurrencyController`（保留旧类做回退开关，仅排障）。
- 任务完成回调提供 `inputBytes/outputBytes/elapsed/outcome`；进度事件提供窗口内字节增量。
- 调度循环每次“取下一个任务”读 `CurrentLimit`；已有任务不抢占，只影响后续启动。
- “空间不足”模式继续由空间计算接管，控制器只做上限约束（不升到空间门之上）。
- UI 线程：所有采样/计算在后台线程；日志每窗口最多一行，变更才写。
- 日志格式：
  ```text
  并发：自动（起点 1，上限 8，来源=profile|设备先验）
  并发调整 2→3：sample 1.42 s/GB（基线 1.10，gradient 0.77，headroom 1.73），吞吐 31.2 MB/s
  并发回退 3→2：延迟 +48%，总吞吐 -6%
  并发冻结：本批已调整 8 次
  ```

## 6. 验证方案（必须跨机器，不能只看 H）

### 6.1 单元/纯逻辑
- 延迟曲线：并发↑延迟不变 → limit 爬到 max；并发↑延迟翻倍 → 回退到 1/上次好值；
- 吞吐护栏：延迟没变但总吞吐下降 → 不加；
- UI 停顿/空间低/失败 → 降档；
- 基线重测：固定 jitter 种子，验证会压到 1 并更新 baseline；
- 持久化：写/读/换盘键失效/回退删除。

### 6.2 无头基准矩阵（真机，H 盘只是其中一格）
- 机器：本机 SSD（E:）、本机 HDD/USB（H:）、至少一台低配/虚拟机（若有）。
- 负载：4×600 MiB 大包；20×50 MiB 中包；200×2 MiB 小包；加密/不加密各一组。
- 基线：固定 1、固定 2、固定 4（旧默认）、固定 8。
- 指标：总耗时、p50/p95 单任务归一化延迟、UI 最大停顿、调整次数、探测窗口占比。
- 验收：
  - 每种负载/机器：自动总耗时 ≤ 固定 4 × 1.05；
  - 慢盘（H）自动 ≤ 固定 4 × 0.9；
  - 快盘自动 ≥ 固定 4 的 0.95（不能为了慢盘牺牲快盘）；
  - UI 停顿 < 500 ms；每批调整 ≤ 8 次；无“加到 8 后长时间不降”的振荡。
- 如果达不到：先修控制器，不改验收阈值。

### 6.3 红检
- 把梯度公式换成“只看吞吐” → 延迟恶化用例必须红；
- 去掉回退 → “加档后变慢”用例红；
- 去掉持久化 → 第二次批次仍从 1 起步的用例红；
- 把 min/max 去掉 → 越界用例红。

## 8. 风险与未决

- **延迟噪声**：缓存命中/杀软扫描会让单任务样本忽快忽慢；用 p50 + 2 窗口确认，不用单样本。
- **任务异质性**：加密/压缩比差异大，归一化延迟仍受 CPU 影响；必要时按格式分组统计。
- **短批次**：任务少时无法学习，直接用先验/上次好值，不探测。
- **持久化误判**：换盘后键失效；文件损坏则回退设备先验。
- **空间模式**：空间不足时空间门优先，控制器不得抬上限。
- **进程数上限**：外部引擎本身有全局闸门（同机 4 个），控制器 maxLimit 要与之对齐，不能设计成 8 却永远被 4 卡住。
- **验收成本**：跨机器矩阵需要时间；不能再用“H 盘一轮”当结论。

## 9. 与当前实现的关系

- 当前 `1898c41`：吞吐 AIMD + 设备先验，能工作但缺延迟梯度/基线/持久化；H 盘调参痕迹重。
- 本方案保留其“保守起点、试探、回退、上限”的正确部分，替换判据为延迟梯度，并新增持久化与跨机器验收。
- 迁移期间保留旧控制器作为 kill-switch（内部开关，不暴露 UI），验证达标后删除。
