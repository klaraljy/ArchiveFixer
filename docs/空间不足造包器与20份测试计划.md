## 2. 设计原则

- 小包：0.2–2.0 MB，生成/解压/清理都快；
- 一包一层，不嵌套、不加密，专门测空间调度；
- 内容用不可压缩随机数据，源包大小 ≈ 内容物大小，避免压缩率让体积不可控；
- 空间用测试宿主注入，不填真实 H 盘；
- 普通模式与空间不足模式各解一次，普通模式作为对照；
- 每一份的源包、内容物、剩余空间都写进 recipe。

## 3. 普通 15 份

### 3.1 结构

每份是**一个普通压缩包**，内含一个内容文件：

```text
大测试\910300000\910300001\
├─ 原包\
│  └─ space-910300001.7z
└─ recipe.json
```

源包大小、内容物大小、格式、预期空间都记录。

### 3.2 场景矩阵

5 个场景组 × 3 份 = 15。

| 组 | 样本 | 包大小 | 剩余空间 | 预期 |
|---|---|---:|---:|---|
| N1 | 001 / 002 / 003 | 2.0 / 1.0 / 0.3 MB | 2.2 MB | 先跑 2.0；成功后 1.0 + 0.3 可并行 |
| N2 | 004 / 005 / 006 | 2.0 / 1.5 / 0.3 MB | 3.8 MB | 2.0 + 1.5 并行，0.3 等 |
| N3 | 007 / 008 / 009 | 2.0 / 1.0 / 0.3 MB | 1.2 MB | 2.0 一开始跳空间不足；1.0 先跑 |
| N4 | 010 / 011 / 012 | 2.0 / 1.5 / 1.0 MB | 0.2 MB | 三份全部空间不足，源包不动 |
| N5 | 013 / 014 / 015 | 1.5 / 1.0 / 0.6 MB | 1.6 MB | 1.5 先跑；之后 1.0 + 0.6；015 故意损坏 |

- 所有 MB 按 **1,000,000 字节**口径；
- 测试保留余量 64 KiB；
- 实际 free 由生成器按“内容物 + 64 KiB + 少量余量”计算，表中是名义值；
- N5 的 015 在造包后截断/破坏，用于失败/最后过程物测试。

### 3.3 每组的预期执行

#### N1

```text
排序：2.0 > 1.0 > 0.3
初始 2.2MB：
  2.0 内容物 + 余量 ≈ 2.1MB 可启动
  1.0 不能同时启动（2.0 + 1.0 + 余量 > 2.2）
并发：1
2.0 成功 + 删源后空间增加，1.0 + 0.3 可并行
最终：3 成功，源包全删
```

#### N2

```text
排序：2.0 > 1.5 > 0.3
初始 3.8MB：
  2.0 + 1.5 + 余量 ≈ 3.6MB ⇒ 两并发同时启动
  0.3 等
并发：2
最终：3 成功，源包全删
```

#### N3

```text
排序：2.0 > 1.0 > 0.3
初始 1.2MB：
  2.0 放不下 ⇒ 立即 space blocked，退出队列
  1.0 + 余量可启动
  0.3 不能同时
并发：1
1.0 成功后 0.3 启动；2.0 不重试
最终：1.0 / 0.3 成功；2.0 空间不足，源包保留
```

#### N4

```text
初始 0.2MB：
  2.0 / 1.5 / 1.0 全部放不下
  三份都不启动，状态空间不足
最终：0 内容物，三份源包全部保留
```

#### N5

```text
排序：1.5 > 1.0 > 0.6
初始 1.6MB：
  1.5 启动；1.0 不能同时
并发：1
1.5 成功删源后，1.0 + 0.6 可并行
并发：2
015（0.6）是损坏包：
  → 任务失败
  → 内容物不发布
  → 源包保留为最后一层过程物
最终：1.5 / 1.0 成功；015 失败；只有 015 源包保留
```

## 4. 特定解压 5 份

### 4.1 结构

每份是**一个外层特定解压包**，内含 **3 个相同文件**：

```text
大测试\910400000\910400001\
├─ 原包\
│  └─ specific-910400001.7z
└─ recipe.json
```

- 三份内容文件内容相同、大小相同；
- 不加密、不嵌套；
- 外层一层解出 3 个文件，正好验证特定解压的“多相同文件”形状。

### 4.2 样本矩阵

| 样本 | 外层总大小 | 内部文件 | 剩余空间 | 预期 |
|---|---:|---|---:|---|
| 910400001 | 1.8 MB | 3 × 600 KB | 2.0 MB | 先跑 1.8 |
| 910400002 | 1.4 MB | 3 × 约 466 KB | 2.0 MB | 1.8 成功后与 1.0 并行 |
| 910400003 | 1.0 MB | 3 × 约 333 KB | 2.0 MB | 与 1.4 并行 |
| 910400004 | 0.6 MB | 3 × 200 KB | 2.0 MB | 后续并行 |
| 910400005 | 0.2 MB | 3 × 约 66 KB | 2.0 MB | 收尾 |

### 4.3 预期执行

```text
排序：1.8 > 1.4 > 1.0 > 0.6 > 0.2
初始 2.0MB：
  1.8 + 余量可启动
  1.4 不能同时启动
并发：1
1.8 成功 + 删源后：
  1.4 + 1.0 + 余量可并行
并发：2
最后 0.6 + 0.2 收尾
并发上限始终 <= 2
```

全部成功时源包全删；任何一步失败则源包保留，最后过程物固定留下。

## 5. 测试宿主与空间注入

### 5.1 为什么不能靠真实 H 盘

生产保留余量设计上会从固定 512 MiB 调整为**可配置 + 按任务缩放**（默认上限 64 MiB、下限约 1 MiB，最终公式待单位讨论），但 0.2–2 MB 的包仍然无法在真实 H 盘上稳定测到“只剩 2 MB”的边界。

所以 20 份必须跑无头测试宿主：

```text
SpaceTightMode = true
SpaceTightKeepSource = false
用户并发 = 2
SpaceReserveOverride = 64 KiB
SpaceProbeOverride = recipe.space.freeBytes
```

- `SpaceProbeOverride` 是本项目已有的测试注入点；
- 不需要填 H 盘；
- 不触碰用户真实数据；
- 每次 probe 返回同一个 free，便于复现。

> **“无头注入”** = 不打开 WPF 界面，由测试 runner 直接调用解压管线；用测试钩子把“目标盘可用空间”和“保留余量”替换成 recipe 指定的数字。它只改变测试时的空间探测结果，不改变真实磁盘，也不改生产默认值。

### 5.2 批次划分

| 运行 | 样本 | 注入 free | 并发 |
|---|---|---:|---:|
| B1 | N1 001–003 | 2.2 MB | 2 |
| B2 | N2 004–006 | 3.8 MB | 2 |
| B3 | N3 007–009 | 1.2 MB | 2 |
| B4 | N4 010–012 | 0.2 MB | 2 |
| B5 | N5 013–015 | 1.6 MB | 2 |
| B6 | S1–S5 910400001–005 | 2.0 MB | 2 |

每个批次独立：

- 复制母本到工作目录；
- 独立 data/log；
- 跑完记录源包/内容物/最后过程物；
- 不跨批复用任务对象。

## 6. 造包器契约

### 6.1 脚本

建议新增：

```text
E:\AF\大测试-造空间不足包.ps1
```

参数：

```text
-SpaceRoot       H:\...\大测试
-BackupRoot      H:\...\大测试备份位置
-LogRoot         H:\...\大测试日志
-SpecifiedRoot   H:\...\大测试指定位置
-NormalSeedBase  910300000
-SpecificSeedBase 910400000
-Force
```

### 6.2 普通包生成

1. 生成指定大小的随机内容文件；
2. 用 7z 打包（部分样本用 zip），`-mx=1`；
3. 记录实际源包大小和内容物大小；
4. 输出 `原包` + `recipe.json`；
5. 备份到 `910300000-空间不足-备份`；
6. N5-015 造完后截断/破坏，并标记 `expectedFailure`；
7. 校验每份的实际大小与计划差异。

### 6.3 特定包生成

1. 生成 3 个相同内容文件；
2. 打成一个外层 7z；
3. 记录外层源包大小、3 个文件总内容物大小；
4. 输出 `原包` + `recipe.json`；
5. 备份到 `910400000-空间不足-特定解压-备份`；
6. 不嵌套内层包，避免把特定解压的空间测试变成递归测试。

### 6.4 recipe 字段

```json
{
  "schemaVersion": 1,
  "seedBase": 910300000,
  "sample": "910300001",
  "kind": "NormalSpaceTight",
  "spaceGroup": "N1",
  "sourceBytes": 2000123,
  "contentBytes": 2000000,
  "processArtifactBytes": 0,
  "space": {
    "freeBytes": 2200000,
    "reserveBytes": 65536,
    "concurrency": 2,
    "expectedFirst": "910300001",
    "expectedSkipped": [],
    "expectedMaxConcurrency": 1
  },
  "expected": {
    "sourceDeleted": true,
    "contentPublished": true,
    "lastProcessKept": false,
    "taskOutcome": "Succeeded"
  }
}
```

损坏样本额外：

```json
{ "expectedFailure": true, "expectedLastProcess": true }
```

### 6.5 批次计划

生成：

```text
大测试日志\大测试日志-910300000-空间不足\空间计划.json
大测试日志\大测试日志-910400000-空间不足-特定解压\空间计划.json
```

列出每个批次的样本、注入 free、reserve、并发、期望顺序。

## 7. 20 份测试断言

### 7.1 通用断言

每份检查：

```text
任务是否启动
最终 TaskOutcome
源包 before/after
最终内容物文件数
是否出现部分内容
最后过程物路径
日志中的空间数字
```

### 7.2 按组断言

| 组 | 必须成立 |
|---|---|
| N1 | 初始并发 1；2.0 成功后 1.0/0.3 可并行；3 成功；源包全删 |
| N2 | 2.0+1.5 并行；0.3 等待；最大并发 2；3 成功 |
| N3 | 2.0 立即空间不足；1.0 成功；0.3 成功；2.0 不重试、源包保留 |
| N4 | 3 份全部空间不足；0 内容物；源包全保留 |
| N5 | 1.5 先成功；1.0 成功；0.6 失败；失败内容物不发布；0.6 源包保留为最后过程物 |
| S1–S5 | 1.8 先跑；1.4+1.0 并行；最大并发 2；全部成功；源包全删 |

### 7.3 安全断言

- 删除源包只发生在成功、校验通过、未取消的任务；
- 失败 / 空间不足任务源包一个字节不动；
- 失败任务最终目录没有半成品内容物；
- 最后过程物固定保留；
- 硬链接别名清理后才能删源；
- 跨盘测试不复制源包。

## 8. 对照测试：普通模式

同样 N1 三份，再跑一次**关闭空间不足**：

- 源包默认保留；
- 过程物成功删除；
- 3 份都能完成或按普通空间门排队；
- 不允许因为空间不足代码改变普通模式行为。

N1 普通模式主要钉住“普通模式不变”，不需要重复其他组。

## 9. 跨盘补充测试

不属于 20 份计数，单独跑一份：

```text
源包 E:\...\space-cross\pack.7z
目标 H:\...\space-cross-out
free = 内容物 + 64 KiB
```

预期：

- 不复制源包到 H；
- H 只多出内容物；
- 源包成功后可删除；
- 如果实现走了 group-entry 跨盘复制，测试必须红。

如果该样本是**分卷组**，则源盘 E 上建入口/别名，不把整组复制到 H。

## 10. 通过标准

- 20/20 份按 recipe 预期结束；
- 普通 15 份：成功/空间不足/失败三类数量与矩阵一致；
- 特定 5 份：全部成功，并发最多 2；
- 源包删除/保留与预期一致；
- 失败内容物 0 发布；
- 最后过程物路径存在；
- 跨盘补充样本无源包复制；
- 普通模式对照无行为变化；
- 日志能逐份复核“需要 / 可用 / 差 / 实际并发 / 源包去向”。

## 11. 待讨论

- 保留余量的最终公式：方向是不再固定 512 MiB，改为可配置 + 按任务缩放；
- 真实盘 VHD 模式是否作为补充，不作为 20 份小包的主测试手段；
- 特定解压是否直接共用同一份 `SpacePolicy` 对象，还是先接简化版空间账本；
- 最后一层过程物固定保留在原路径，还是统一集中到 `其余物`。

### 已确认

- 大包空间不足后**允许用户手动重试**；不自动排队反复重试；
- 20 份小包用无头注入测空间边界，不填真实 H 盘。
