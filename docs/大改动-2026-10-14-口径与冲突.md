## 2. 清理方式（本次大改的核心口径）

### 2.1 两个开关（都只有两档，都默认"留下"）

| 开关 | 管什么 | 档 |
|---|---|---|
| **源包操作（成功）** | **只**在"完全成功拿到内容物"时才动源包 | **留下（默认）** / 彻底删除（不进回收站） |
| **删除操作（失败和部分完成）** | **只**管"最后一层过程物" | **留下（默认）** / 彻底删除 |

### 2.2 链条模型（用户逐字给的比方：`A->B->C->D->a`）

| 情形 | 谁被删 | 谁被留 | 依据（用户口径） |
|---|---|---|---|
| 一路成功得到完整 `a` | `B` `C` `D`（过程物）**统一彻底删除** | `A` 按**源包操作（成功）**（默认留） | 「只要成功就删掉」；`A` 是唯一需要用户决定的那一份 |
| `B->C` 失败 | `B` 以前的过程物（若有）删；**`B` 本身按删除操作（失败）**（默认留） | `A` 一定留（没完全成功） | 「C->D 的情况下失败了，C 就是最后一层过程物」 |
| `D->a` 失败或**部分完成** | `B` `C`（成功过的）删；**`D` 按删除操作**（默认留，且 `D` 是完整的） | `A` 一定留 | 「D 肯定会留下，而且是完整的……前面的 B 和 C 都是成功的」 |

⇒ **`A` 只有在"完全成功"时才可能被删** ⇒ 与 25 GB 那次事故不冲突：那次的失败位置相当于 `D->a`，
`A` 与 `D` 都留下了。

### 2.3 用户对"为什么这样不危险"的论证（照抄，作为实现时的判据）

- 「`A` 只有在完全成功的前提下才能操作，他不会和 25G 的情况发生冲突」；
- 「失败的情况下原包一定会留下」；
- 「删掉的是**成功过的那几层**——它们可以从留下的那一层重做，所以不是证据」。

### 2.4 其余物（用户 2026-10-14 定）

- **位置与名字不变**（还是各层里的 `其余物\`），**语义**改成「**过程物 + 无用物**」；
- 用户明确：这次**不**取消其余物，暂按现状跑。

## 7. 工作区内部（用户要求"了解得一清二楚"）

### 7.1 根在哪（唯一来源，⛔ 没有回落）

- `Storage/WorkspaceRootResolver`：工作区 = **这一批第一个算得出落点的目标目录** + `\.ArchiveFixer.work`
  （常量 `DefaultWorkspaceDirectoryName`，点开头 + 隐藏属性）。
- ⛔ 拿不到目标目录 ⇒ **报错指路**，绝不回落程序目录 / C 盘 / 源卷根 / `%TEMP%`（2026-09-30 用户拍板，代码里那一档已彻底删除）。
- 批首由 `ApplyBatchWorkspaceRoot` 定根：**跳过"入口包还没解出来"的分卷组单**（它们的落点只是占位值）。

### 7.2 里面长什么样（两种路各一套）

| 路 | 目录形状 | 出处 |
|---|---|---|
| 普通单层/续解 · 入仓 | `<根>\<任务名>-<8位哈希>\stage\` | `PathService.StageDirectoryName = "stage"`；夹具实例逐字 `…\.ArchiveFixer.work\111-L2.001-2c88e855\stage` |
| 递归 · 每层 | `<根>\recursive\<包名>_<时间戳>_<guid>\layer-000\output\`、`layer-001\output\`… | `RecursiveExtractor.cs:4938`（自己再挂一层 `recursive`）+ `ExtractionWorkspace`（`layer-` 前缀、`output` 固定名） |
| 每层台账 | 每层目录里一份 **`report.json`** | `ExtractionWorkspace`：崩溃后按这个约定恢复 |

- **引擎的产物只写进这些目录**（7z/UnRAR 的 `-o` 目标），**⛔ 内容物绝不在工作区定稿**；
- 「入仓」= 先落 `stage`，**定稿那一刻**才按落点规则搬进成品目录（同卷是改名，不是复制）；
- 递归核的工作区根是**进程级静态**，批首跟着目标目录一起换（`MainViewModel.cs:421` 有注释钉着）。

### 7.3 什么时候删（顺序与判据）

1. **递归每一层定稿并发布之后**：当场清理那一层的中间产物
   （日志逐字：`递归解压已完成且产物已发布，清理本次任务的工作区（1 个文件 / 2688 字节）`）；
2. **一单成功之后**：整份删它的工作区
   （逐字：`解压成功且输出校验通过，清理本任务的中间工作区（0 个文件 / 0 字节）`）；
3. **失败 / 部分完成 / 取消**：默认也删；只有"失败时保留中间产物"打开才留现场
   （逐字：`未发布的产物留在工作区：…\recursive\111-W0-0_20261013_191045_5e6ec487…`）；
4. **空目录/空壳**：顺手收掉（逐字：`顺手收掉了空的工作区目录：…\.ArchiveFixer.work`、
   `顺手清掉了空的工作区壳：…\.ArchiveFixer.work\recursive`）；
5. **上一批的残留**：`WorkspaceLeftoverShellCleaner` 只清"除了一个空 `.ArchiveFixer.work` 什么都没有"的目录
   （逐字：`发现 1 个工作区残留（上次失败 / 取消留下的，共 0 字节）`）；
6. **防误删**：`WorkspaceCleanupGuard` —— 只允许删"本任务工作区"那一棵，判不出 ⇒ 一个字节都不动。

### 7.4 为什么"工作区"和判据强相关（这条最关键）

工作区**一被清理，没被"记下/发布"的产物就没了**。这就是为什么：
- "缺卷"那一档必须**先把那一片记下来**（`RememberUnresolvedVolumePiece`）再收场 —— 否则链条一收尾，
  那一组永远缺片（`1111` 当年就是这么红的，第 15 修）；
- 分卷的"片区链接"必须**硬链接**（零字节、跨清理存活），不能只在工作区里留一份。

| 单一包外面**又套了一层包**（压缩 0–2 次） | ✅ 认外层；内层要**解出来之后**才认得（第一大步的递归） | `RecursiveExtractor` |

## 13. 我审出来的问题（按危险度，每条：用户原话 → 问题 → 建议判据）

1. **⛔「末卷 = 最小的那个」不能当判据**（7z 族 + rar 族 + zip 族都用到了它）
   - 问题：**任意一个"下载不全 / 被改坏 / 被单独压缩过"的片都会是最小的**。而你自己的造包规则里写着
     「**每一片可被单独压缩 0–2 次**」⇒ 压缩过的中间片**体积远小于满片** ⇒ 一定会被误判成末卷 ⇒ 整组改名全错。
   - 建议判据：**只有"唯一一个小于满体积、其余全都等于满体积"时才认它是末卷**；
     出现两个及以上"小的"⇒ **判不出**（⛔ 不猜）；**先解开外面那一层**（被压缩过的片先解出来再谈体积规律）。
2. **⛔ rar 族的"卷号一清二楚"只对 RAR5 成立**
   - RAR5：主头 `MHFL_VOLUME_NUMBER` ⇒ **绝对卷号** ✓（你说的"最简单"这一档）；
   - RAR4 **新编号**：结尾块里的字段**基数待定** ⇒ 只能**相对定序**（我为此专门加了卡上的 `RawVolumeField`）；
   - RAR4 **老编号族**（`.rar`+`.r00`）：本程序**只认 `partN.rar` 一种写法**，那一族**不动**（`Fail = RarOldNumbering`）。
   - ⇒ 设计里要按这三档分别写，否则实现时会踩"以为都能读卷号"。
3. **⛔ 跨盘 zip 有两族、末片名完全不同，别混**
   - **跨盘 ZIP 族**：`.z01/.z02/...` + **末片 `X.zip`**（头尾编号是反的）；末片的 EOCD 里有盘号 ⇒ 片数 B ✓；
   - **7z 造的通用分片**：`X.zip.001/.002/...`（**末片也是 `X.zip.00N`**，`X.zip` 在这里反而意味着**单一包**）；
   - 而且**光看头判不出"是分卷"**：`PK\x03\x04` 就是普通单卷 zip 的头 ⇒ 中间片在内容上只能落 `Unknown`（判不出），
     必须靠 **EOCD 盘号（只有末片有）+ 名字 + 同组里有末片** 这三条一起。
4. **通用分片族的"族"由第一片定**：第一片有魔数（认得出格式），后续片**没有魔数** ⇒ 族只能从第一片读；
   其余片靠**基名 + 除末卷等大 + 序号**排；改名照**既有片的写法**（我实现里是 `TryNameSlotLikeExistingPiece`+自验）。
5. **"额外引擎"要落下**：新增一个引擎只需要接三件事 ——（a）能列目录/试开（`IArchiveEngine`）、
   （b）能报缺卷与错误类型（结构化码）、（c）能按给定密码解到指定目录；**判据一律走底层那张卡**
   （⛔ 不许按格式/引擎分支写第二套）。
6. **批级结论 vs 单级结论必须分开**（你 line 32/33 那套"全部的行为而不是全体的行为"的技术含义）
   - 单级（每一单、每一层）：照旧落"这一单成没成 / 哪些层失败"（**红色 ERROR 行照旧**，它是单级真实失败）；
   - **批级**（汇总/色带）：按你说的三条重算 —— **有内容物 + 还有包没解出来 = 部分完成（橙）**；
     **零内容物 + 只剩包 = 失败（红）**；**零包剩余 + 内容物齐 = 成功（蓝）**；
   - ⚠ 现在的实现是"**批末只要有 Failed 单就报红**"（`BatchSummarySeverityRules`）⇒ **必须改成读批级结论**，
     否则"单一失败 + 有内容物"会被误报红。
7. **汇总的分母**（你 line 36）要写死：**只数"用户自己操作的那些东西"**（导入/勾选的原包那几条链），
