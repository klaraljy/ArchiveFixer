## 2. 清理方式（本次大改的核心口径）

### 2.1 两个开关（都只有两档，都默认"留下"）

| 开关 | 管什么 | 档 |
|---|---|---|
| **源包操作（成功）** | **只**在"完全成功拿到内容物"时才动源包 | **留下（默认）** / 彻底删除（不进回收站） |
| **删除操作（失败和部分完成）** | **只**管"最后一层过程物" | **留下（默认）** / 彻底删除 |

### 2.2 链条模型（用户逐字给的比方：`A->B->C->D->a`）

| 情形 | 谁被删 | 谁被留 | 依据（用户口径） |
|---|---|---|---|
| 一路成功得到完整 `a` | `B` `C` `D`（过程物）**统一彻底删除** | `A` 按**源包操作（成功）**（默认留） | 「只要成功就删掉」；`A` 是唯一需要用户决定的那一份 |
| `B->C` 失败 | `B` 以前的过程物（若有）删；**`B` 本身按删除操作（失败）**（默认留） | `A` 一定留（没完全成功） | 「C->D 的情况下失败了，C 就是最后一层过程物」 |
| `D->a` 失败或**部分完成** | `B` `C`（成功过的）删；**`D` 按删除操作**（默认留，且 `D` 是完整的） | `A` 一定留 | 「D 肯定会留下，而且是完整的……前面的 B 和 C 都是成功的」 |

⇒ **`A` 只有在"完全成功"时才可能被删** ⇒ 与 25 GB 那次事故不冲突：那次的失败位置相当于 `D->a`，
`A` 与 `D` 都留下了。

### 2.3 用户对"为什么这样不危险"的论证（照抄，作为实现时的判据）

- 「`A` 只有在完全成功的前提下才能操作，他不会和 25G 的情况发生冲突」；
- 「失败的情况下原包一定会留下」；
- 「删掉的是**成功过的那几层**——它们可以从留下的那一层重做，所以不是证据」。

### 2.4 其余物（用户 2026-10-14 定）

- **位置与名字不变**（还是各层里的 `其余物\`），**语义**改成「**过程物 + 无用物**」；
- 用户明确：这次**不**取消其余物，暂按现状跑。

## 7. 工作区内部（用户要求"了解得一清二楚"）

### 7.1 根在哪（唯一来源，⛔ 没有回落）

- `Storage/WorkspaceRootResolver`：工作区 = **这一批第一个算得出落点的目标目录** + `\.ArchiveFixer.work`
  （常量 `DefaultWorkspaceDirectoryName`，点开头 + 隐藏属性）。
- ⛔ 拿不到目标目录 ⇒ **报错指路**，绝不回落程序目录 / C 盘 / 源卷根 / `%TEMP%`（2026-09-30 用户拍板，代码里那一档已彻底删除）。
- 批首由 `ApplyBatchWorkspaceRoot` 定根：**跳过"入口包还没解出来"的分卷组单**（它们的落点只是占位值）。

### 7.2 里面长什么样（两种路各一套）

| 路 | 目录形状 | 出处 |
|---|---|---|
| 普通单层/续解 · 入仓 | `<根>\<任务名>-<8位哈希>\stage\` | `PathService.StageDirectoryName = "stage"`；夹具实例逐字 `…\.ArchiveFixer.work\111-L2.001-2c88e855\stage` |
| 递归 · 每层 | `<根>\recursive\<包名>_<时间戳>_<guid>\layer-000\output\`、`layer-001\output\`… | `RecursiveExtractor.cs:4938`（自己再挂一层 `recursive`）+ `ExtractionWorkspace`（`layer-` 前缀、`output` 固定名） |
| 每层台账 | 每层目录里一份 **`report.json`** | `ExtractionWorkspace`：崩溃后按这个约定恢复 |

- **引擎的产物只写进这些目录**（7z/UnRAR 的 `-o` 目标），**⛔ 内容物绝不在工作区定稿**；
- 「入仓」= 先落 `stage`，**定稿那一刻**才按落点规则搬进成品目录（同卷是改名，不是复制）；
- 递归核的工作区根是**进程级静态**，批首跟着目标目录一起换（`MainViewModel.cs:421` 有注释钉着）。

### 7.3 什么时候删（顺序与判据）

1. **递归每一层定稿并发布之后**：当场清理那一层的中间产物
   （日志逐字：`递归解压已完成且产物已发布，清理本次任务的工作区（1 个文件 / 2688 字节）`）；
2. **一单成功之后**：整份删它的工作区
   （逐字：`解压成功且输出校验通过，清理本任务的中间工作区（0 个文件 / 0 字节）`）；
3. **失败 / 部分完成 / 取消**：默认也删；只有"失败时保留中间产物"打开才留现场
   （逐字：`未发布的产物留在工作区：…\recursive\111-W0-0_20261013_191045_5e6ec487…`）；
4. **空目录/空壳**：顺手收掉（逐字：`顺手收掉了空的工作区目录：…\.ArchiveFixer.work`、
   `顺手清掉了空的工作区壳：…\.ArchiveFixer.work\recursive`）；
5. **上一批的残留**：`WorkspaceLeftoverShellCleaner` 只清"除了一个空 `.ArchiveFixer.work` 什么都没有"的目录
   （逐字：`发现 1 个工作区残留（上次失败 / 取消留下的，共 0 字节）`）；
6. **防误删**：`WorkspaceCleanupGuard` —— 只允许删"本任务工作区"那一棵，判不出 ⇒ 一个字节都不动。

### 7.4 为什么"工作区"和判据强相关（这条最关键）

工作区**一被清理，没被"记下/发布"的产物就没了**。这就是为什么：
- "缺卷"那一档必须**先把那一片记下来**（`RememberUnresolvedVolumePiece`）再收场 —— 否则链条一收尾，
  那一组永远缺片（`1111` 当年就是这么红的，第 15 修）；
- 分卷的"片区链接"必须**硬链接**（零字节、跨清理存活），不能只在工作区里留一份。

| 单一包外面**又套了一层包**（压缩 0–2 次） | ✅ 认外层；内层要**解出来之后**才认得（第一大步的递归） | `RecursiveExtractor` |

## 13. 我审出来的问题（按危险度，每条：用户原话 → 问题 → 建议判据）

1. **⛔「末卷 = 最小的那个」不能当判据**（7z 族 + rar 族 + zip 族都用到了它）
   - 问题：**任意一个"下载不全 / 被改坏 / 被单独压缩过"的片都会是最小的**。而你自己的造包规则里写着
     「**每一片可被单独压缩 0–2 次**」⇒ 压缩过的中间片**体积远小于满片** ⇒ 一定会被误判成末卷 ⇒ 整组改名全错。
   - 建议判据：**只有"唯一一个小于满体积、其余全都等于满体积"时才认它是末卷**；
     出现两个及以上"小的"⇒ **判不出**（⛔ 不猜）；**先解开外面那一层**（被压缩过的片先解出来再谈体积规律）。
2. **⛔ rar 族的"卷号一清二楚"只对 RAR5 成立**
   - RAR5：主头 `MHFL_VOLUME_NUMBER` ⇒ **绝对卷号** ✓（你说的"最简单"这一档）；
   - RAR4 **新编号**：结尾块里的字段**基数待定** ⇒ 只能**相对定序**（我为此专门加了卡上的 `RawVolumeField`）；
   - RAR4 **老编号族**（`.rar`+`.r00`）：本程序**只认 `partN.rar` 一种写法**，那一族**不动**（`Fail = RarOldNumbering`）。
   - ⇒ 设计里要按这三档分别写，否则实现时会踩"以为都能读卷号"。
3. **⛔ 跨盘 zip 有两族、末片名完全不同，别混**
   - **跨盘 ZIP 族**：`.z01/.z02/...` + **末片 `X.zip`**（头尾编号是反的）；末片的 EOCD 里有盘号 ⇒ 片数 B ✓；
   - **7z 造的通用分片**：`X.zip.001/.002/...`（**末片也是 `X.zip.00N`**，`X.zip` 在这里反而意味着**单一包**）；
   - 而且**光看头判不出"是分卷"**：`PK\x03\x04` 就是普通单卷 zip 的头 ⇒ 中间片在内容上只能落 `Unknown`（判不出），
     必须靠 **EOCD 盘号（只有末片有）+ 名字 + 同组里有末片** 这三条一起。
4. **通用分片族的"族"由第一片定**：第一片有魔数（认得出格式），后续片**没有魔数** ⇒ 族只能从第一片读；
   其余片靠**基名 + 除末卷等大 + 序号**排；改名照**既有片的写法**（我实现里是 `TryNameSlotLikeExistingPiece`+自验）。
5. **"额外引擎"要落下**：新增一个引擎只需要接三件事 ——（a）能列目录/试开（`IArchiveEngine`）、
   （b）能报缺卷与错误类型（结构化码）、（c）能按给定密码解到指定目录；**判据一律走底层那张卡**
   （⛔ 不许按格式/引擎分支写第二套）。
6. **批级结论 vs 单级结论必须分开**（你 line 32/33 那套"全部的行为而不是全体的行为"的技术含义）
   - 单级（每一单、每一层）：照旧落"这一单成没成 / 哪些层失败"（**红色 ERROR 行照旧**，它是单级真实失败）；
   - **批级**（汇总/色带）：按你说的三条重算 —— **有内容物 + 还有包没解出来 = 部分完成（橙）**；
     **零内容物 + 只剩包 = 失败（红）**；**零包剩余 + 内容物齐 = 成功（蓝）**；
   - ⚠ 现在的实现是"**批末只要有 Failed 单就报红**"（`BatchSummarySeverityRules`）⇒ **必须改成读批级结论**，
     否则"单一失败 + 有内容物"会被误报红。

## 25. 已落（2026-10-16）：**默认档下「本批已成功的密码」复用链整条失效** —— 递归内核补一个回传口

> 这是桶 C 里**第一个真正的产品缺陷**（前面两条是"用例扳机没了"与"用例追旧口径"）。

### 25.1 症状与运行期事实（⛔ 全部是探针读数，不是读代码推的）

- 红：`PasswordReuseTests.第一包第五候选成功_第二包第一次尝试就是复用来的密码`，逐字
  `Assert.Single() Failure: The collection contained 6 items` +
  `Collection: ["", "<示例密码1>", "<示例密码2>", "<示例密码3>", "<示例密码4>", ···]`。
- 探针（三处 `RecordPasswordSuccess` 各插一行 + 用例内把两次候选表与整份日志倒出来，读完即删）逐字：

```
first  =  | <示例密码1> | <示例密码2> | <示例密码3> | <示例密码4> | <示例密码5>
second =  | <示例密码1> | <示例密码2> | <示例密码3> | <示例密码4> | <示例密码5>
```

  两个包拿到的候选表**一模一样**（都从空密码开始）；日志里那两轮候选逐字是
  `├ 第 0 层：first.7z：开始解压，密码候选 N/6` —— **递归内核的**循环，
  而三处 `[排障·桶C] 记成功密码·站点N` **一条都没出现**。
- ⇒ **`PasswordService.RecordPasswordSuccess` 在默认档下一次都没被调到** ⇒
  `BatchVerifiedPasswords` 恒空 ⇒ "复用本批已成功的密码"这一档永远不会出现在任何候选表里。

### 25.2 根因（一句话）

默认档是「有压缩包就解压」⇒ 解压交给递归核心 `RecursiveExtractor`；而 `RecordPasswordSuccess` 的
调用点只有三处（协调器的单层路 `:23846`、协调器自己的候选循环 `:24242`、换引擎兜底 `:25128`）——
**没有一处覆盖递归内核**。内核的成功路只把"用了哪把密码"**脱敏**后放进层报告
（`RecursionLayerReport.UsedPasswordMasked`），协调器拿不回明文 ⇒ 记不了账。

### 25.3 落了什么（产品两处，判据方向一个字没改）

- `RecursiveExtractor`：新增**瞬时回传口** `public Action<string>? PasswordVerified`，
  唯一调用点 = `FinishSuccessfulLayerAsync`（**三条成功路的共同出口**：主引擎循环 / 尾部归档直读 /
  换引擎兜底）⇒ 直读与兜底两条路也照样报；空密码不报（与 `RecordVerifiedPassword` 的既有口径一致）。
- `ExtractionCoordinator.RunRecursiveAsync`：把回传口挂成
  `_passwordService.RecordPasswordSuccess(task.CurrentPath, password)` —— 挂**源文件**，
  与单层路那三处逐字同一口径（"工作区里抠出来的临时文件活不过这次任务"）。
- ⛔ **`RecursionLayerReport` 那条「本类不得出现明文密码」的规矩一个字没动**：回传口不是报告字段，
  它与既有的 `DescribeCandidate` 同一档 —— 那个口子本来就把候选值交给调用方。

### 25.4 ⚠ 一处如实记账的语义差别（⛔ 不隐瞒）

内核报的时刻 = **引擎在这一层接受了这把密码**；单层路那三处记的时刻 = **产物校验通过之后**。
⇒ 存在一种形状：引擎说成功、但（收尾）校验判否 ⇒ 这一把密码仍会被记进"本批已成功"。
方向是**多记一次**（后一个包先试它一下），⛔ 不会让任何东西被跳过、也不会把失败说成成功；
要对齐到"校验通过才记"需要把逐层校验结论回灌内核（更大的改动），本轮**没做**，如实记在这里。

### 25.5 红检（实测原文）

把挂钩临时换成 `_ => { }`（调用点保留、效果掐掉）⇒ 重编 ⇒ 那一族**2 红 → 4 红**，
逐字新增的两条正是 `PasswordReuseTests.第一包第五候选成功…` 与
`Item45LogAndPasswordTests.真7z_密码复用_第二个包的第一条候选就是本批成功的那个`；
还原 ⇒ 两条转绿、`AF_REDCHECK` 残留 0。

### 25.6 读数（红名单差集为唯一判据）

- 定向 `PasswordReuseTests` + `Item45LogAndPasswordTests`（18 条）：**4 红 / 14 绿 → 2 红 / 16 绿**。
- 全量 **92 红 / 2898 通过 / 13 跳过 / 3003 总 / 8 分 38 秒**（上一轮 94 红 / 2896 通过 / 13 跳过 / 3003 总）
  ⇒ 差集 = **转绿 2 ＋ 新增红 0**。`dotnet format --verify-no-changes` 退出 0。
- 剩下的两条 `Item45LogAndPasswordTests`（`真7z_文件名也加密且密码排在后面_空密码照样跳过`、
  `真7z_先试错两个候选再成功_成功档照样只留一行`）**与本刀无关**：红检时它们照旧红，修好后照旧红。

## 26. 已落（2026-10-16）：**递归内核的候选循环从不校验产物** —— 0 字节桩把正确密码挡在门外

### 26.1 症状与运行期事实（探针读数）

- 红：`OutputVerificationGateTests.第一个候选产出0字节_第二个候选正确_最终成功且两个候选都试过`，
  逐字 `Expected: "解压成功" / Actual: "解压失败"`。
- 探针（用例内倒出结果 + 整份日志，读完即删）逐字：

```
Status=解压失败 | Outcome=Failed | OutputVerification=Failed
ErrorMessage=产物校验未通过：产物为空 —— 预期 2 个文件 / 20 字节，实际 2 个 / 0 字节（解出来的全是 0 字节文件）
Passwords=wrong-one
```

  日志里只有 `├ 第 0 层：pack.7z：开始解压，密码候选 1/2，尝试密码列表第 1 项：******`，
  且**没有**「这个候选不算数，继续尝试下一个候选密码」那一行 ⇒ **只试了 1 个候选**，
  第二个（正确密码）一次都没被试过。

### 26.2 根因（一句话）

默认档「有压缩包就解压」把解压交给递归内核 ⇒ 内核的候选循环在 `result.Success` 上**直接 break 接受**，
**从不校验产物**；校验只发生在协调器收尾（整单一次）⇒ 第一个候选留下两个 0 字节桩文件时，
整单落「解压失败」，而正确密码那个候选再没有机会。单层路在同一个形状上有一档
「校验判否 ⇒ 这个候选不算数 ⇒ 清掉它写下的东西 + 接着试下一个」。

### 26.3 落了什么（内核一处判据 + 一个新出口）

- 新出口 `RecursiveExtractor.CandidateProductsVerified(item, candidateManifest, out message)`：
  判据转调**同一个** `OutputVerifier.Verify`（⛔ 不另写一套尺子）；清单取 `candidateManifest`
  ——「解开它的那个候选」自己列出来的那一份，与层报告"采信成功那个候选的清单"同口径；
  清单取不到 ⇒ 给一份 `Success = false` 的预期（`OutputVerifier` 退化成"只做非空校验"），
  ⛔ **不是**"期望 0 个 / 0 字节"（那等于把任何产物都放过）。
- 候选循环里判否 ⇒ 一行 WARN（**与单层路逐字同一句**：「…（这个候选不算数，继续尝试下一个候选密码）」）
  ＋ `TryResetLayerOutputDirectory`（既有出口，它的注释本来就写着"换密码候选之前调用"）＋ `continue`。
- **两条例外**（与单层路同源）：**产物越界**（更具体的原因交给收尾的落点校验去报）、
  **没有下一个候选**（这一条是最后一个 / 已到每层尝试上限 ⇒ 产物留着交给收尾说清为什么失败，⛔ 不许清）。

### 26.4 ⚠ 一处实测教训（写死，这是本轮第二次被既有守门救回来）

第一版把"没有下一个候选"写成 `lastConsumedCandidateIndex >= candidates.Count`，而这个下标是
**0 起**的（初值 `-1`，每进一次循环 +1）⇒ **最后一个候选也被判成"还有下一个"** ⇒
0 字节产物被清掉、整层落「密码错误」。**既有守门当场逮住**：
`OutputVerificationGateTests.假引擎成功但产物全是0字节_不是成功_不续解_不搬其余物_源包不动`
逐字 `Expected: "解压失败" / Actual: "密码错误"` ⇒ 改成 `>= candidates.Count - 1` 后回绿。
⇒ 又一次印证 AGENTS 那条：**一处改动把既有守门打红 ⇒ 先怀疑"改错了层 / 写错了判据"**，别去改用例。

- 定向三族（`OutputVerificationGateTests` + `ExtractionPipelineFixTests` + `PasswordReuseTests`，51 条）：

### 26.6 ⚠ 仍未做（半绿的那一条，下一刀）
