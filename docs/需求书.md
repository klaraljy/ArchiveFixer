# 归档识别、智能解压与多引擎任务处理工具

## 产品需求、架构设计与 AI 开发总任务书

---

# 一、项目总体定位

本项目是一款运行在 Windows 平台上的本地归档处理工具。

它面向普通用户，但内部需要具备较强的工程可靠性，用于处理以下类型的问题：

- 文件没有扩展名；
- 文件扩展名被错误修改；
- 文件拥有多个伪装后缀；
- 用户不知道某个文件到底是什么格式；
- 一个目录中混有大量普通文件和压缩包；
- 用户需要批量识别和处理压缩包；
- 压缩包中还包含其他压缩包；
- 多层压缩包使用不同密码；
- 压缩包存在分卷；
- 压缩包部分损坏；
- 外部解压工具支持范围不同；
- 解压中途发生错误；
- 解压结果需要清晰整理；
- 用户需要知道任务到底成功了多少；
- 解压过程中需要保护源文件和用户已有文件。

软件不是简单的批量重命名工具，也不是只把 7-Zip 命令行套上一层 GUI。

软件的长期定位是：

> **一个能够识别真实归档格式、分析文件名伪装、批量修正后缀、验证归档内容、执行安全解压、自动处理合理嵌套、管理密码和分卷、支持多种解压引擎，并为每个任务提供可追踪结果的 Windows 桌面工具。**

---

# 二、产品核心目标

产品需要解决的核心问题不是“能不能解压一个 ZIP”。

而是下面这些连续问题：

```text
这个文件到底是什么格式？
它的扩展名是否可信？
文件是否损坏？
是否需要密码？
是否属于分卷归档？
应该使用哪个解压引擎？
解压后是否还存在下一层归档？
是否应该继续递归？
递归是否会产生过多文件？
是否会覆盖用户文件？
中途失败后能否继续？
最终结果是否完整？
源文件有没有被修改？
用户能否看懂处理结果？
```

软件最终应使用户能够完成这样的操作：

```text
把一批未知文件或文件夹拖入软件
→ 软件自动扫描和识别
→ 显示真实格式及伪装情况
→ 用户预览或执行批量改名
→ 测试和解压
→ 自动处理合理的多层嵌套
→ 管理密码和分卷
→ 发现异常时暂停或询问
→ 最终输出整理好的文件
→ 查看完整报告和失败列表
```

# 四、核心概念模型

```text

某个任务的中间工作区。

负责识别、测试、列目录和解压的具体引擎。

StorageLocation：
文件所在的本地磁盘、移动磁盘、网络共享或其他存储环境。

TaskResult：
任务最终结果。

FailureRecord：
结构化失败信息。
```


# 八、批量改名系统

改名必须是一个独立模块。

---

## 改名计划

在真正改名前生成计划：

```cpp
struct RenameOperation {
    Path source;
    Path target;
    RenameReason reason;
    RenameStatus status;
    std::string error;
};
```

用户需要看到：

```text
原名称
新名称
改名原因
是否冲突
是否需要临时名称
是否可以执行
```

---

## 改名规则

支持：

```text
自动添加推荐扩展名
替换错误扩展名
删除多余扩展名
保留复合扩展名
只改最后一个扩展名
根据真实格式重命名
使用用户指定后缀
```

必须避免破坏：

```text
archive.tar.gz
archive.part1.rar
archive.7z.001
```

例如：

```text
archive.tar.gz
```

不能被错误改成：

```text
archive.gz
```

除非用户明确选择只处理最后一层。

---

## 改名冲突

必须处理：

```text
A.jpg → A.zip
A.zip 已存在
```

默认策略：

```text
跳过或自动生成新名称
```

不能默认覆盖。

名称交换：

```text
A.zip → B.zip
B.zip → A.zip
```

需要使用临时名称：

```text
A.zip → .temporary-name-1
B.zip → .temporary-name-2
temporary-name-1 → B.zip
temporary-name-2 → A.zip
```

普通一层解压流程：

```text

```

# 十、智能递归解压

递归解压是本项目的重要功能，但必须有明确策略。

递归不是：

```text
只要发现里面还有压缩包，就无限解压。
```

正确流程是：

```text
解压一层
→ 分析当前层输出
→ 判断是否存在内层归档
→ 计算内层归档数量
→ 检查资源预算
→ 检查安全风险
→ 根据递归模式决定是否继续
```

---

## 三种递归模式

### 1. 单层模式

只解压当前归档。

### 2. 单链模式

默认推荐。

只有发现一个主要内层归档时自动继续。

例如：

```text
outer.zip
└── inner.7z
    └── data.tar
        └── files
```

### 3. 全部分支模式

处理所有内层归档。

例如：

```text
outer.zip
├── A.zip
├── B.7z
└── C.rar
```

全部处理。

启用前必须显示：

```text
检测到 3 个内层归档
预计最多产生 3 个子任务
可能需要多个密码
可能产生大量输出
是否继续？
```

---

# 十一、递归分支判断

需要定义“主要归档”的判断规则。

可以根据以下因素判断：

```text
文件是否为归档
文件大小
文件所在目录
是否为唯一归档
是否与外层任务名称相关
是否存在旁路说明文件
```

以下情况可自动继续：

```text
只有一个内层归档
其他文件只是说明文件
没有安全风险
没有达到资源限制
```

以下情况默认暂停：

```text
多个同级归档
归档数量很多
内层归档位于多个目录
存在多个密码请求
预计输出过大
发现疑似循环嵌套
```

暂停时提供：

```text
继续当前主归档
展开全部
停止递归
查看当前层
选择特定归档
```

---

# 十二、递归停止条件

递归遇到以下情况必须停止或暂停：

```text
达到最大嵌套层数
达到最大输出大小
达到最大文件数量
达到最大单文件大小
达到最大展开比例
密码尝试次数超限
检测到循环归档
检测到路径不安全
发现分卷缺失
源文件发生变化
设备离线
目标空间不足
用户取消
引擎不支持
```

停止后必须保存：

```text
当前层
已完成层
未处理的内层归档
工作区位置
失败原因
已输出文件数量
已输出字节数
```

不能把递归停止简单显示为“失败”。

应该区分：

```text
已完成
部分完成
等待用户选择
受安全策略阻止
资源限制停止
用户取消
设备离线
引擎不支持
```

# 十四、最终结果整理和发布

递归处理不应直接向用户最终目录不断写入。

建议：

```text
所有中间结果写入工作区
递归完成后进行整理
完成安全检查
完成结果统计
最后发布到目标目录
```

最终发布前检查：

```text
是否存在路径冲突
是否存在危险文件
是否超过目标卷空间
是否存在未完成层
是否存在未确认内容
是否需要合并目录
```

发布状态：

```text
WaitingForPublish
Publishing
Published
PartiallyPublished
PublishFailed
```

跨卷发布：

```text
工作区 → 目标目录
```

必须：

```text
复制
→ 文件大小检查
→ 必要时哈希验证
→ 记录已发布文件
→ 成功后清理工作区
```

如果发布中断：

```text
保留工作区
保留已发布文件清单
保留未发布文件清单
允许继续发布
```

# 十五、密码处理

密码模型不能只有一个全局字符串。

建议分为：

```text
TaskPassword：
当前任务使用的密码。

LayerPassword：
当前递归层使用的密码。

PasswordList：
用户配置的密码列表。

RecentSuccessPassword：
当前任务中最近成功的密码。

TemporaryPassword：
只在本次运行期间有效的密码。
```

每层可能使用不同密码。

密码尝试顺序可以是：

```text
空密码
当前层最近成功密码
当前任务密码
全局临时密码
密码列表
```

必须设置上限：

```text
每层最大尝试次数
```

```text
密码列表内容
带密码的完整命令
```

# 十七、多引擎架构

核心业务必须依赖抽象接口，而不是具体程序。

建议定义以下接口：

```cpp
class IArchiveEngine {
public:
    virtual ~IArchiveEngine() = default;

    virtual std::string id() const = 0;

    virtual std::string display_name() const = 0;

    virtual EngineVersion version() const = 0;

    virtual EngineCapabilities capabilities(
        const ArchiveDescriptor& archive) const = 0;

    virtual ProbeResult probe(
        const ArchiveRequest& request) = 0;

    virtual ListResult list(
        const ArchiveRequest& request,
        IProgressSink& progress,
        std::stop_token stop_token) = 0;

    virtual TestResult test(
        const ArchiveRequest& request,
        IProgressSink& progress,
        std::stop_token stop_token) = 0;

    virtual ExtractResult extract(
        const ArchiveRequest& request,
        const ExtractionPolicy& policy,
        IProgressSink& progress,
        std::stop_token stop_token) = 0;
};
```

核心模块应该只调用：

```text
probe()
list()
test()
extract()
```

不应该出现：

```text
直接拼接 7z.exe 参数
直接解析 7-Zip 文本输出
GUI 中判断 7-Zip 错误字符串
递归逻辑中写 WinRAR 参数
```

# 十八、引擎能力模型

```cpp
struct EngineCapabilities {
    bool can_probe = false;
    bool can_list = false;

    bool can_extract = false;
    bool supports_password = false;
    bool supports_multi_volume = false;
    bool supports_streaming = false;
    bool supports_large_files = false;
    bool preserves_unicode_names = false;
```

格式能力不是简单的：


```text

支持普通密码
支持 AES 密码
支持大文件
支持 Unicode
支持流式处理
```

不同版本的同一个引擎能力也可能不同，因此需要记录：

```text
引擎名称
引擎版本
格式
操作类型
能力结果
测试样本
已知问题
```

# 二十一、外接磁盘和网络路径

外接磁盘是一个重要兼容场景，但不应改变软件的核心任务模型。

核心业务应该只看到：

```text
读取一个源文件
写入一个工作区
发布到一个目标目录
```

至于路径属于：

```text
本地 SSD
移动硬盘
U 盘
SD 卡
网络共享
UNC 路径
```

应该由存储层处理。

需要支持：

```text
NTFS
exFAT
FAT32
移动硬盘
U 盘
SD 卡
USB SSD
UNC 路径
网络共享
盘符发生变化
设备暂时离线
目标空间不足
源设备只读
```

默认策略：

```text
源文件只读打开
不默认在源目录创建工作区
不默认删除源文件
任务开始前检查源文件稳定性
处理期间监控设备状态
设备离线时安全停止
重新连接后重新确认设备和文件
```

---

## 外接磁盘中的几个特殊问题

### 1. 盘符变化

不能只保存：

```text
E:\file.zip
```

还要记录：

```text
卷 GUID
卷序列号
设备身份
相对路径
文件 ID
```

恢复任务时：

```text
先确认是不是同一个设备
再确认文件是否还是同一个文件
最后才允许继续
```

### 2. FAT32 大文件限制

如果目标是 FAT32，必须提前检查：

```text
单文件是否超过 4GB
```

不能等写入失败后才提示。

### 3. 设备断开

设备断开后：

```text
停止新的 I/O
停止当前引擎
保留工作区
记录已完成内容
任务标记为 DeviceOffline
不显示成功
```

重新连接后：

```text
重新检查设备
重新检查文件
重新检查目标路径
由用户确认是否继续
```

### 4. 外接设备空间

必须分别统计：

```text
源设备剩余空间
工作区设备剩余空间
目标设备剩余空间
```

外接磁盘是重要的使用场景，但这些检查属于存储适配层，不应散落到识别、递归和 GUI 逻辑中。

# 二十三、任务暂停、中止和恢复

必须区分以下操作。

## 暂停新任务

当前任务继续，但不再启动新任务。

## 停止当前任务

请求当前引擎安全停止。

## 停止批次

当前任务完成后不再开始新任务。

## 立即取消

终止当前外部进程，保留工作区和日志。

## 清理任务

只有用户确认后才清理工作区。

# 三十二、必须保证的不变量

```text
1. 默认不修改源文件。
2. 默认不删除源文件。
3. 默认不覆盖已有文件。
4. 改名和解压是两个独立操作。
5. 识别结果不会被扩展名覆盖。
6. 解压结果不会越出工作区。
7. 路径安全检查不会被外部引擎绕过。
8. 密码不会进入日志、报告和普通状态文件。
9. 部分提取不会显示为完整成功。
10. 设备离线不会显示为成功。
11. 源文件变化后不会继续使用旧识别结果。
12. 分卷缺失不会开始不可完成的任务。
13. 递归不会无限执行。
14. 多分支递归不会默认无限展开。
15. 外部进程退出后资源都会释放。
16. 清空任务不会误删工作区之外的文件。
17. GUI、CLI 和核心库采用相同业务规则。
18. 新增引擎不需要修改递归核心。
19. 工作区、源文件和最终输出相互独立。
20. 所有最终结果都可以追溯到具体任务和具体引擎。
```

```text
本阶段目标
涉及模块
不涉及模块
设计假设
需要修改的文件
需要新增的接口
需要新增的测试
潜在兼容风险
```

每次开发后输出：

```text
实际修改的文件
核心逻辑说明
接口变化
编译命令
运行命令
测试命令
测试结果
已知问题
未完成事项
下一阶段建议
```

如果需求或现有代码不明确，AI 必须：

```text
指出缺失信息
列出合理假设
基于假设给出最小方案
不要把假设伪装成已确认需求
```

不要一次生成：

```text
完整 GUI
全部引擎
完整递归
所有设置
所有测试
```

正确方式是：

```text
先稳定核心模型
→ 再做一层流程
→ 再做递归
→ 再做安全
→ 再做多引擎
→ 再做便利功能
```

# 三十四、最终产品主线

本项目最终应该按照以下主线发展：

```text
文件导入
→ 文件内容识别
→ 真实格式判断
→ 后缀状态分析
→ 改名预览
→ 安全批量改名
→ 完整性测试
→ 普通批量解压
→ 智能单链递归
→ 多分支递归确认
→ 密码和分卷管理
→ 失败分类
→ 备用引擎重试
→ 工作区恢复
→ 结果整理
→ 最终发布
→ 报告和统计
```

外围支持能力包括：

```text
本地磁盘适配
外接磁盘适配
网络路径适配
设备断开处理
空间检查
盘符变化处理
```

这些能力非常重要，但它们服务于主流程，而不是替代主流程。

# 三十五、最终产品价值

本项目真正有价值的地方不是：

```text
支持多少个扩展名
```

也不是：

```text
捆绑多少个解压工具
```

而是：

```text
用户不需要先猜格式
用户不需要手动改很多次后缀
用户不需要一层层手工寻找压缩包
用户不需要自己判断每一层是否损坏
用户不需要记住当前使用哪个引擎
用户不需要担心任务是否完全成功
用户能够看到清晰的失败原因
用户能够在中断后恢复或重试
用户的源文件和已有文件不会被轻易破坏
```

最终产品可以概括为：

> **让用户用尽可能少的操作，可靠地处理复杂、伪装、嵌套、加密、分卷和格式混杂的归档文件，同时保证过程可控、结果可追踪、失败可恢复、引擎可扩展。**
