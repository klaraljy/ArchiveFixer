## 0. 一页速览：能分发什么、不能分发什么

| 工具 | 谁提供 | 能不能随包分发 | 能不能调用 | 本版状态 |
|---|---|---|---|---|
| **`7z.exe` + `7z.dll`**（7-Zip 26.03） | **我们内置**在 `ArchiveFixer/tools/7zip/` | ✅ 可以（LGPL：未修改 + 随包带许可文本 + 说明如何取得对应源码） | ✅ 通用引擎（zip / 7z / tar / iso… 都走它） | **已接线**（`Engines/SevenZip/SevenZipEngine`） |
| **`UnRAR.exe`**（RARLAB 官方解压件，7.23 稳定版） | **我们内置**在 `ArchiveFixer/tools/unrar/`（附 `license.txt`） | ✅ 可以：许可第 2 条明确允许随其它软件包分发（**必须带许可文本**），且**不得**用于造一个 RAR 压缩器 | ✅ RAR 侧的第二引擎，默认优先级在 7-Zip **之前** | **已内置 + 已接线**（`Engines/WinRar/UnRarEngine`） |
| **`Rar.exe` / `WinRAR.exe`**（共享软件 / 简体中文非商业个人版） | 用户自装 | ⛔ **绝不分发、绝不捆绑**（其许可本身禁止再分发与捆绑） | ✅ 只允许"**用户自装、我们检测与调用**"（`AGENTS.md` §3.1）—— 且**只读同目录的免费件 `UnRAR.exe`**，绝不调用这两个 | 探测已落地（`ToolLocator.WinRarInstallationCandidates`）；两个 exe 本体永不触碰 |
| `C:\Program Files\WinRAR\7zxa.dll` | WinRAR 自带（其实是 **7-Zip 的只解压 DLL**） | ⛔ 不是我们的文件，不碰、不拷 | ⛔ **不需要**：我们自带 `7z.dll` | 不涉及 |

**一句话**：我们内置 **7-Zip（通用）** 与 **RARLAB `UnRAR.exe`（只管 RAR）** 两个引擎；
`Rar.exe` / `WinRAR.exe` 一律走"**用户自己装、我们只检测与调用**"，
而且所有引擎**只解压、绝不改包**（README「设计边界」的承诺，`AGENTS.md` §6 不变量 1/4/5）。

## 1. 我们的位置（先把边界说死）

1. **不捆绑、不默认依赖、不替用户装任何东西、不做安装包 / 自更新**（`AGENTS.md` §2 非目标）。
   WinRAR 许可证本身就禁止捆绑与再分发（`docs/WinRAR功能参考.md` §5.2 第 2 条），
   所以这条不是取舍，是**硬边界**：想捆也捆不了。
   唯一允许的"探测"是**只读地看一眼用户自己装的 WinRAR 目录里有没有免费件 `UnRAR.exe`**
   （`AGENTS.md` §3.1 的"用户自装、我们检测与调用"），探测本身不改动系统、不装任何东西。
2. **只读归档**：所有引擎都**只用于解压（读）**。我们不实现建包、修包、改注释、改分卷、锁包 ——
   所以任何第二引擎也**只允许接它的解压能力**，不得因为"它有 `a`/`d`/`u` 命令"就顺手接进来。
3. **外部工具路径只有一个来源**：`Engines/ToolLocator.cs`（`AGENTS.md` §3.1）。
   禁止在任何别的文件里再拼一遍 exe 路径 —— 一旦有两处，"这次到底用的哪个引擎"就说不清了。
4. **能力按引擎版本记录**（`AGENTS.md` §3.1、设计.md §十八）：引擎名 / 版本 / 格式 / 操作 /
   能力结果 / 测试样本 / 已知问题。同一个引擎不同版本能力可能不同，不能只写一次"支持 RAR"。
5. **回退规则照设计.md §二十**：可换引擎的只有 `UnsupportedFormat` / `UnsupportedFeature` /
   `EngineUnavailable` / `ParserRejected` / `KnownCompatibilityIssue`；
   `WrongPassword` / `MissingVolume` / `UnsafePath` / `NoDiskSpace` / `PermissionDenied` /
   `SourceChanged` / `DeviceOffline` / `UserCancelled` / `OutputLimitExceeded` **换引擎也没用，直接报给用户**。
   备用引擎只解出一部分时，状态必须是 `PartiallyCompleted`，**不得显示 Completed**（不变量 6）。

## 2. 内置 7-Zip（`tools/7zip/7z.exe` + `7z.dll`，26.03）

- **现状**：**通用引擎**（能处理格式最多的那个），走命令行（`Engines/SevenZip/SevenZipProcessRunner`）；
  任何没被专用引擎认领的格式都由它兜底。`7z.dll` 的**进程内调用是预留通道**
  （只做了存在性检查），第一版不做。
- **版本**：随包的是 **26.03 (x64)**（发布日 2026-09-03），来源、SHA256 与升级步骤见
  `ArchiveFixer/tools/7zip/README.md`。⚠ 早期文档里的"26.01"是**上一个内置版本**的记录，
  以 `tools/7zip/README.md` 为准。
- **许可证**：7-Zip 主体是 **LGPL**，其中 RAR 解码部分带 **unRAR restriction**（见下）。
- **分发义务（LGPL）**：
  1. 随包附上 **7-Zip 的许可文本**（`License.txt` / `DOC/License.txt` 一类）；
  2. 我们是**未修改原样**内置的（`AGENTS.md` §3.1 已写明），因此不需要附带我们的修改；
  3. 说明如何取得对应源码（指向 7-Zip 官方发布页即可）—— 分发前把这三件事一起做完。
- **`unRAR restriction` 的边界**（要点，原文为准）：7-Zip 的 RAR 解码源自 UnRAR 源码，
  允许在任何软件里**免费处理 RAR 归档**，但**不得**用它去开发 RAR（WinRAR）兼容的**压缩器**，
  也不得用它反向重建 RAR 压缩算法。
  → 我们的用法（**只解压**）正落在这条允许里；**将来也绝不允许**把 RAR 解码拿去做压缩。
- **已知的诚实边界**：`7z.exe` 是独立进程，**它自己的落盘我们看不见**
  → 两道防线只能是"解压前条目预检 + 解压后落点校验"（`README.md` 已知限制第 4 行）。
  第二引擎同样适用这条，不要以为换个引擎就有了额外保障。

## 3. RARLAB 的 `UnRAR.exe`（**现役的第二引擎**）

- **它是什么**：RARLAB 官方的**解压专用**命令行 / DLL（`unrar x`、`unrar l`、`unrar t`），
  与共享软件的 `Rar.exe`（会压缩、受试用 / 注册限制）**不是一回事**。
- **为什么它是 RAR 侧的合理选择**：**免费可用于解压**，格式支持最正（RAR5、加密文件名 `-hp`、
  分卷、恢复记录都在），而且用户机器上常常已经装了 WinRAR —— 它自带的 `UnRAR.exe` 就在同一个目录里。
- **许可要点**（原文为准）：
  1. 解压用途**免费**；
  2. **不得**用于开发"RAR 兼容压缩器"或反向重建 RAR 压缩算法（与 unRAR restriction 同源）；
  3. 分发（含随包分发）**必须附带其许可文本** —— 我们**已经内置**，
     所以 `license.txt` 随 `tools\unrar\` 一起分发（发布清单里逐条过 §6）。
- **接线现状**（原来写的是"写给将来的实现者"，现已落地，逐条对照）：
  1. ✅ 只接**解压侧的能力位**，入口仍是 `IArchiveEngine` 的四件事（probe / list / test / extract）：
     `Engines/WinRar/UnRarEngine`；`Extraction/` 与 GUI 里**没有**任何 `unrar` 参数拼接
     （`AGENTS.md` §3.1 四条禁止项）；
  2. ✅ 路径来源只在 `ToolLocator` 里：**用户自选 → 已装 WinRAR 目录 → 内置 `tools\unrar\`**；
     "当前在用哪个引擎、为什么"在设置窗口的引擎列表里能看到（设计.md §十九的"显示当前是否在用"），
     启动日志里还有一行 `引擎分派（按格式与优先级…）`；
  3. ✅ 输出解析（退出码 / 加密头标志 / 缺卷点名 / 错误分类）都待在 `Engines/WinRar/` 内，
     统一映射成既有错误码；退出码表参考 `docs/WinRAR功能参考.md` §1.15；
  4. ✅ 界面与报告只做**事实性说明**（名字写作"UnRAR 命令行（RARLAB 解压工具）"、
     "使用内置 UnRAR：…（版本 7.23.0）"），**不用** WinRAR / RAR 的名称或图标做宣传性表述；
  5. ✅ 密码只存内存；命令行 `-p<明文>` 的固有限制照旧（不变量 5、README 已知限制第 1 行）。
- ⚠ **诚实交代一处能力边界**（实测，2026-09-22）：早期文档指望的"7-Zip 解不开 `-hp`"**不成立** ——
  带正确密码时 7-Zip 26.01/26.03 能解 RAR4/RAR5 的 `-hp`（含分卷）。
  这个引擎真正的增量在**分类与报错更准**：缺卷时它直接点名缺哪一卷、加密头有显式标志
  （`Details: RAR 5, encrypted headers`），而 7-Zip 只会说 "Cannot open the file as archive"。

## 4. `Rar.exe` / `WinRAR.exe`：共享软件，**绝不分发**

- **绝不做的四件事**（`AGENTS.md` §2 / §3.1）：捆绑、默认依赖、自动探测安装、复制其任何文件进本仓库。
- **`AGENTS.md` §3.1 保留的位置**只有这一种形态：
  **用户自装、自选路径，程序只检测与调用，并在界面显示当前是否在用**（正式分发前核对许可证）。
- **为什么这条没有商量余地**：本机这份许可（《简体中文 RAR 非商业个人版最终用户许可协议》）
  明确禁止再分发单独部分、禁止放进其它软件包分发、**禁止任何形式的捆绑**，
  并且限**自然人非商业**用途、不得去除其广告对话框（`docs/WinRAR功能参考.md` §5.2）。
  换句话说：即使将来想做 `Rar.exe` 支持，也只能是"读用户自己装的路径 + 传参调用"。
- **本仓库里没有任何它的二进制**（`tools\` 下只有 LGPL 的 7-Zip 与 freeware 的 `UnRAR.exe`）。
  ⚠ **2026-09-23 更正一句旧话**：这里曾写"源码里没有一处会去打开 `Rar.exe` / `WinRAR.exe`（grep 零命中）"——
  打包功能（2026-09-22）落地后已经不成立：**只有**本机装了 WinRAR 时，
  `PackingService` 才会调用**用户自己装的**那一份（路径由 `ToolLocator` 解析：自选 → 已装 WinRAR 目录）；
  **没有就自动改用内置 7-Zip 做外层**（产物 `源名.7z`，2026-09-26 第 46 条改口径）。
  它**只被调用**：不复制、不内置、探测只读。
- **RARLAB 官方 EULA 的依据**（2026-09-23 查证，用于回应用户"能不能随包发 `Rar.exe`"）：
  §3.1 只允许单独分发 **UnRAR 组件**、§3.2/§3.3 不得放进任何其它软件包（**Any bundling is interdicted**）、
  §10 不得分发 licensed software 的 **any subset**。→ 结论与本节一致，且正是"打包的外层
  **必须有一条不依赖 WinRAR 的出路**（内置 7-Zip）"的原因（见 `docs/打包功能.md` §5.1、§5）。

## 5. `C:\Program Files\WinRAR\7zxa.dll` 是什么，以及为什么我们不需要它

- 它是 **WinRAR 自带的第三方组件**：来自 **7-Zip** 的**只解压 DLL**（LGPL 2.1 或以后），
  WinRAR 用它来解压 `.7z` 归档（`docs/WinRAR功能参考.md` §5.2 第 7 条 / §5.3 第 2 条）。
- **我们不需要它**：我们已经自带完整的 `7z.exe` + `7z.dll`（同一个上游项目，且版本更新、功能更全）。
  去借用 WinRAR 目录里的那份 DLL，只会把"我们的引擎来自哪里"搅浑，还多一层许可与版本不确定性。
- 顺带一个**有用的旁证**（不是结论）：WinRAR 在自己的闭源产品里未修改地使用 7-Zip 的 LGPL 组件来解压 7z，
  说明"未修改地使用 7-Zip 的解压组件"在 LGPL 下是被接受的做法。
  但**我们的形态不同**（内置的是独立可执行文件，且含带 unRAR restriction 的 RAR 解码）
  → **不能靠这个旁证直接下结论**，仍需按 §2 的义务逐条核对。
