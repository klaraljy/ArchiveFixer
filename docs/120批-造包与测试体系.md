## 1. 三件东西的分工

| | 造包器 | 测试操作 | 测试检测 |
|---|---|---|---|
| 干什么 | 造 120 份样本包 + recipe | 把样本真交给 ArchiveFixer 跑一遍 | 读 recipe + 运行记录 + 磁盘，逐条判红绿 |
| 会不会改盘 | 只写备份目录 | 写测试区 `大测试\<seed>` | 只读 |
| 失败怎么办 | 该份失败，其余照造 | 该份记 error，其余照跑 | 该份红，其余照判 |
| 耗时 | 约 2.6 分钟 | 约 4.3 分钟 | 0.5 秒 |

一句话：**造包器产出"题面"（recipe）和"题"（包），操作代码去答题，检测代码判卷。**

## 3. 造包器

### 3.1 120 份构成

```
普通 50：40 成功 + 5 缺片 + 5 坏片，落点 25 Original / 25 Specified
特定 20：1–10 Original（旧 10 形状）、11–20 Specified（新增 10 形状）
异常 25：placement 全部 Original
空间 25：C01–C15（普通档）、B01–B10（特定解压档）
```

### 3.2 普通 50：8 种场景

`scenario` 三要素相乘：

```
placement      Original / Specified
sourceHandling KeepInPlace / DeleteInPlace
contentHandling Keep / Delete
```

50 份按 8 档轮转（`(n-1) % 8`），失败 10 份用 `failureCombos` + `failurePlacements` 保证总数仍是 25/25。

失败样本的破坏是**固定**的：

```
最终层固定 ZipNumbered，标准名 aaa-L4.zip.001..005
缺片：删中间 .003（剩 4 片）
坏片：五片都在，只把 .003 前 4096 字节写成 0xA5
```

### 3.3 特定 20

1–10 是旧 `大测试-造特定解压包.ps1` 的十个固定布局，逐一对照过（10/10 结构一致）。
11–20 是新增十个形状，组合互不相同：

```
11 直接单包            16 最后一层落在文件夹
12 外层即 7z 分卷      17 跨盘 ZIP（WinRAR -afzip -v1m）
13 两层单包            18 内层密码不在密码本
14 三层单包（三密码）  19 空归档
15 三层中间分卷        20 同一形状两个父目录各一份
```

### 3.4 异常 25

1–20 是旧脚本的二十个形状。旧脚本里已含「空归档」「内层分卷缺最后一卷」，所以新增的五个另选：

```
ZIP EOCD 截断 / RAR 分卷头冲突 / 7z 起始头 CRC 损坏 /
ZIP 中央目录偏移越界 / 同基名不同族强锚点
```

`expectedOutcome` 的映射规则（旧脚本的 outcome 是中文描述，不是机器值）：

```
失败/跳过/拒绝 开头              → FailedOrSkipped
成功 开头 且 含「/」或「或」      → Either（两可）
成功 开头                        → Succeeded
其余（描述性文字）               → Either
```

### 3.5 空间 25

C 用旧矩阵的结构：`packages[]` + `space{freeBytes,reserveBytes,concurrency}` + `expected{blocked,failed}`。
C 的随机序列必须与旧脚本逐位一致——旧脚本用一个 `[Random]::new(913)` 顺序消费 15 批，所以造包器**先整体重放一遍**（只算随机数不落盘），单份生成再取自己那一片。

B 补 `expectedTaskFileName(s)`，B01–B05 与旧 5 批一致，B06–B10 新增。

### 3.6 生成后自检（2026-11-09 新增）

```powershell
Assert-CreatedArchiveIntact  # 整包 7z t，不通过当场 Fail 并点名
Assert-SevenZipSignature     # 7z 头必须 37 7A BC AF
```

挂在 `New-Archive` 的十个分支和异常单包上，分卷只测首片（7z 会自己串同目录后续片）。
代价：120 份生成从 136 秒到 158 秒。

**为什么加**：917 / 918 两批都出现过"包尾部少 1–3 字节"。头是对的，只查头拦不住，必须整包测试。

### 3.7 已知坑（都是实测）

| 坑 | 事实 |
|---|---|
| 加密包不可复现字节 | 7z/rar 是 AES + 随机 IV，同输入两次密文不同、长度相同；zip 不加密则两次完全相同。所以对照只能比结构，单文件字节差 ≤128 |
| 输入时间戳会进压缩头 | 造包器把输入文件 mtime 固定成 `2020-01-01`，去掉这一路变化 |
| WinRAR 造跨盘 zip 必须带 `-r` | 不带 `-r` 时 `a -afzip -v1m x.zip *` 会产出 155 字节空包 |
| 空间 C 的 RNG 是全局序列 | 单跑 `-Only 3` 必须靠整体重放，否则随机序列错位 |
| 分卷第 2 片以后不是 7z 头 | 扫包时不能按头判断分卷 `.002+` |

## 4. 测试操作

### 4.1 每份样本的流程

```
1 读备份里的 recipe.json
2 清空并重建工作区 大测试\<seed>\<样本>，从备份复制 原包\ + recipe.json
3 重建该样本的指定位置子目录（空）
4 新建临时 DataRoot（每份一个），写 3 条密码
5 摆档位（见 4.2），装整条栈
6 导入 原包\ → OneClickCoordinator.RunAsync()（超时 5 分钟）
7 收任务终态 + 跑前/跑后文件快照
8 写运行记录，删临时 DataRoot
```

不弹窗：`DialogService` 在没有 WPF Dispatcher 时 `LogFallback` 只写日志（`DialogService.cs:1083`），确认面板用 `OptionsPromptOverride = _ => OneClickOptionsPrompt.NotShown()` 绕过。

### 4.2 档位映射

只摆三项，其余一律不动：

| 档位 | 怎么摆 |
|---|---|
| 落点 Original | `ExtractToOriginalDirectory = true`、`CustomOutputDirectory = ""` |
| 落点 Specified | `ExtractToOriginalDirectory = false`、`CustomOutputDirectory = <指定位置>\<样本>` |
| 源包 | `SourceHandling = KeepInPlace / DeleteInPlace` |
| 最后一层过程物 | `RestHandlingAfterVerify = Keep / Delete` |

普通 50 从 `recipe.scenario` 取；特定/异常/空间从 `recipe.placement` 取，源包与过程物默认 Keep。

### 4.3 两个额外档位

```
特定 20 份 + 空间 B01–B10：settings.UseSpecificExtraction = true
空间 25 份：vm.SpaceTightMode = true、vm.SpaceTightKeepSource = true、
           extraction.SpaceProbeOverride = _ => recipe.space.freeBytes、
           extraction.SpaceReserveOverride = recipe.space.reserveBytes
```

`SpaceProbeOverride` 收一个路径、返回该文件夹可用字节 —— **不需要真的把磁盘写满**，也不需要改产品。

### 4.4 硬链接保真

样本 `917200007` 靠"同一物理文件两个名字"测去重。用 `File.Copy` 会把硬链接拆成两个独立文件，样本就白造了。

复制时用 `GetFileInformationByHandle` 取 `(卷序列号, 文件索引)` 做键，第二次遇到同一文件改用 `CreateHardLink`。

### 4.5 运行记录格式

```json
{
  "SampleId": "918000001", "Category": "Normal",
  "Placement": "Original", "SourceHandling": "KeepInPlace", "RestHandling": "Keep",
  "UseSpecificExtraction": false, "SpaceTightMode": false, "InjectedFreeBytes": 0,
  "Workspace": "…\\大测试\\918000000\\918000001",
  "SpecifiedRoot": "…\\大测试指定位置\\918000000-指定位置\\918000001",
  "Before": [ { "Root": "工作区", "Path": "原包\\aaa\\L4\\片-001\\xxx.001", "Bytes": 1048576 } ],
  "After":  [ … ],
  "Tasks":  [ { "Name": "…", "Outcome": "Succeeded", "Reason": "None",
                "StatusDisplay": "解压成功 100%", "FinalContentPath": "…" } ],
  "ElapsedMs": 3210, "Error": null
}
```

`Before` / `After` 是工作区 + 指定位置的全量文件快照。检测代码不盲信它 —— 会重新扫盘对账（G6）。

### 4.6 失败隔离

每份样本独立 try/catch：一份抛异常只记 `Error`，其余照跑。
**没有断点续跑**：每次运行都会重建工作区重跑，所以一次跑完为准。

## 5. 测试检测

### 5.1 输入

`recipe.json` + 运行记录 + 磁盘现状（重新扫）。不跑产品、不改任何文件。

### 5.2 通用 G1–G8

| ID | 判什么 |
|---|---|
| G1 | 运行记录存在且 `Error == null` |
| G2 | 记录的 category / placement 与 recipe 一致 |
| G3 | 跑前快照非空 |
| G4 | 任务非空 |
| G5 | 每个任务都有终态（Pending / PartiallyCompleted 算合法） |
| G6 | **磁盘与记录对账**：重扫出的文件集合与字节必须等于记录 After |
| G7 | 不残留 `.ArchiveFixer.work` |
| G8 | Original 时指定位置必须为空；Specified 时工作区不许新增产出（改名不算新增，按基名+字节认） |

### 5.3 普通 N1–N7

| ID | 判什么 | 备注 |
|---|---|---|
| N1 | 产出落在正确落点 | Original → 源包父目录；Specified → 指定位置根 |
| N2 | 最终内容物 | 成功：`expectedFinalContentName` 存在且字节 == `expectedContentBytes`；失败：不得存在 |
| N3 | 源包保留 | KeepInPlace 全在、DeleteInPlace 全没、失败一律全在 |
| N4 | 过程物 | Delete 档必须 0；`部分完成\` 不算过程物 |
| N5 | 组状态 | `Missing` ⇒ 必须有 `FinalGroupIncomplete`；`Complete` ⇒ 不许有 |
| N6 | 终态 | 成功至少一个 Succeeded；失败至少一个 Failed |
| N7 | 失败收尾 | 坏片 + Delete 档：`其余物\` 必须清空（是否发布"部分完成"不硬要求） |

> N3 按「基名 + 字节」认源包，**不能按原名**：产品会修正伪装后缀（`aaa-W3-1.pd44` → `aaa-W3-1.rar`）。

### 5.4 特定 S1–S4

| ID | 判什么 |
|---|---|
| S1 | 每个 target 的 `sourceRelative` 还在 |
| S2 | 每个 target 的产物存在且字节对得上（按叶子名 + 字节 + 落点根，每个 target 消费不同文件） |
| S3 | `UseSpecificExtraction == true`（防回归） |
| S4 | `expectedOutcome == Failed` 的那份必须真的失败且无内容物 |

### 5.5 异常 A1–A5

| ID | 判什么 |
|---|---|
| A2 | 源包保留（异常样本一律 `expectedSourceKeep = true`） |
| A3 | 终态语义：按 `expectedOutcome`（Succeeded / FailedOrSkipped / Either） |
| A4 | 危险条目未落盘：路径穿越、Windows 保留名、docx/xlsx 受保护内部条目 |
| A5 | 压缩炸弹没被真的解出 >16MB |

### 5.6 空间 P1–P2

| ID | 判什么 |
|---|---|
| P1 | `SpaceTightMode == true` 且注入的 freeBytes 等于 recipe |
| P2 | 只硬判两档：`allblocked` 全部被挡且无产出；`ample` 全部放行且有内容。`largest` / `corrupt` 只记录不硬判（旧矩阵测试同口径：不固定断言处理次序） |

### 5.7 输出

每条检查一行：`{ SampleId, CheckId, Expected, Actual, Verdict, Note }`。
`Verdict` 只有 `Green` / `Red`。一份里有任一红 → 这份红。

## 7. 定性过的历史红项（教训）

### 7.1 坏包：文件头是分卷后续片

现象：单个 `.7z` 被产品判「分卷缺失」。查文件头：

```
坏 dup-import.7z  46 49 4C 45 = "FILE"   → 7-Zip 分卷后续片
坏 bomb.7z        52 43 52 44 = "RCRD"
正常              37 7A BC AF 27 1C 00 04
```

结论：**不是产品缺陷**，是那一次生成写进去的是分卷片，且尾部少 1–3 字节。重新生成即正常。
处理：加生成后整包 `7z t` 自检。根因仍未查清（不可复现）。

### 7.2 「部分完成」不是过程物

现象：坏片 + 其余物 Delete 档下，`片-001\aaa-L4\部分完成\` 还剩 3 个内层片，被判过程物没清。

对照发现 `部分完成\` 只在 Delete 档出现（Keep 档没有），是"部分完成发布"捞回可恢复片用的产物。
处理：N4 排除 `部分完成\`；N7 改为判 `其余物\` 必须清空。

### 7.3 两可期望值必须判 Either

旧脚本的 outcome 是中文描述：「成功/拒绝」「去重或两个独立任务」「不强行组卷」。
压成单一 Succeeded / FailedOrSkipped 就会假红。处理见 3.4 的三条规则。

### 7.4 判据不能过拟合

N7 最初写成"坏片 + Delete 档下**必须**有部分完成产物"——那是拿 917 的一次行为当规则。
918 里那三份一个片都没捞回，就红了。改成判档位语义（其余物必须清空）才成立。

**教训：判据要判"规则"，不要判"上一次观察到的现象"。**

## 8. 已知限制 / 未定

1. **坏包根因未查清**。同一份代码有时写出不完整的包，复现不了。现在靠生成后 `7z t` 兜底：一出现就在造包阶段红。
2. **空间档位只硬判两档**。`largest` 档的 `blocked` 依赖随机体积，旧矩阵测试的口径本来就是"不固定断言处理次序"，所以只记录不判。并发峰值没有数据源，P4（并发）目前不做。
3. **操作代码没有断点续跑**。中断后重跑会从头来，120 份约 4.3 分钟，可接受。
4. **S2 按叶子名 + 字节判**。落点目录名由产品决定（实测和造包器的假设不一致），所以不强求整条相对路径。
5. **硬链接只在同卷有效**。跨卷复制会退回普通复制。
6. **期望落点前缀**：所有产物路径都带 `原包\` 那一层（Specified 是 `<指定位置>\<样本>\原包\…`）。检测按后缀/叶子名判，不依赖这一层。
