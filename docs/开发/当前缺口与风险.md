# 当前缺口与风险

> 适用版本：ArchiveFixer v0.2.3  
> 最后核对：2026-11-15，代码 HEAD `8a70d9cc`  
> 状态：现行。只列当前仍存在的限制/风险；已修历史见 `修改日志.md` 与 `docs/历史/`。

## 1. 功能边界

- **普通内容物不做通用内容识别**：只有用户源包或同基名/分卷候选才走 `ContentAdmission`。因此自动路径里“改了名且没有同基名证据的内容容器”可能按归档候选处理；docx/xlsx/epub/jar 的常规后缀仍由 `ContentContainerProtection` 保护。
- **真正的 APK 不碰**；不是 APK 但含同名条目的 ZIP 仍按普通归档处理。
- **部分完成发布**默认关闭（`PartialPublishEnabled=false`）；开启后需单独验收。
- **回收站档已下线**：其余物只有保留/彻底删除。
- **自动并发实验暂停**：当前只认用户手动 1–4，实验代码在 `Experimental/AutoConcurrency/`，不参与调度。

## 2. 性能/UI

- 产物扫描已放后台，但扫描本身仍是同步文件 I/O；超大目录可能耗时，只是不阻塞 UI。
- `LargeContentScanTests` 只证明 4,000 个普通内容物不会被逐张内容识别，不替代真机 UI 计时。
- UI 响应日志依赖 `UiResponsivenessMonitor`；它只能报告“停滞时长 + 标记”，不能证明具体调用栈。
- 工作区递归删除仍可能耗时；已由 `PostProcessSuccessStep` 放进 `Task.Run`，不要在 UI 线程再包一层。

## 3. 分卷/内容识别

- 判不出卷号/缺片/族冲突时按“什么都不做”；不尝试猜测补片。
- 同基名不同组、强锚点冲突、非均匀分卷仍依赖族 resolver + 试开；失败时保留原片。
- 媒体前缀分卷不在当前识别范围；媒体前缀“完整单卷”仍支持。
- SizeAnomaly 的 prepared 组不生成候选；发现层完整组保留回退。
- 标准名 `.001删` 不再物理改名；入口层用逻辑名/硬链接；源片保留原名。

## 4. 验证环境

- 真实 336 组依赖用户密码；没有密码时只能跑同形状合成样本。
- `930000000` 批次备份在本机不存在时，30 份复跑无法执行；不能用“跳过”当通过。
- 真实样本测试可能因缺 7-Zip/WinRAR/样本而跳过。
- 全量测试通过不等于真机 UI 无卡顿；需要看 `[性能]` 日志和实际交互。
