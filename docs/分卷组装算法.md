# 分卷组装算法

> **唯一出口**：`Detection/VolumeGroupResolver.cs`（类型 `VolumeGroupResolver`；同步入口 `Resolve(VolumeGroupQuery)`，
> 带试开入口 `ResolveAsync(VolumeGroupQuery, CancellationToken)`；唯一结论类型 `VolumeGroupResolution`，
> 唯一"能不能删"出口 `VolumeGroupResolution.CanEnterDeletableRestItems`）。
> 消费方四处（+导入期一处）都只读同一份 `VolumeGroupResolution`，⛔ 不许各自再判一遍。
> 本文写的是**判据本身**：证据表、判定流程、真案 walk-through、以及**诚实的限制**。

---

## 0. 为什么必须有它

7z 分卷是**裸切**：

- 元数据（下一份头 / 编码头）只在**最后一卷末尾**；
- 第 2 卷起**没有任何格式标记** —— 它不是归档，是一段裸字节流。

所以「这一堆文件是不是同一次分卷切出来的」这个问题，**纯按内容识别对第 2 卷起必然失败**。
只能靠**证据**：名字、体积、位置、物理同一性、以及最后的**试开**。

真机两次事故（`docs/真机事故复盘.md`）：

| # | 现场 | 老判据的结论 | 后果 |
|---|---|---|---|
| ① | `111.7z.001` + 无后缀的 `111` + `111.7z.003` | 中间那卷"名字看不出来" | 误诊 / 漏认 |
| ② | `一只顶美.z01…z05` + 末卷被改名成 `一只顶美.z删除ip` | 剩下 5 卷"每一卷单看都像待续解的过程物" ⇒ 全进**可删的其余物** | 叠加「空间不足」模式的永久删除 ⇒ **25 GB 不可恢复** |

红线（`AGENTS.md` §6 不变量 1、§11.4）：**分卷要进"可删的其余物"，必须先证明整组完整**；
**判不出 ⇒ 一律不删源、不移动源**。

## 1. 证据表

判据只有六条。每条都进 `VolumeGroupResolution.Evidence`（`VolumeEvidence{Kind, Weight, Outcome, Title, Detail}`），
结论里能逐行看到"依据是什么"。

| 证据 | 怎么取 | 权重 | 判不出时怎么办 |
|---|---|---|---|
| **基名相等** | 去卷标记 + 去归档后缀之后名字相同（`StemOf`）。`111.7z.001`→`111`、无后缀的 `111`→`111`、`一只顶美.z删除ip`→`一只顶美`。「后缀不同但名字一定相同」就是这一条 | 强 | 名字里没有卷标记、同目录也没有同基名的组 ⇒ 结论 `判不出`，一个字节都不动 |
| **卷号连续** | 转调 `VolumeGroupDetector`（卷名判据的**唯一出口**）。`1..max` 之间的洞 = 有证据的缺卷 | 强 | 认不出族 / 卷号解析不出来 ⇒ `判不出` |
| **体积关系** | 除最后一卷外体积相等（裸切），最后一卷 ≤ 其余。⛔ **只对 `.00N` / `.partNN` 当硬证据**；`.z01`/`.r00` 族的首卷天然可能更短，那一档只记录 | 强 | 量不出体积 ⇒ 记 `Unknown`，**不据此下结论** |
| **物理同一性** | 同一目录 + 同一卷根；`CreateFileW`+`GetFileInformationByHandle` 取 FileId：同 FileId ⇒ 一定是同一份（硬链接 / 同一个文件的两个名字） | 强 | 跨目录 / 跨卷 / FileId 撞车 ⇒ `判不出` |
| **位置推定** | 没有卷号的候选按**体积 + 目录内位置（枚举次序）+ 时间**插进序列，一律标 `InferredByPosition` | **弱** | ⛔ 只报"推定"，**不采信**、**不据此说完整** |
| **试开确认** | 按推定的顺序在 `.ArchiveFixer.work` 里做**硬链接**交给引擎列目录 / 报头加密 | **决定性** | **没引擎** ⇒ 记 `Unknown`（**没试 ≠ 不成立**），退回前五条；**跨盘 / 拿不到工作区根** ⇒ 不试开，且**整组降为「判不出」、`CanEnterDeletableRestItems=false`**（硬链接不能跨卷是原理限制，见 §6.11） |

**结论枚举**（对外只有这四个值，没有第五档）：

| 结论 | 含义 | 可不可以进"可删的其余物" |
|---|---|---|
| `Complete` 完整 | 试开成立，或名字序号齐全且每一卷都是标准卷名 | **只有**"完整 **且** 每卷名字都标准"才行 |
| `IncompleteMissingVolume` 不完整·缺第 N 卷（有证据） | 卷号上有洞，且那一槽没有任何可采信的填充物 | ✗ |
| `IncompleteSuspected` 不完整·疑缺卷（弱证据） | 只有推定候选，或体积规律对不上 | ✗（**弱证据只报不删**） |
| `Undetermined` 判不出 | 名字对不上 / 目录读不到 / 关键事实取不到 | ✗ |

> `CanEnterDeletableRestItems` = `Verdict == Complete` **且** **没有**名字不标准的成员。
> 名字不标准 ⇒ 7-Zip 按原名根本打不开 ⇒ 删了就是不可逆的数据丢失。
> **唯一算法**是 `VolumeGroupResolver.Deletable(verdict, hasRenamedVolume)`（私有）——
> `Build(...)` 与试开那一档（`ApplyTrialOutcome`）**都转调它**，⛔ 不许两处各写一遍判据（AGENTS §9.5）。

## 2. 可复算的判定流程（伪代码级）

```
Resolve(query):
    anchor ← query.AnchorPath 的绝对路径
    若 取不到 anchor / 目录读不到 / 目录里没文件     → Undetermined（"判不出"）
    entries ← query.DirectoryEntries ?? 列目录（Path / Size / LastWriteTimeUtc / OrderIndex）

    # ① 命名归组（转调 VolumeGroupDetector，卷名判据的唯一出口）
    groups ← VolumeGroupDetector.Group(entries)
    group  ← groups 里含 anchor 的那一组
    group  ← group ?? 基名段与 anchor 相同的组        # 锚点自己不是规范卷名时的反向找法
    若 group 为空                                    → Undetermined（"名字里没有卷标记…"）

    # ② 已按名字定位的卷 + 名字层面的洞
    located ← group.Volumes 按卷号升序
    maxFound ← located 的最大卷号
    openSlots ← 1..maxFound 里没有 located 的那些卷号
    family   ← Numeric / ZipSpanned / RarOld / PartNumbered（按 TryGetFirstVolumeName 判）
    boundarySlotOpen ← family ∈ {ZipSpanned, RarOld} 且 1 ∈ openSlots   # 本体位规范名不带卷号

    # ③ 没卷号的候选（弱证据）：基名段相同 且 0 < size ≤ 满卷
    candidates ← entries 中 不在 located 且 StemOf 相同 且 体积满足上式 的那些
    fillSlots  ← openSlots + 每个多余候选开一个虚拟槽（maxFound+1 起）
    inferred   ← 候选按"大→小、目录次序、时间、名字"排序后依次占槽（边界族的 1 号槽优先）
                 注：占的是**推定**位子，全部标 InferredByPosition

    # ④ 证据逐条取（每条一行）
    Sequence          ← openSlots 为空？
    SizePattern       ← 除末卷外等大 且 末卷 ≤ 其余
    PhysicalIdentity  ← 同目录 + 同卷根 + FileId 两两不同
    TrialOpen         ← Unknown（"这一次没有试开"），真试过由 ResolveAsync 替换

    # ⑤ 落结论（顺序就是优先级）
    若 物理同一性 不成立                              → Undetermined
    若 中间槽有洞（后面还有更大卷号的卷）              → IncompleteMissingVolume(missingNames)
    若 还有槽没填 或 边界槽是推定填的                  → IncompleteSuspected
    若 名字序号之外还有等大/更短的候选（疑似续卷）      → IncompleteSuspected
    若 硬证据族的体积规律对不上                        → IncompleteSuspected
    否则                                              → Complete


ResolveAsync(query, ct):
    base ← Resolve(query)
    若 没注入试开端口 / AllowTrialOpen=false / base 判不出 → base
    若 base 的 1..max 不连续（凑不出完整顺序）             → base + "试开确认:没试"
    trial ← 试开端口(第 1 卷, 若干种排列, WorkRootDirectory)
    若 没引擎（没取到证据，没试 ≠ 不成立）              → base + "试开确认:没取到"（结论不变，退回前五条）
    若 跨盘 / 拿不到工作区根（原理上做不了硬链接）      → Undetermined（整组降「判不出」、CanEnterDeletableRestItems=false）
    若 成立                                          → Complete（一票定案；成员按引擎认的顺序重排）
    若 试过但不成立                                  → 组错；base 是 Complete 的**降级**为 IncompleteSuspected
```

**判定顺序里最关键的一条**：
> 「中间槽」的规范名**带卷号**（`.002` / `.part2`），一个没有卷号的文件**不可能**被断言成"就是那一卷"
> —— 断言了就得改用户的名字，而程序**永远不改用户的文件名**。
> 「边界槽」（`x.zip` / `x.rar` 那个本体位）的规范名**不带卷号**，"名字被改坏"落在这里最自然，所以那一档算弱证据。

## 3. 三个真案 walk-through

### 真案 ① `111.7z.001` + `111`（无后缀）+ `111.7z.003`

```
基名相等  成立   组基名 111.7z（去归档后缀后是 111）；111 的基名段也是 111
卷号连续  不成立 第 1..3 卷之间缺 111.7z.002
体积关系  成立   第 1 卷 4 KB（与 111 等大），最后一卷 512 B
物理同一性 成立  同一个目录、同一个卷根，FileId 互不相同
位置推定  成立   111（4 KB）按体积 + 位置推定是第 2 卷 —— 但它的名字里没有任何卷号，
                只当推定、不当已找到的卷（程序不改你的文件名）
试开确认  没试   同步判定不调引擎
──────────────────────────────────────────────────────────────
结论      不完整·缺第 2 卷（有证据）：缺 111.7z.002
```

**为什么不判"完整"**：第 2 卷那一槽的规范名是 `111.7z.002`（带卷号）。`111` 名字里没有任何卷号，
采信它就得先把用户的文件改名 —— 程序不做这件事。所以**如实报缺第 2 卷，并把推定与依据一起写出来**。
（若引擎试开真的成立，那一档是一票定案的"完整"，但因为它名字不标准，**照样不许进可删的其余物**。）

### 真案 ② `一只顶美.z01…z05` + 末卷被改名成 `一只顶美.z删除ip`

```
基名相等  成立   组基名 一只顶美；一只顶美.z删除ip 的基名段也是 一只顶美
卷号连续  不成立 第 1..6 卷之间缺 一只顶美.zip（.zip 是跨盘的第 1 段）
体积关系  成立   .z01…z05 等大，改成 z删除ip 的那一卷更短
物理同一性 成立  同一个目录、同一个卷根
位置推定  成立   一只顶美.z删除ip（1 KB）按体积 + 位置推定是第 1 卷
试开确认  成立   引擎按 [z删除ip, z01, z02, z03, z04, z05] 的顺序列得出清单
──────────────────────────────────────────────────────────────
结论      完整（试开确认）
可删？    否 —— 组里有名字不标准的卷，7-Zip 按原名打不开
```

**没有试开时**（导入期 / 定稿闸门）：结论是 `不完整·疑缺卷（弱证据）` —— 名字上看缺 `一只顶美.zip`，
同目录那个文件体积与位置都对得上，但名字里没有卷号。**只报不删**。

### 真案 ③ 续卷伪装成 `.mp4` / `.apk`

```
电影.7z.001（8 KB） + 电影.mp4（8 KB，其实是被改名的第 2 卷）

基名相等  成立   电影.7z 的基名段是 电影；电影.mp4 的基名段也是 电影
卷号连续  成立   第 1..1 卷一个不缺（名字上看不出后面还有卷）
位置推定  成立   电影.mp4（8 KB）按体积 + 位置推定是第 2 卷（虚拟槽 2）
──────────────────────────────────────────────────────────────
结论      不完整·疑缺卷（弱证据）—— 没试开时不许说完整
试开后    完整（一票定案），电影.mp4 是这一组的第 2 卷，名字不标准 ⇒ 不许删
```

**更短的末卷被改名**（`安装包.7z.001` + `.002` + 被改名成 `安装包.apk` 的末卷）走同一条路：
候选比名字序号还多 ⇒ 至少"疑缺卷"，⛔ 永远不许说"完整"后删掉它。

### 真案 ④ `222.zscip` + `222.z删除01`（归档本体后缀被塞了中文字符，2026-10-01 真机）

```
222.zscip（246.85 MiB，本体）+ 222.z删除01（400 MiB，第 1 片）

基名相等  成立   两者的基名段都是 222（`z删除01` 按容错档还原成 `z01`）
卷号连续  成立   第 1..2 卷一个不缺
体积关系  —      `.z01` 族首卷天然可能更短 ⇒ 这一条只记录、不当硬证据
物理同一性 成立  同一个目录、同一个卷根
位置推定  —      没有候选要推定
试开确认  —      试开在**解前预检**那一档做（有工作区根时）
──────────────────────────────────────────────────────────────
结论      完整
可删？    是（每一卷的名字都是标准卷名）── 但它**不是**"删掉源包"，
          是"整组进可删的其余物"（源包操作=放入其余物 + 其余物=彻底删除时才真删）
```

**没有试开时也叫"完整"**，凭的是**名字本身的证据**：`z删除01` 去掉中文字符就是 `z01`，
而 `zscip` 去掉 `sc` 就是 `zip` —— 归档**本体**那一档的规范名（`ExtensionHelper.TryRecoverDisguisedArchiveBody`）。

**关键区分（真案 ② 与 ④ 是同一族的两个方向）**：

- 删完之后落回**分卷标记**（`z01`）或**归档本体后缀**（`zip`）⇒ 只是"名字脏"，**组是齐的**（真案 ④）；
- 删完之后落回的是**别人**（`z01…z05` + 一个 `zip` 形态的卷）⇒ 那一卷就是**改名后的本体**，
  它在位、组齐，但**整组永远不许进可删的其余物**（真案 ②，25 GB 那次）。

⛔ **同号冲突（两个文件都声称自己是第 1 卷）**：`VolumeBucket.Add` 让**规范名优先**
（名字一字不差的那个当这一卷），另一个进 `VariantFilePaths`（算组成员、不占独立卷号、
不进推断清单）⇒ 不再出现"既说缺 `222.zip`、又说那个文件就是第 1 卷"这种自相矛盾的结论。

### 真案 ⑤ 引擎刚解出来的那一堆（定稿那两道闸门问错对象，2026-10-01 真机）

```
暂存目录（引擎这一趟解 `222.zscip.zip` 的产物）：
  222\222.zip        258845972 字节（PKZIP 跨盘的末片）
  222\222.z0sc1      419430400 字节（第 1 片，名字里塞了 `sc` / 中文）

老判据    `222.zip` 后缀像归档 ⇒ 当"待续解的过程物" ⇒ 进分卷组闸门 ⇒
          同目录那一卷名字不标准 ⇒ 判"不完整" ⇒ **整份定稿计划作废**（产物一个字节没落地）
新判据    这两个文件在**这一趟引擎的产物清单**里（`RecursionResult.FinalOutputPath` 指向的那一层）
          ⇒ 它们是**内容物**：既不是过程物，**也不进分卷组那两道闸门**
──────────────────────────────────────────────────────────────
结论      两个文件照旧搬进成品目录（落点 `222\222.zscip\222\`），源包按档处理
```

⛔ 拿不到递归结果（预检那一档）⇒ 退回老判据，一个字不变（用例 `DisguisedBodyNameTests` 里有对照组）。

## 4. 接到哪几处（都消费同一份结论）

| # | 位置 | 做什么 |
|---|---|---|
| ① | `ViewModels/ExtractionCoordinator.cs` —— `ExtractSingleTaskAsync` 里 `task.IsVolumeGroup && !task.IsVolumeComplete` 那一段（`ResolveVolumeGroupAsync` / `BuildVolumeVerdictMessage` / `LogVolumeGroupEvidence`） | **解前预检**：缺卷就别开解，直接说清**缺哪一卷 / 为什么这样判**；证据表逐行进日志。⛔ **不改变"这一单开不开"**（名字不标准 ⇒ 7-Zip 按原名打不开 ⇒ 照旧不开始），换掉的只是**诊断** |
| ② | 同上 —— `TryConfirmVolumeGroupComplete`（现在是判定器的薄壳） / `ResolveStageVolumeGroups` / `FindStageVolumeGroup` | **删除闸门**（commit `9a54d99` 那道）：判据整体搬进唯一出口，`PlanFinalLayout` 改成"**组成员只有被判定器证明整组完整且名字标准**，才允许进可删的其余物" |
| ③ | 同上 —— `IsProcessArtifactFile` 的调用点（`PlanFinalLayout` 循环里） | **可删残留分类**：⛔ 凡是被判定"属于某个分卷组"的文件，**永远不许进可删残留名单**；证明不了 ⇒ **整份计划作废**（源包与其余物的删除全部不发生） |
| ④ | 同上 —— `IsVolumePartFile` + `StageVolumeScan.EntriesFor`（`PlanFinalLayout` 循环里那道**孤儿卷**闸门） | **兜底**：带卷标记（`.001` / `.z01` / `.r00` / `.partN`）却**没落进任何一组**的文件（`VolumeGroupDetector` 会把"名字被伪装 + 尺寸不规律"的整桶丢掉）⇒ **回头逐文件问判定器**；证不出完整 ⇒ 整份计划作废。⛔ 这一档是第二轮的补丁，老写法在这里只看扩展名 |
| ⑤ | `Storage/SourceJunkScanner.cs` —— `AddResolverGroupPaths` | **导入期的"疑似无用物"提醒**：判定器认下来的组成员一个都不许出现在提醒框里（25 GB 就是被这个提醒框送进删除的）。⚠ 判据是 **`GroupFilePaths` 非空**（"认出了组成员"），**不是** `Verdict == Complete` —— 判不出时组也可能已经认出来了（同 FileId 那一档），那一档更不能放手 |
| ⑥ | `Extraction/VolumeNameRepair.cs` —— `PlanByContentAsync(..., workRootDirectory, ct)`（**必需参数**，没有默认值）＋ `PlanSevenZipByContentAsync` | **改名路的试开落点**：工作区根由调用方传进来（不变量 12），`ExtractionCoordinator.NormalizeDisguisedVolumeNamesAsync` 的两处调用点传 `_pathService.WorkDirectory`。**同盘** ⇒ 硬链接探针落在目标工作区里、改名路照旧可用；**跨盘 / 拿不到根** ⇒ 不试开、如实报"无法确认"、**不出改名计划**（⛔ 不退源卷根、⛔ 不复制、⛔ 不落程序目录 / `%TEMP%`） |

试开那一档落在 `Extraction/VolumeProbeVerifier.cs` 的 `TryOpenAsync`（端口 `VolumeTrialOpen` 定义在 Detection，
由调用方注入 —— Detection 不引用 Extraction）。**探针目录的落点只有一个来源 = 调用方传进来的工作区根**；
没有它就不做那件事（不变量 12）。

> ⛔ **"完整"有两档来源，诊断里不许混着说**：只有试开那一条证据真的
> `Outcome == Satisfied` 时，`BuildVolumeVerdictMessage` 才许写"按试开验证这一组是齐的"；
> 只靠名字/体积那五条判出来的"完整"，文案必须写成"看不出缺哪一卷 …… 没有经过试开确认"
> （第一版在这里把"没试"说成了"验过"，已修）。

## 5. 试开怎么做到**只读**（逐条对代码，⛔ 不是自述）

## 6. 诚实的限制（⛔ 不许假装做到了）

1. **跨物理盘拼不出来**。「跨卷做不了硬链接」是操作系统的硬限制：硬链接不能跨卷。
   所以源卷在 `H:`、目标目录在 `D:` 时，**试开这一档做不了** ⇒ 结论如实记 `判不出`（"无法确认"），
   ⛔ 不退到源盘卷根建探针目录、⛔ 不改退程序目录 / `%TEMP%`、⛔ 不复制文件硬凑。
   真正的"跨盘装配"需要复制（几十 GiB + 几分钟 + 空间），本程序**不做**，也不会假装能。
2. **第 2 卷起没有格式标记**。裸切的性质决定的：`内容 → 卷号` 在 7z 上**不可能**。
   本算法给的是"证据 + 试开"，不是"从内容读出来"。
3. **弱证据只报不删**。位置推定这一条永远不单独升级成"完整"；只有试开能。
4. **定稿闸门不试开**（同步路径、且不该在定稿时起进程）。后果：**靠试开才认齐的组（真案 ②）在定稿
   这一档仍然按"不完整"处理 ⇒ 那一层不定稿、什么都不搬**。方向是安全的（宁可不搬不删），
   代价是"组其实齐的、只是名字坏了"这种包最后一层走不通 —— 那是**改名**该解决的问题，不是删除该解决的问题。
5. **同基名的说明文件会被当成候选**：体积规则放宽到 `0 < size ≤ 满卷`（因为"末卷必然更短"），
   于是 `电影.7z.001` 旁边的 `电影.txt` 也会被算成候选 ⇒ 整组只到"疑缺卷" ⇒ 定稿作废。
   这是**故意**的取舍：漏掉一个被改名的末卷 = 它被当内容物搬走 + 其余卷进可删的其余物（不可逆）；
   多报一个说明文件 = 那一层不定稿（可逆，挪开那个文件即可）。
6. **同一槽有多个候选时**只试排名第一的那个（加上少量互换，上限 `MaxTrialOrderings = 8`）；
   候选很多时**不保证**穷举。
7. **识别不了"名字完全不相关"的续卷**：基名段必须相同。若某一卷被改名成完全不相干的名字
   （例如 `abc.7z.001` 的第二卷叫 `xyz.bin`），本算法认不出它 —— ⛔ 不猜。
8. **重复文件 / 硬链接**：同一 FileId 的两卷会导致 `判不出`（一份数据不能算成两卷）。
9. **落点/其余物的删除动作本身**不在这儿：本判定器只回答"可不可以进可删的其余物"；
   真删不删由既有设置（源包操作 + 删除操作 + 「空间不足」模式）决定，一个字都没改。
10. **已否决：不在源卷建探针目录**（本分支第一版干过，已整条删掉）。
    第一版的原话是"跨卷时如实退到 `<第一卷所在卷根>\.ArchiveFixer.work\volprobe-<guid>`" ——
    **协调者 2026-09-30 明确否掉**，依据是用户红线原话：
    「**这个彻底取消，用户没有定工作区的权力，就是在解压的地方设立隐形的工作区，这就完全不存在跨盘的操作**」
    ＋ 不变量 12「中间产物不得写进源目录」。在**源卷根**建目录（哪怕只含硬链接、收工即删、不碰源字节）
    正是他明令取消的那种"在别的盘开个工作区"的形态；程序中途崩掉还会在他盘上留垃圾
    （本机实测 `C:\.ArchiveFixer.work` 与 `E:\.ArchiveFixer.work` 两个空壳就是这么来的）。
    现在的口径见 §6.11。
11. **硬链接不能跨卷是原理限制，不是偷懒**：卷是文件系统的边界，硬链接是"同一份 inode/FileId 的第二个名字"，
    跨越卷就不存在这个概念。所以"试开"**天然只能在同一卷内做**，跨盘这一档不存在等价做法
    （复制 = 几十 GiB + 几分钟，本程序不做）。据此，**跨盘 / 拿不到工作区根 ⇒ 一律 `判不出`**：
    `CanEnterDeletableRestItems = false`，文案如实写「跨盘无法试开，整卷是否齐全无法确认」/「没有工作区根…无法确认」，
    ⛔ 绝不许写成"已按试开验证"。安全结论一个字不变（认成同组 + 不删、不移动、不改名），
    只是把"完整"换成如实的"无法确认"。
12. **孤儿卷兜底只覆盖带卷标记的后缀**（`.001`/`.z01`/`.r00`/`.partN`）。名字里完全没有卷标记
    又没有同基名兄弟的文件，`IsProcessArtifactFile` 本来就返回 false（它不会被当其余物删除）。
13. **本轮验证状态（如实）**：跑的是**定向**用例（分卷/无用物/管线这一片），⛔ **没跑全量**；
    真机 `H:` 上的真分卷样本**一个都没跑**（不变量：只读、本轮不碰）；GUI 没看；
    真 7z 试开那几条是**现造的合成分卷**，不是真样本。
14. **导入期保护只挂在"自己就是分卷名"的任务上**：`SourceJunkScanner.AddSiblingVolumePaths` 的前置闸门是
    `FileNameHelper.IsVolumePartFileName(task 自己的文件名)`，不满足就直接返回（连判定器都不问）——
    那是**性能**取舍（一个目录几百个任务，逐任务列目录太贵）。任务自己的路径无论如何都进保护集
    （`CollectProtectedPaths` 先收 `CurrentPath` + `VolumePaths`），所以漏的只是"非分卷名任务的兄弟"这一格。

## 8. 三族系统化识别（2026-10-04）

本节只写这一轮定下的口径：工序链、四级优先级、基名出口、7z 的内容路、还原工序的挂点、反例与红线。
草稿在 `_tmp\方案-分卷族系统化识别.md`（⛔ 不入库），真机现场与推演仍归 `docs/真机事故复盘.md`。

### 8.1 工序链（五步，顺序不许换）

**识别底层（按魔数，认不出就不猜）→ 还原名字（伪装后缀改回规范形态，替换不追加）→ 族骨架匹配 → 硬链接试开裁决 → 只改名（全成或全不成、绝不覆盖）**。

### 8.2 识别优先级四级

1. **第 0 层 魔数**：这一卷自己开头就能自证格式的先用它，认不出就往下走，⛔ 不猜。
2. **第 1 层 族专属**：**RAR 内容自述** > **跨盘 ZIP 末片索引**（`Detection/SpannedZipIndex.cs`）>
   **7z 起始头字节数 + 除末片外等大**（`Detection/SevenZipStartHeader.cs` + `Detection/VolumeContentInference.cs`）。
3. **第 2 层 名字骨架**：**卷标记段的数字就是卷号**（`Helpers/ExtensionHelper.TrySplitVolumeSegment` / `TrySplitPartNumberedVolume`）。
4. **第 3 层 最后弱线索**：**后缀段**里有 `1` ⇒ 只提"这一卷可能是首卷"当候选，⛔ **与基名里的数字无关**。

### 8.3 基名只有一个出口

`Helpers/FileNameHelper.cs` 的 `TryResolveVolumeBaseName`（5 档：组键 / 剥标记 / 包名 / 锚点 / 伪装卷）。
⚠ **组键**保留归档后缀段（`giu910.7z`）、**包名 / 锚点**剥掉它（`giu910`）是**两件事**，⛔ 别合并；
RAR 的基名 = `partN` 段**之前**的所有点段（`444.p1art2.partN.rar` ⇒ 基名 `444.p1art2`）。

### 8.4 7z：入口判据 = 这一组的名字自不自洽

`Detection/VolumeContentInference.cs` 的 `ReadSiblingShape` 三条同时成立才算自洽：**基名逐字相同 + 卷标记连续 + 除末片外等大**，
且组里真有丢名成员（⛔ 不是"入口是标准名第 1 卷就放宽"）；手上这卷没魔数就去同目录找锚点，**两个锚点 ⇒ 判不出 ⇒ 什么都不做**。
拿起始头自述的 `32 + NextHeaderOffset + NextHeaderSize` 比 Σ 卷长：**小于 ⇒ 如实报还差多少字节、一次引擎都不调**（事实位 `ByteBudgetMismatch`）；
**正好 ⇒ 整组齐（字节数证据成立）**；**大于 ⇒ 只接受唯一说得通的缩池**。

### 8.5 还原工序的两个挂点

递归层 `Extraction/VolumeNameRepair.cs` 的 `RestoreDisguisedInnerPackageNames`（**组卷之前**还原本层产物目录里的伪装名）／
批首的「智能修正后缀」（`ExtractionCoordinator.NormalizeDisguisedVolumeNamesForBatchAsync`，早于并发）。

### 8.6 反例（现场 ⇒ 结论）

| 现场 | 结论 |
|---|---|
| `111.7z.00删除文字1` | ⇒ `111.7z.001`（**替换不追加**） |
| `111.parst1.racr` | ⇒ `111.part1.rar`（**保留 `.rar`**、基名不变） |
| `444.p1art2.partN.rar` | 基名 `444.p1art2`（基名自己还带一段，⛔ 不许再拆） |
| 两片都丢名且等大 | ⇒ **定不出**（什么都不做） |
| `.txt` / `.bak` | 归**还原工序**，卷匹配器照旧不认 |
| 纯数字尾 `0012` | 不猜 |
| 名字全丢的片 > 3 | 排列爆炸 ⇒ 如实报"定不出来" |

### 8.7 红线

- **判不出 ⇒ 什么都不做**：不改名、不试开、不动源文件；
- **只改名不改内容**：一个字节都不动；
- **跨盘 ZIP ≥ 3 片的中间片顺序只有名字能回答**（内容路 ≥ 3 片直接拒绝）；
- **RAR 老式编号族 `.rar` / `.r00` 按设计不认**。

### 8.8 「去杂质」的三档与骨架命中（用户 2026-10-04 拍板）

**这一段是新口径**：凡是别处（含 `docs/真机事故复盘.md` 的历史现场）还写着"去杂质 = 删掉**最多 2 个**
非数字字符"的地方，**以本节为准** —— 那一档现在是**前两档里的第二档**，后面还有第三档。

| 档 | 判据 | 例子 |
|---|---|---|
| ① 剔非字母数字 | 段里剔掉所有非字母数字字符后整体是合法标记 | `z0删除3` ⇒ `z03` |
| ② 删 ≤2 个任意字符 | 删掉最多 2 个字符后是合法标记（被删的不许全是数字；段长 ≥5 才试删 2 个） | `00c1` ⇒ `001`、`zscip` ⇒ `zip` |
| ③ **通用骨架命中** | **已知骨架的字符在该段里按顺序出现**（且**首尾对齐**：首字符在段首、末字符在段末，杂质只夹在**中间**） | `7_______z` / `78a8fuaz` ⇒ `7z`、`0a0b1` ⇒ `001`、`ra31415926535r` ⇒ `rar` |

| ④ **卷标记段 + "取最右"**（用户 2026-10-04 第二轮拍板：「放开，但规定取最右边那个能自洽的卷标记」） | **从右往左第一个能自洽（骨架命中 + 首尾对齐 + 唯一 + 该族规则）的段当卷标记，它右边的部分当归档后缀段**；`partN` 骨架只对 `<基名>.<卷标记>.rar`（尾巴**逐字** `rar`）生效，剥完之后**左边剩下来那段照旧不吃骨架档** | `444.pa8rt1.rar` ⇒ 卷标记 `part1`、基名 `444`；**对照** `444.p1art2.part2.rar` ⇒ 仍取最右那个干净的 `part2`、基名 `444.p1art2` |

三条硬约束（⛔ 一条都不许松）：① **唯一** —— 一段能命中**多个**骨架 ⇒ 判不出 ⇒ 什么都不做
（`7zip` 同时含 `7z` 与 `zip`）；② 骨架档**只回答"这一段去掉杂质之后是什么"**，
改不改名仍由既有那几道闸门回答（同组形状自洽 / 目标名没被占 / 硬链接试开）；
③ 判不出 ⇒ 什么都不做。⛔ 纯数字尾（`0012`）与另起一段的后缀（`x.7z.001.txt` / `x.001.bak`）照旧不认。

实现只有一份：`Helpers/ExtensionHelper.TryMatchKnownSkeleton`（+ 卷标记那一份 `TryMatchVolumeMarkerSkeleton`
与 `partN` 那一份 `TryMatchPartNumberedSkeleton`），三个转调点 = 归档后缀段（`TryRecoverDisguisedArchiveBody`）、
卷标记段（`TrySplitVolumeSegmentTolerant`，"取最右"那一处由 `TrySplitPartNumberedVolume` 传
`allowPartNumberedSkeleton: true`）、归组键的后缀段归一（`FileNameHelper.NormalizeArchiveExtensionSegment`）。

**放开的代价（实测，如实记账）**：

| 代价 | 实测结果 |
|---|---|
| `x.rarity` / `x.zipper` 这种"含 `rar` / `zip` 三个字母"的普通名字 | **连"命中"都不算**（骨架没走到段末 ⇒ 首尾没对齐）⇒ ③b 那一档压根不进、不会被改名。孤立一个也成不了组 |
| `x.ra31415926535r`（首尾对齐 ⇒ 真命中） | 会被认成"本体后缀被塞了杂质的 RAR 本体"；旁边真有一组同基名分卷时**会多出一行分卷组**，但**改不了名**（卡在"建议名与每个兄弟卷的基名逐字相等"那道闸门 ⇒ `CanRepair=false`）。用例 `VolumeSkeletonMatchTests.放宽的代价_…` 把闸门链逐条钉住 |
| `444.p1art2.ra3r`（AAA 夹具那一组的形状） | 被认成"本体后缀被塞了杂质的 RAR 本体"⇒ 首卷名 `444.p1art2.rar`（改前是 `null`）。**不并组、不改那个 partN 对的基名**（`ArchiveBaseNameTests` 只改了这**一格**，`VolumeSkeletonMatchTests.AAA形状_…` 钉住） |
| ⛔ partN 骨架 | **只在"取最右"那一格放开**（见上表第 ④ 行）：`pa8rt1`（该认成 `part1`）与 `p1art2`（AAA 夹具的**基名段**，⛔ 不许认成卷标记）是**同一个形状**（字母序列都是 `part`、都夹一个数字），按形状分不开 ⇒ 只能按位置分：骨架档只作用在**最右**那个卷标记位置。红检：把这一格改回"左边剩下来那段也吃骨架档" ⇒ `444.p1art2.part2.rar` 的基名当场从 `444.p1art2` 变成 `444`（用例变红，原文见 `修改日志.md`） |
