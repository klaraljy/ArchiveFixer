# 分卷组装算法

> **唯一出口**：`Detection/VolumeGroupResolver.cs`（类型 `VolumeGroupResolver`；同步入口 `Resolve(VolumeGroupQuery)`，
> 带试开入口 `ResolveAsync(VolumeGroupQuery, CancellationToken)`；唯一结论类型 `VolumeGroupResolution`，
> 唯一"能不能删"出口 `VolumeGroupResolution.CanEnterDeletableRestItems`）。
> 消费方四处（+导入期一处）都只读同一份 `VolumeGroupResolution`，⛔ 不许各自再判一遍。
> 本文写的是**判据本身**：证据表、判定流程、真案 walk-through、以及**诚实的限制**。

---

## 0. 为什么必须有它

7z 分卷是**裸切**：

- 元数据（下一份头 / 编码头）只在**最后一卷末尾**；
- 第 2 卷起**没有任何格式标记** —— 它不是归档，是一段裸字节流。

所以「这一堆文件是不是同一次分卷切出来的」这个问题，**纯按内容识别对第 2 卷起必然失败**。
只能靠**证据**：名字、体积、位置、物理同一性、以及最后的**试开**。

真机两次事故（`docs/真机事故复盘.md`）：

| # | 现场 | 老判据的结论 | 后果 |
|---|---|---|---|
| ① | `111.7z.001` + 无后缀的 `111` + `111.7z.003` | 中间那卷"名字看不出来" | 误诊 / 漏认 |
| ② | `一只顶美.z01…z05` + 末卷被改名成 `一只顶美.z删除ip` | 剩下 5 卷"每一卷单看都像待续解的过程物" ⇒ 全进**可删的其余物** | 叠加「空间不足」模式的永久删除 ⇒ **25 GB 不可恢复** |

红线（`AGENTS.md` §6 不变量 1、§11.4）：**分卷要进"可删的其余物"，必须先证明整组完整**；
**判不出 ⇒ 一律不删源、不移动源**。

## 1. 证据表

判据只有六条。每条都进 `VolumeGroupResolution.Evidence`（`VolumeEvidence{Kind, Weight, Outcome, Title, Detail}`），
结论里能逐行看到"依据是什么"。

| 证据 | 怎么取 | 权重 | 判不出时怎么办 |
|---|---|---|---|
| **基名相等** | 去卷标记 + 去归档后缀之后名字相同（`StemOf`）。`111.7z.001`→`111`、无后缀的 `111`→`111`、`一只顶美.z删除ip`→`一只顶美`。「后缀不同但名字一定相同」就是这一条 | 强 | 名字里没有卷标记、同目录也没有同基名的组 ⇒ 结论 `判不出`，一个字节都不动 |
| **卷号连续** | 转调 `VolumeGroupDetector`（卷名判据的**唯一出口**）。`1..max` 之间的洞 = 有证据的缺卷 | 强 | 认不出族 / 卷号解析不出来 ⇒ `判不出` |
| **体积关系** | 除最后一卷外体积相等（裸切），最后一卷 ≤ 其余。⛔ **只对 `.00N` / `.partNN` 当硬证据**；`.z01`/`.r00` 族的首卷天然可能更短，那一档只记录 | 强 | 量不出体积 ⇒ 记 `Unknown`，**不据此下结论** |
| **物理同一性** | 同一目录 + 同一卷根；`CreateFileW`+`GetFileInformationByHandle` 取 FileId：同 FileId ⇒ 一定是同一份（硬链接 / 同一个文件的两个名字） | 强 | 跨目录 / 跨卷 / FileId 撞车 ⇒ `判不出` |
| **位置推定** | 没有卷号的候选按**体积 + 目录内位置（枚举次序）+ 时间**插进序列，一律标 `InferredByPosition` | **弱** | ⛔ 只报"推定"，**不采信**、**不据此说完整** |
| **试开确认** | 按推定的顺序在 `.ArchiveFixer.work` 里做**硬链接**交给引擎列目录 / 报头加密 | **决定性** | 没引擎 / 跨卷做不了硬链接 ⇒ 记 `Unknown`（**没试 ≠ 不成立**），退回前五条 |

**结论枚举**（对外只有这四个值，没有第五档）：

| 结论 | 含义 | 可不可以进"可删的其余物" |
|---|---|---|
| `Complete` 完整 | 试开成立，或名字序号齐全且每一卷都是标准卷名 | **只有**"完整 **且** 每卷名字都标准"才行 |
| `IncompleteMissingVolume` 不完整·缺第 N 卷（有证据） | 卷号上有洞，且那一槽没有任何可采信的填充物 | ✗ |
| `IncompleteSuspected` 不完整·疑缺卷（弱证据） | 只有推定候选，或体积规律对不上 | ✗（**弱证据只报不删**） |
| `Undetermined` 判不出 | 名字对不上 / 目录读不到 / 关键事实取不到 | ✗ |

> `CanEnterDeletableRestItems` = `Verdict == Complete` **且** **没有**名字不标准的成员。
> 名字不标准 ⇒ 7-Zip 按原名根本打不开 ⇒ 删了就是不可逆的数据丢失。
> **唯一算法**是 `VolumeGroupResolver.Deletable(verdict, hasRenamedVolume)`（私有）——
> `Build(...)` 与试开那一档（`ApplyTrialOutcome`）**都转调它**，⛔ 不许两处各写一遍判据（AGENTS §9.5）。

## 2. 可复算的判定流程（伪代码级）

```
Resolve(query):
    anchor ← query.AnchorPath 的绝对路径
    若 取不到 anchor / 目录读不到 / 目录里没文件     → Undetermined（"判不出"）
    entries ← query.DirectoryEntries ?? 列目录（Path / Size / LastWriteTimeUtc / OrderIndex）

    # ① 命名归组（转调 VolumeGroupDetector，卷名判据的唯一出口）
    groups ← VolumeGroupDetector.Group(entries)
    group  ← groups 里含 anchor 的那一组
    group  ← group ?? 基名段与 anchor 相同的组        # 锚点自己不是规范卷名时的反向找法
    若 group 为空                                    → Undetermined（"名字里没有卷标记…"）

    # ② 已按名字定位的卷 + 名字层面的洞
    located ← group.Volumes 按卷号升序
    maxFound ← located 的最大卷号
    openSlots ← 1..maxFound 里没有 located 的那些卷号
    family   ← Numeric / ZipSpanned / RarOld / PartNumbered（按 TryGetFirstVolumeName 判）
    boundarySlotOpen ← family ∈ {ZipSpanned, RarOld} 且 1 ∈ openSlots   # 本体位规范名不带卷号

    # ③ 没卷号的候选（弱证据）：基名段相同 且 0 < size ≤ 满卷
    candidates ← entries 中 不在 located 且 StemOf 相同 且 体积满足上式 的那些
    fillSlots  ← openSlots + 每个多余候选开一个虚拟槽（maxFound+1 起）
    inferred   ← 候选按"大→小、目录次序、时间、名字"排序后依次占槽（边界族的 1 号槽优先）
                 注：占的是**推定**位子，全部标 InferredByPosition

    # ④ 证据逐条取（每条一行）
    Sequence          ← openSlots 为空？
    SizePattern       ← 除末卷外等大 且 末卷 ≤ 其余
    PhysicalIdentity  ← 同目录 + 同卷根 + FileId 两两不同
    TrialOpen         ← Unknown（"这一次没有试开"），真试过由 ResolveAsync 替换

    # ⑤ 落结论（顺序就是优先级）
    若 物理同一性 不成立                              → Undetermined
    若 中间槽有洞（后面还有更大卷号的卷）              → IncompleteMissingVolume(missingNames)
    若 还有槽没填 或 边界槽是推定填的                  → IncompleteSuspected
    若 名字序号之外还有等大/更短的候选（疑似续卷）      → IncompleteSuspected
    若 硬证据族的体积规律对不上                        → IncompleteSuspected
    否则                                              → Complete


ResolveAsync(query, ct):
    base ← Resolve(query)
    若 没注入试开端口 / AllowTrialOpen=false / base 判不出 → base
    若 base 的 1..max 不连续（凑不出完整顺序）             → base + "试开确认:没试"
    trial ← 试开端口(第 1 卷, 若干种排列, WorkRootDirectory)
    若 没试成（没引擎 / 跨卷）                        → base + "试开确认:没取到"（结论不变）
    若 成立                                          → Complete（一票定案；成员按引擎认的顺序重排）
    若 试过但不成立                                  → 组错；base 是 Complete 的**降级**为 IncompleteSuspected
```

**判定顺序里最关键的一条**：
> 「中间槽」的规范名**带卷号**（`.002` / `.part2`），一个没有卷号的文件**不可能**被断言成"就是那一卷"
> —— 断言了就得改用户的名字，而程序**永远不改用户的文件名**。
> 「边界槽」（`x.zip` / `x.rar` 那个本体位）的规范名**不带卷号**，"名字被改坏"落在这里最自然，所以那一档算弱证据。

## 3. 三个真案 walk-through

### 真案 ① `111.7z.001` + `111`（无后缀）+ `111.7z.003`

```
基名相等  成立   组基名 111.7z（去归档后缀后是 111）；111 的基名段也是 111
卷号连续  不成立 第 1..3 卷之间缺 111.7z.002
体积关系  成立   第 1 卷 4 KB（与 111 等大），最后一卷 512 B
物理同一性 成立  同一个目录、同一个卷根，FileId 互不相同
位置推定  成立   111（4 KB）按体积 + 位置推定是第 2 卷 —— 但它的名字里没有任何卷号，
                只当推定、不当已找到的卷（程序不改你的文件名）
试开确认  没试   同步判定不调引擎
──────────────────────────────────────────────────────────────
结论      不完整·缺第 2 卷（有证据）：缺 111.7z.002
```

**为什么不判"完整"**：第 2 卷那一槽的规范名是 `111.7z.002`（带卷号）。`111` 名字里没有任何卷号，
采信它就得先把用户的文件改名 —— 程序不做这件事。所以**如实报缺第 2 卷，并把推定与依据一起写出来**。
（若引擎试开真的成立，那一档是一票定案的"完整"，但因为它名字不标准，**照样不许进可删的其余物**。）

### 真案 ② `一只顶美.z01…z05` + 末卷被改名成 `一只顶美.z删除ip`

```
基名相等  成立   组基名 一只顶美；一只顶美.z删除ip 的基名段也是 一只顶美
卷号连续  不成立 第 1..6 卷之间缺 一只顶美.zip（.zip 是跨盘的第 1 段）
体积关系  成立   .z01…z05 等大，改成 z删除ip 的那一卷更短
物理同一性 成立  同一个目录、同一个卷根
位置推定  成立   一只顶美.z删除ip（1 KB）按体积 + 位置推定是第 1 卷
试开确认  成立   引擎按 [z删除ip, z01, z02, z03, z04, z05] 的顺序列得出清单
──────────────────────────────────────────────────────────────
结论      完整（试开确认）
可删？    否 —— 组里有名字不标准的卷，7-Zip 按原名打不开
```

**没有试开时**（导入期 / 定稿闸门）：结论是 `不完整·疑缺卷（弱证据）` —— 名字上看缺 `一只顶美.zip`，
同目录那个文件体积与位置都对得上，但名字里没有卷号。**只报不删**。

### 真案 ③ 续卷伪装成 `.mp4` / `.apk`

```
电影.7z.001（8 KB） + 电影.mp4（8 KB，其实是被改名的第 2 卷）

基名相等  成立   电影.7z 的基名段是 电影；电影.mp4 的基名段也是 电影
卷号连续  成立   第 1..1 卷一个不缺（名字上看不出后面还有卷）
位置推定  成立   电影.mp4（8 KB）按体积 + 位置推定是第 2 卷（虚拟槽 2）
──────────────────────────────────────────────────────────────
结论      不完整·疑缺卷（弱证据）—— 没试开时不许说完整
试开后    完整（一票定案），电影.mp4 是这一组的第 2 卷，名字不标准 ⇒ 不许删
```

**更短的末卷被改名**（`安装包.7z.001` + `.002` + 被改名成 `安装包.apk` 的末卷）走同一条路：
候选比名字序号还多 ⇒ 至少"疑缺卷"，⛔ 永远不许说"完整"后删掉它。

## 5. 试开怎么做到**只读**（逐条对代码，⛔ 不是自述）

1. 临时物落 **`.ArchiveFixer.work`**：`VolumeProbeVerifier.VerifyAsync`（`Extraction/VolumeProbeVerifier.cs:99`）
   调 `VolumeContentInference.BuildProbeRoot(firstVolumePath, preferredWorkRoot)`
   （`Detection/VolumeContentInference.cs:412`）—— 优先 `<目标目录>\.ArchiveFixer.work\volprobe-<guid>`；
   ⚠ 与第一卷**不在同一个卷**时**如实退到**"第一卷所在卷根下的 `.ArchiveFixer.work`"
   （硬链接不能跨卷，见 §6.1；退档这件事写在代码注释里，⛔ 不许悄悄复制大文件去凑）；
2. `TryLinkAndListAsync`（`Extraction/VolumeProbeVerifier.cs:290`）用 `CreateHardLinkW`
   （`:410`）给每一卷建**第二个名字**（零字节、瞬时）；全类**没有一处** `File.Copy` / `File.WriteAllBytes` ——
   ⛔ **绝不复制大文件**（一卷 2 GiB，复制一组要几十 GiB 和几分钟）；
3. 交给引擎 `ListAsync` 列一次目录（`:325`，⛔ 只列不解）：
   - 列得出清单 ⇒ 成立；
   - 报"文件名也加密"（`EngineErrorTypes.EncryptedHeaders`）⇒ **也算成立**（引擎真读到了那一份头）；
   - 报 `Missing volume` / 打不开 / `IsRawSplitStream` ⇒ 不成立；
4. `finally` 里 `TryDelete(probeRoot)`（`:170`）把**整棵试开目录**删掉（删的是链接，源文件一个字节不动）；
5. 用例里钉住了这一条：真 7z 三卷 + 末卷改名 ⇒ 判完整，且**源文件字节与长度前后一致**
   （`VolumeGroupResolverTests.真七z_末卷被改名成别的后缀_试开能认出整组是齐的`）。

> ⚠ 第二轮实测的边界（如实写）：试开的**决定性**只体现在**诊断**上 —— 目前真正决定
> "能不能进可删其余物"的那两处（定稿闸门 / 导入期保护）都是**同步、不试开**的
> （`AllowTrialOpen = false`）。所以"试开成立 ⇒ 判完整"这条链路**今天不会**让任何文件被删；
> 它保住的是"别把齐的一组说成缺卷"。要让试开直接参与删除资格，得先想清楚同步路径怎么起进程。

## 6. 诚实的限制（⛔ 不许假装做到了）

1. **跨物理盘拼不出来**。「跨卷做不了硬链接」是操作系统的硬限制：硬链接不能跨卷。
   所以源卷在 `H:`、目标目录在 `D:` 时，试开只能退回源盘卷根下的 `.ArchiveFixer.work`；
   若连卷根都拿不到（UNC / 权限），试开那一档记 `Unknown`，结论退回前五条 —— **不会**去复制文件硬凑。
   真正的"跨盘装配"需要复制（几十 GiB + 几分钟 + 空间），本程序**不做**，也不会假装能。
2. **第 2 卷起没有格式标记**。裸切的性质决定的：`内容 → 卷号` 在 7z 上**不可能**。
   本算法给的是"证据 + 试开"，不是"从内容读出来"。
3. **弱证据只报不删**。位置推定这一条永远不单独升级成"完整"；只有试开能。
4. **定稿闸门不试开**（同步路径、且不该在定稿时起进程）。后果：**靠试开才认齐的组（真案 ②）在定稿
   这一档仍然按"不完整"处理 ⇒ 那一层不定稿、什么都不搬**。方向是安全的（宁可不搬不删），
   代价是"组其实齐的、只是名字坏了"这种包最后一层走不通 —— 那是**改名**该解决的问题，不是删除该解决的问题。
5. **同基名的说明文件会被当成候选**：体积规则放宽到 `0 < size ≤ 满卷`（因为"末卷必然更短"），
   于是 `电影.7z.001` 旁边的 `电影.txt` 也会被算成候选 ⇒ 整组只到"疑缺卷" ⇒ 定稿作废。
   这是**故意**的取舍：漏掉一个被改名的末卷 = 它被当内容物搬走 + 其余卷进可删的其余物（不可逆）；
   多报一个说明文件 = 那一层不定稿（可逆，挪开那个文件即可）。
6. **同一槽有多个候选时**只试排名第一的那个（加上少量互换，上限 `MaxTrialOrderings = 8`）；
   候选很多时**不保证**穷举。
7. **识别不了"名字完全不相关"的续卷**：基名段必须相同。若某一卷被改名成完全不相干的名字
   （例如 `abc.7z.001` 的第二卷叫 `xyz.bin`），本算法认不出它 —— ⛔ 不猜。
8. **重复文件 / 硬链接**：同一 FileId 的两卷会导致 `判不出`（一份数据不能算成两卷）。
9. **落点/其余物的删除动作本身**不在这儿：本判定器只回答"可不可以进可删的其余物"；
   真删不删由既有设置（源包操作 + 删除操作 + 「空间不足」模式）决定，一个字都没改。
10. **试开临时目录在跨卷时会落到源盘**（`<第一卷所在卷根>\.ArchiveFixer.work\volprobe-<guid>`）。
   这是硬链接不能跨卷的硬限制下的取舍：要么写一个**只含硬链接、收工即删**的探针目录，
   要么在"源在 H:、目标在 D:"这种真机常见形态下**完全放弃试开**（那真案 ② 就永远判不出"齐"）。
    选前者。⛔ 它**不碰任何源文件的一个字节**、不复制数据、`finally` 里整棵删掉；
    ⛔ 但"临时物只准落目标目录"这条**在这一格上是有例外**的 —— 如实写在这里，别假装没有。
11. **孤儿卷兜底只覆盖带卷标记的后缀**（`.001`/`.z01`/`.r00`/`.partN`）。名字里完全没有卷标记
    又没有同基名兄弟的文件，`IsProcessArtifactFile` 本来就返回 false（它不会被当其余物删除）。
12. **本轮验证状态（如实）**：跑的是**定向**用例（分卷/无用物/管线这一片），⛔ **没跑全量**；
    真机 `H:` 上的真分卷样本**一个都没跑**（不变量：只读、本轮不碰）；GUI 没看；
    真 7z 试开那一条是**现造的合成三卷**，不是真样本。
13. **导入期保护只挂在"自己就是分卷名"的任务上**：`SourceJunkScanner.AddSiblingVolumePaths` 的前置闸门是
    `FileNameHelper.IsVolumePartFileName(task 自己的文件名)`，不满足就直接返回（连判定器都不问）——
    那是**性能**取舍（一个目录几百个任务，逐任务列目录太贵）。任务自己的路径无论如何都进保护集
    （`CollectProtectedPaths` 先收 `CurrentPath` + `VolumePaths`），所以漏的只是"非分卷名任务的兄弟"这一格。
