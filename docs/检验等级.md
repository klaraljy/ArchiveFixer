# 检验等级（L0–L6）

> 谁定的：用户 2026-09-30 接受这套阶梯，并要求**写进规则、且代码里的闸门对得上**。
> 这份文档是**唯一**写 L0–L6 的地方（⛔ 不要再往 `docs/输出与整理模型.md` 里抄一份 —— 两处写同一件事必然漂移）。
> 相关：`AGENTS.md` §6（不变量）、`docs/输出与整理模型.md`（落点与整理模型）、`docs/真机事故复盘.md`（每次事故的现场）。

---

## 0. 一句话

**每一级都是一道闸门；闸门没答案时，兜底一律落在"什么都不做"那一档。**

不可逆的动作（删源包、搬源包、永久删除）**只允许**发生在 L4 = 可证完整 + L5 收尾复核通过 + 未被取消 + 属于本任务
这四条同时成立的时候。

## 1. 阶梯表（等级 / 目的 / 判据来源 / 唯一出口 / 判不出时怎么办）

| 等级 | 目的 | 判据来源（机器事实，⛔ 不比中文文案） | 唯一出口 | 判不出时怎么办 |
|---|---|---|---|---|
| **L0 识别** | 搞清楚"这是什么格式、认不认得"，**不认识就什么都不做** | `ArchiveTask.IsArchive`（bool）、`ArchiveTask.DetectedFormat`（`"Unknown"` 是字面量常量）、`DetectResult`；加密判读 `ArchiveEncryptionState` | `Services/ArchiveDetectService.ApplyDetectResultAsync`（写字段）+ `DetectAsync`（四条路：缓存 / 常规 / 尾部内嵌 / 拿到卷组）；解压侧收口 `ExtractionCoordinator` 里 `!IsArchive \|\| DetectedFormat == "Unknown"` 那一处 | 格式未知且没开「试解未知格式」⇒ 状态 `已跳过`、**一个字节都不写**；开了就先 `ListAsync` 试列，列不出来同样跳过 |
| **L1 解前** | 写盘之前把"不可能完成 / 会伤到别处"的活挡住 | ① 源文件快照 `SourceFileSnapshot`；② `ArchiveTask.IsVolumeComplete` / `MissingVolumeNames`；③ `PathSafetyReport.IsSafe` / `UnsafeEntries`；④ `BudgetCheckResult.Allowed` / `IsSpaceShortage`；⑤ `SpaceGate` 的可用空间 | ① `ExtractionCoordinator.EnsureSourceSnapshot` + `StopIfSourceChanged`；② 同文件里的缺卷闸门（不变量 7）；③ `Security/ArchivePathGuard.CheckEntries`；④ `Security/ResourceBudget.CheckBeforeExtract`（上限唯一出口 `ExtractionCoordinator.BudgetLimits` ← `ResourceBudgetOptions.FromSettings`）；⑤ `ExtractionCoordinator.ReconcileReservation` → `Storage/SpaceGate.Check`、启动前排序 `Storage/ExtractionScheduler.Build` | 缺卷 ⇒ 报"缺哪几个"、不开工；越界 ⇒ 拒绝该条目 / 整包；超预算 ⇒ 拒绝并带 `StatusText.SecurityCapHint`；空间不够 ⇒ 换下一单 / 标 `SpaceBlocked`。**⚠ 已知缺口 ①：列不出清单时这一级被整段跳过**（见 §3） |
| **L2 解后** | 产物真的落在该落的地方、而且不是空的 | `RecursiveExtractor.FindLandingViolation` 的结论（内部 `ArchivePathGuard.IsInsideRoot`）；`OutputVerifier.Measure` 的（文件数, 总字节）；`OutputVerificationResult` 规则 1/2 | 落点：`Extraction/RecursiveExtractor.FindLandingViolation`；非空：`Extraction/OutputVerifier.Verify` 规则 1（0 个文件）与规则 2（总字节 ≤ 0） | 越界 ⇒ 任务落 `Failed` + `IsOutputVerified=false`、**定稿一步都不做**；空产物 / 全 0 字节 ⇒ 判否（不变量 6） |
| **L3 清单核对** | **只有在有可信清单时**才逐条对账 | `ArchiveListResult.Success` + `Entries` / `FileCount` / `TotalUncompressedSize`；大小写折算结果 `CaseOnlyDuplicateGroups` | `Extraction/OutputVerifier.Verify(stageDirectory, expected)`（比较用 `>=`，预期按"仅大小写去重"折算） | 清单不可信（没列过 / 列目录失败 / 递归展开 > 1 层刻意不给）⇒ **不做核对**，只保留 L2 的底线校验，并把这件事如实记进 `ManifestCrossChecked = false` |
| **L4 完整性分类** | 回答"这一单的结果**能不能被证明**是完整的" | `OutputVerificationOutcome` + `OutputVerificationResult.ManifestCrossChecked`（或任务上的 `ArchiveTask.OutputManifestCrossChecked`）+ `MissingVolumeNames` | `Extraction/ResultCompleteness.cs` 的 `ResultCompletenessClassifier.Classify`（返回 `Complete` / `Incomplete` / `Undeterminable`） | **判不出 ⇒ 一律不删源、不搬源、结果照常保留**，结论如实写"无法确认完整性"（`StatusText.CompletenessUndeterminableFormat`） |
| **L5 收尾复核** | 定稿前后再复核一次"这一单真的成了" | `OutputVerifier.Measure` 的事后预算结论；`StageCommitResult.Attempted` / `FailedCount` | 校验 + 事后预算在 `ExtractionCoordinator.RunPostProcessWork`（定稿在同一个方法里的 `ExecuteFinalLayout`） | 复核不通过 ⇒ 落 `Failed`、不定稿、源包不动。**⚠ 已知缺口 ②：定稿**之后**没有第二次复核**（见 §3） |
| **L6 删除闸门** | 删 / 搬源包之前，把上面所有结论 + 取消 + 归属一起查一遍 | `TaskOutcome`、**L4 裁决**、调用方传进来的 `cancelled`、`ArchiveTask.RestDirectoryPath`、`ArchivePathGuard.IsInsideRoot` | ① 其余物删除：`Storage/RestItemPurger.Purge`（五道门槛）；② 空间不足模式永久删源：`ExtractionCoordinator.PurgeSourcePackageForSpaceTight`；③ 源包移入其余物：`ExtractionCoordinator.MoveSourcePackageIntoRest`；④ 链尾：`Extraction/ChainCompletionGate.DescribeBlocker`（+ `ExtractionCoordinator` 里那几处链尾加固） | 任何一条不成立 ⇒ **一个字节都不动**，写 WARN 说清是哪一条拦下的。**⚠ 已知缺口 ③：③ 页手工清理其余物是旁路**（见 §3） |

## 2. "判不出就不动"红线（用户 2026-09-30）

1. **L4 = 判不出 ⇒ 不删源、不搬源**（`ResultCompletenessVerdict.AllowsSourceRemoval` 只有 `Complete` 才为 true）。
2. **结果照常保留**：判不出完整性**不改变**这一单产出什么；只改变"我们敢不敢动源包"。
3. **结论如实写**："无法确认完整性"（`StatusText.CompletenessUndeterminableFormat`）—— ⛔ 不许把它写成"校验通过"，
   也不许反过来写成"校验失败"（两句话都是错的：一句是假话，一句会给用户一个错的理由）。
4. **⛔ 兜底永远落在"什么都不做"那一档**：枚举默认值 = `Undeterminable`；新增任何分支时，
   忘了赋值也只会变成"不删"，不会变成"删"。

## 3. 已知缺口（⛔ 不许只写"已实现"糊过去）

### 缺口 ①：列不出清单时，L1 的"路径预检 + 资源预算"被整段跳过 —— **只写文档，未修**

- 位置：`src/ArchiveFixer/ViewModels/ExtractionCoordinator.cs`，`preflightList == null` 那个分支
  （连内容清单都读不出来的两条 WARN：`StatusText.EncryptedHeaders` 档与"没能列出归档内容"档）。
- 现状：`preflightList == null` ⇒ `ArchivePathGuard.CheckEntries`（路径预检）与
  `new ResourceBudget(BudgetLimits).CheckBeforeExtract`（资源预算）**都不执行**，直接往下解。
  落点校验（L2）仍然照做，所以"产物越出目标根"这一条不会被跳过。
- 为什么没顺手修：这一档的**主要来源是加密头**（RAR `-hp` / 7z `-mhe=on`）—— 连文件名都读不出来，
  手上根本没有条目名可预检。硬拦等于把"需要密码才能列出内容"的包**全部挡在门外**，
  而它们本来正是这个工具要处理的对象。要真修得先有"解压时逐条流式拦截"的能力，
  那是解压器内部的事，不是这里加一行判断能解决的。
- 风险等级：中。加密头包的越界条目**只有** L2 落点校验兜底（事后拦），不是事前拦。

### 缺口 ②：L5 没有"定稿之后"的第二次复核 —— **只写文档，未修**

- 位置：`Extraction/OutputVerifier.Verify` 全仓只有两个调用点，传的都是**暂存目录**
  （`ExtractionCoordinator` 里候选循环那一处、以及 `VerifyStageProductsAsync` 那一处）；
  `OutputVerifier.Measure` 另外两处只做工作区清理统计，不是门。
- 现状：定稿（`ExecuteFinalLayout`）之后**没有任何一次**对最终落点重新核对；
  "定稿搬过去的那一份是不是完整"目前只有 `StageCommitResult` 的搬运计数兜着。
- 为什么没顺手修：定稿是"暂存 → 成品"的同卷改名，重新枚举最终落点等于把整棵树再走一遍
  （几万到几十万个文件），代价与收益不成比例；而搬运失败本来就会落 `Failed`。
- 风险等级：低。留在这里是为了**别把它当成"验过了"**。

### 缺口 ③：③ 页手工"清理其余物"是 L6 的旁路 —— **只写文档，未修**

- 位置：`src/ArchiveFixer/Services/MaintenanceCleanupService.cs` 的 `CleanProcessArtifacts`
  （门槛只有三条：作用域已解析、与预览一致、`ArchivePathGuard.IsInsideRoot`）。
- 现状：它**不读** `TaskOutcome` / L4 裁决，也就是说被 `MoveSourcePackageIntoRest` 搬进 `其余物\`
  的**源包本体**可以沿着这条"用户确认即删"的路被删掉，与 L4/L5 无关。
- 为什么没顺手修：这条路本来就是**用户显式确认**的手工动作（"我要清掉这些其余物"），
  加一条"完整性判不出就不许清"会让他连自己确认过的东西都清不掉；
  而自动路径（L6 的那四道门）已经全部收紧到"可证完整"。
- 风险等级：低（需要用户点击 + 确认框两次）。⛔ 但**不许**把它读成"删源已经全走闸门了"。

### 缺口 ④：L0 的 `IsArchive` 在"试解未知格式"成功后会被改写成 true —— **已知，保留**

- 位置：`ExtractionCoordinator` 里"引擎能列出来就认它"那一处。
- 现状：改写之后，下游读的是**被改写过的** `IsArchive`，而 `DetectedFormat` 仍是 `Unknown`。
- 保留理由：这正是"试解未知格式"这一档要的效果（后缀与魔数都认不出、但引擎确实能开）；
  下游凡是要判"是不是归档"的地方读的都是这两个字段的组合，改写不会让它误判成别的格式。
- 风险等级：低。⛔ 但新增判据时**不许只看 `IsArchive` 一个字段**。
