# ADR 0004：ExtractionCoordinator 类型总行数目标（5,479 → 3,000）的架构评审

- 状态：接受（类型总行数目标暂缓，非永久豁免）
- 日期：2026-11-15
- 关联：ADR 0003 / M5 / M6

## 事实

- `ExtractionCoordinator` 37 个 partial 已全部按职责抽出 29 个步骤 Handler（`ViewModels/Extraction/Steps/`），类型总行数从 18,395 降到 **5,479**（HEAD `67665813` 实测）。
- 每个 partial 文件都 ≤800 行；新 Handler 都 ≤800 行、1 个顶层类型；结构基线中的大文件条目已逐批删除。
- 剩余 5,479 行主要是三类：
  1. `ServiceForwarding.cs` 774 行：`IWorkspaceStepHost`/`IExtractionStepHost` 等接口的显式实现与跨步骤转发（对外契约，改掉会动其他 partial、测试和界面调用点）；
  2. `ExtractionCoordinator.cs` 487 行：构造、跨 partial 共享状态、公开命令/属性（ViewModel 绑定面）；
  3. 其余 29 个步骤分片约 4,200 行：每个分片只剩“有外部调用方的同名薄转发 + 最小 internal 访问器 + 少量仍被其他 partial 直接读写的状态字段”。
- 继续把薄转发搬进新类，只能减少几十行/片；要再降 2,479 行必须改调用点（其他 partial、Handler、测试、XAML 绑定面）或删公开兼容 API。

## 决策

- **继续保留 M5 的硬门禁：每个源文件 ≤800 行、每文件 1 个顶层类型、单方法 ≤150 的目标由 M3/M5 守卫继续执行。**
- **类型总行数 3,000 的目标暂缓到 M6/M7 的 API 收口之后**：M6 把 Models/INPC 和绑定适配层分开、M7 完成测试分层后，才允许改 `ServiceForwarding` 的接口实现与调用点；届时重新评估本目标。
- 不把 5,479 行写成“默认长期例外”；本 ADR 是明确的架构评审记录，退出条件是“接口/调用点收口完成后再拆一轮”，并由 M6/M7 的验收复核。
- 禁止为了压行数：删公开属性/命令、把属性压成一行转发、按行数切方法、改测试断言、按样本名加分支。

## 后果

- M5 的“单文件 800 / 单类型文件结构”达标；`ExtractionCoordinator` 类型总行数目标尚未达标，登记为本 ADR 的未结项，不宣称 M5 全绿。
- 后续任何“类型总行数”验收必须引用本 ADR 与实测数字，不得口头豁免。
- M6/M7 完成后必须重新测量；若仍无法在保持公开 API/测试不变的前提下降到 3,000，需再开 ADR 决定是否接受 5,000 级或做破坏性接口重构。
